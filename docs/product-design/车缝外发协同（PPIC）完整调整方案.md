## 1. 调整结论

本轮不是新建一套PPIC系统，也不是重新设计整套FCS界面，而是在当前原型已经具备的菜单、路由、任务、仓储交接、裁片放行、打印、批版、后道回货和标准列表能力上，继续把业务事实收口到正确对象和正确责任人。

调整采用四种处理等级：

1. **直接保留：** 当前实现与业务一致，只补回归验证和必要文案。
2. **针对性优化：** 保留页面、路由和主要数据结构，调整列表布局、筛选、操作入口、字段或局部交互。
3. **局部干净重写：** 仅重写已经与业务冲突、继续叠补丁会扩大错误的投影或动作；保持原有路由、外壳、数据入口和视觉体系兼容。
4. **完整删除：** 删除已经明确不需要的PPIC专属入口、路由、页面、处理器、Mock和旧文案；相邻专业域的真实事实源不随之删除。

最终目标是：

- 仍然使用当前Vite、Vanilla TypeScript字符串模板和`renderAppShell`外壳；
- 仍然使用当前企业后台视觉、标准列表组件、抽屉／弹窗、分页和统一打印预览；
- 不迁移React，不引入新框架，不新建平行库存账、平行回货账或平行任务池；
- 对当前不合理的“部位排除改变回货责任”“裁床交出后自动模拟工厂接收并开工”“分配只检查裁片放行却不硬校验配料”等局部逻辑进行干净改写；
- 新增“生成单全流程耗时”时，以现有真实业务对象的只读投影为基础，不把现有43条静态生产进度Mock直接改名冒充全链事实；
- 页面形态保持原来的管理后台体系，只做信息层级、可读性和操作闭环上的针对性优化。

## 3. 现有能力处理边界

### 3.1 直接保留

以下能力不推翻：

- `renderAppShell`、顶部系统切换、左侧菜单、页签和现有后台视觉；
- `renderStandardListPage`、`renderStandardListFilters`、标准表格、分页、列配置、弹窗／抽屉等公共组件；
- 当前车缝外发协同的8个业务路由及其页面主体结构；
- 统一任务分配工作台的任务来源、直接派单和加工价格填写方向；
- 有效任务分配快照、工厂PPIC快照和显式责任移交历史；
- 裁片放行单、目标数量、可用放行数量和版本历史；
- 裁剪配料、裁片单、铺布单、特殊工艺加工单、PDA交接、打印和后道最终确认等既有专业事实源；
- 批版建议中的多图上传、四类结构化意见、线下批版单照片和“明确要求再次批版”能力；
- 裁片退仓中“PPIC建单、仓库接收”和实物数量／责任调整数量分离的主体结构；
- 财务、质量、结算等相邻专业域的既有页面和数据，只是不在PPIC菜单内重复建设。

### 3.2 针对性优化

以下保留原页面和路由，只调整局部：

- 8个现有专业页统一Tab、筛选、列表、分页和操作列；
- 所有有搜索区的页面统一提供“查询”“重置”，输入条件不实时重绘整页；
- 除“我的工作台”外删除重复统计卡片；
- 车缝任务操作列增加领料单打印，把专业入口全部收进操作列；
- 批版建议删除解释性大横幅，只保留必要的Tab、筛选、列表和动作；
- 补料跟进补齐真实场景Mock；
- 裁片退仓把Tab、搜索和主操作分区，补齐待接收、异常、已入仓Mock；
- 所有款式／物料缩略图使用与对象对应的稳定图片，并支持大图、加载和失败反馈；删除通用`/shirt-sample.jpg`冒充多款式图片的做法；
- 责任移交仅在凌云、婕哥管理视角开放，新负责人选择、剩余事项和历史保持原界面风格。

### 3.3 局部干净重写

以下继续叠补丁会保留错误含义，应在原模块范围内重写：

1. **车缝任务全集投影：** 从“由批版／补料／回货等卫星记录拼出任务”改为“以全部当前有效车缝执行任务为主集合，再左连接专业事实”。
2. **部位排除投影：** 删除其改变有效齐套、回货责任或下游门禁的计算；如保留标记动作，只生成“参考查看标记”，严格需求和欠片永远不变。
3. **任务可分配判断：** 把裁片放行、裁剪配料、车缝配料统一为提交前硬校验，列表与提交共用同一函数，不能只在弹窗展示。
4. **裁片交接启动：** 删除裁床一提交便自动写成“工厂已接收、任务已开工”的模拟；改为领料单／二维码驱动的真实交出确认，再由接收事实推动后续节点。
5. **回货聚合：** 从少量Demo生产单改为所有当前有效执行任务，唯一数量来源仍是后道最终确认版本。
6. **回货SLA：** 收口为一套规则和一套截止时间算法，补上起算周周日排除规则。
7. **生成单全流程耗时：** 新建只读生产单投影和节点明细，不复用静态43条进度Mock作为事实源。

### 3.4 完整删除或禁止恢复

- 不恢复“综合查询”；
- PPIC侧“对数与结算跟进”的菜单、路由、页面、专属投影、处理器和专项Mock保持删除；
- 删除车缝任务页面向业务用户的“历史迁移审计”入口；原型无需向业务用户展示生产迁移报告；
- `migration-audit`若没有其他开发检查调用，则连同路由、渲染器、处理器和专属数据删除；若仍被专项脚本引用，只保留开发期检查函数，不保留业务页面；
- 删除“部位排除会减少最终应回”“排除后允许不完整成衣进入后道”等旧文案和计算；
- 删除裁床交出后自动模拟工厂接收／开工的写动作；
- 不新增电子合同，不把现有相邻合同能力设为PPIC分配、领料、生产、批版或回货门禁；
- 不把上游实际耗时直接解释为超时，不加入被打码内容、JT／T、产品等级、产能自动排期、扣款或结算分析。

| 普通PPIC | 当前责任属于本人的执行任务及其关联生产单 | 打印／补打领料单、确认收到产前版样衣并上传多图、转交批版人员、反馈工厂、补料跟进日志、创建裁片退仓申请 | 切换成他人身份、替仓库确认实交、发起补料单、填写回货、发起责任移交、确认少数／超数 |
| 凌云、婕哥 | 团队全部执行任务、未分配任务和全部相关生产单 | 普通PPIC动作、显式责任移交、少数／超数管理确认 | 冒充某普通PPIC形成其操作记录、替仓库／后道确认 |
| 裁床 | 放行、裁剪、裁片交出、补料相关对象 | 放行版本、裁剪完成、补料发起／推进、裁片交出确认 | PPIC跟进、批版建议、后道回货确认 |
| 辅料仓／中转仓 | 待交出的面料、辅料、领料单和批次 | 扫码确认实交、记录差异、出库事实 | 代PPIC分厂、修改任务价格 |
| 批版人员 | 已由PPIC转交的产前版样衣 | 确认接收实物、填写结构化批版建议、上传线下单据照片、明确是否再次批版 | 修改任务分配、填写大货回货 |
| 三方车缝工厂 | 自己承接的执行任务 | 现有工厂端适用动作、线下提出退仓需求 | 在PPIC页面建退仓申请、修改裁片放行或PPIC责任 |
| 后道回货确认岗位 | 工厂送回的成衣批次 | 最终确认回货数量、时间和差异 | 代PPIC调整任务或裁片欠片 |

### 5.2 核心对象关系

```text
生产单
├─ 上游面辅料采购／加工／中转仓／裁剪／特殊工艺／裁片放行事实
├─ 来源车缝任务
│  ├─ 独立车缝：可按完整SKU分给多厂
│  ├─ 车缝＋烫包：整任务单厂
│  └─ 裁剪＋车缝＋烫包：整任务单厂
└─ 执行任务（一家工厂一张）
   ├─ 有效分配、价格、任务PPIC快照
   ├─ 领料单与仓库实际交出记录
   ├─ 裁片欠片／面辅料差异
   ├─ 产前版样衣与批版建议轮次
   ├─ 裁床补料关联、裁片退仓
   ├─ 后道最终确认回货
   └─ 显式责任移交历史
```

所有会改变任务履约的事实绑定执行任务或有效分配；生产单只做跨执行任务聚合。独立车缝分多厂时，一个工厂的超交、超回、样衣或回货不能覆盖另一个工厂的未完成。

## 6. 三类任务与可分配门禁

### 6.1 分类和拆分

| 任务类型 | 是否允许多厂 | 拆分颗粒度 | 交出对象 | 是否有裁片欠片 |
|---|---|---|---|---|
| 独立车缝 | 是 | 完整SKU；同一SKU不得按数量拆开 | 裁片＋车缝辅料 | 是 |
| 车缝＋烫包 | 否 | 整任务 | 裁片＋车缝辅料 | 是 |
| 裁剪＋车缝＋烫包 | 否 | 整任务 | 面料＋辅料 | 否 |

“独立车缝单厂”和“独立车缝且分多厂”只是同一任务类型的分配结果，禁止继续作为两个任务类型出现在筛选、枚举或统计中。

### 6.2 统一门禁计算

列表、派单弹窗和提交动作必须调用同一份可分配判断，返回：

- `readinessState`：`暂不可分配`、`可分配尚未分配`、`已分配`；
- `blockingReasons[]`：每个缺失条件、来源单号、要求量、当前量和单位；
- `readyAt`：所有适用门禁最后一次满足的时间；
- `sourceRefs[]`：放行版本、裁剪配料单、车缝配料单等来源；
- `checkedAt`：本次投影时间，仅用于说明查询快照，不冒充业务时间。

门禁公式：

```text
独立车缝／车缝＋烫包可分配
= 有效裁片放行可用数量 >= 本次拟分配数量
  AND 车缝辅料全部配齐

裁剪＋车缝＋烫包可分配
= 裁剪配料全部配齐
  AND 车缝配料全部配齐
```

缺少预期物料范围、缺少来源投影、数量单位不一致或来源记录失效时必须判定为“暂不可分配”，不能用当前代码中“没有投影即ready”的兜底继续派单。

### 6.3 分配工作台调整

保留现有`/fcs/dispatch/workbench`页面、顶部操作、任务类型Tab、筛选、表格和派单弹窗。在“独立车缝任务”和“合并任务”内部增加一层业务三态Tab：

- 暂不可分配：展示所有阻断原因和来源入口，不显示可提交的派单按钮；
- 可分配尚未分配：展示可用数量、门禁满足时间，PPIC明确选厂并填写价格；
- 已分配：展示工厂、任务PPIC、分配时间、加工价格和执行进度。

“满足门禁”只开放人工分配，不触发自动派单。分配时：

- 当前登录人必须是有效PPIC或凌云／婕哥；
- 工厂必须有且只有一个启用PPIC；
- 加工价格必须大于0，并保存币种、单位、填写人和确认时间；
- 独立车缝多厂必须按完整SKU分配；
- 两个组合任务必须整任务单厂；
- 不增加核价审批、工厂确认价格或电子合同门禁。

## 7. 领料单、扫码交接与数量账

### 7.1 车缝任务操作列

车缝任务页面保持标准列表，操作列按任务类型显示适用动作：

| 任务类型 | 打印动作 | 专业入口 |
|---|---|---|
| 独立车缝 | 打印裁片领料单、打印辅料领料单 | 交出与欠片、批版建议、补料跟进、回货跟进、裁片退仓、全链详情 |
| 车缝＋烫包 | 打印裁片领料单、打印辅料领料单 | 同上 |
| 裁剪＋车缝＋烫包 | 不生成裁片领料单；从既有面辅料交出详情打印面料／辅料领料内容 | 面辅料交出、批版建议、回货跟进、全链详情 |

动作数量较多时使用现有Dropdown或“更多”菜单；主动作保留一到两个，不能把动作重新放回“专业来源”列。

### 7.2 复用统一打印服务

不新建独立打印框架。扩展现有`PICKUP_SLIP`／`ISSUE_SLIP`来源适配，新增PPIC领料用途和模板标题。领料单至少包含：

- 领料单号、打印版本、有效状态和二维码；
- 执行任务、生产单、SPU／款式图、三方工厂、任务PPIC；
- 交出仓库、领料对象、颜色、尺码、部位、物料编码、批次／菲票／包号；
- 应领、此前已领、本次可领、本次实领、差异和单位；
- 打印人、打印时间、交出人、领取PPIC和现场备注／签字区。

原型默认使用A4打印预览和一联签字区；现场纸张、联数以后可只调整模板参数，不改变业务对象。

### 7.3 二维码和幂等

二维码绑定“执行任务＋领料单＋打印版本”，扫码后进入既有仓库／PDA交出页面并再次核对当前有效版本。规则为：

- 补打只增加打印版本，不新增任务、不新增应领量；
- 作废版本扫码必须阻断并提示打印最新版本；
- 同一个交出事件ID重复提交返回已处理结果，不重复累计；
- 允许同一领料单分批交出，每一批生成独立交出记录；
- PPIC不能代替裁床待交出仓或辅料仓确认实交；
- 实交差异按颜色、尺码、部位／物料和单位保留；
- 交出事实继续写入现有PDA交接、裁片交出责任或面辅料交出账，不新建第二套库存流水。

### 7.4 删除自动接收和自动开工

当前`submitCuttingSewingDispatchBatch`之后调用自动接收／启动的逻辑必须拆除。目标链路为：

```text
PPIC打印领料单
→ PPIC到裁床待交出仓／辅料仓
→ 交出方扫描有效二维码
→ 核对本次实交和差异
→ 确认交出并形成线上记录
→ 接收方确认或既有规则完成写回
→ 才更新领取／交接事实和后续可执行节点
```

“打印成功”不能代表已领料，“裁床提交”也不能直接代表工厂已经收到。

### 7.5 裁片数量公式

前两类任务按执行任务、SKU、颜色、尺码和部位计算：

```text
应交片数 = 执行任务分配件数 × 每件该部位用片数
累计实交片数 = 当前有效交出批次实交片数之和
欠片 = max(应交片数 - 累计实交片数, 0)
超交 = max(累计实交片数 - 应交片数, 0)
严格齐套件数 = 所有必需部位 floor(累计实交片数 ÷ 每件用片数) 的最小值
```

不同部位、片与件、不同单位不能相互抵消。未发生任何有效交出时归入“未交出”，不提前显示欠片。

### 7.6 部位排除改为参考查看

当前会改变`effective kit`和回货责任的排除版本必须重写。目标只允许形成“参考查看标记”：

- 原必需部位、应交片数、欠片和严格齐套不变；
- 不改变执行任务最终应回责任；
- 不放宽后道接收完整成衣的门禁；
- 页面并列展示严格齐套、参考齐套／参考应回，并明确“仅供跟进判断”；
- 标记／取消标记保留人、时间、原因和证据，但不需要审批；
- 整个部位未交、缺口达到需求量一半、影响生产或逾期时可在工作台提升优先级；极小差异仍保留明细但不占据高优先级首页入口。

旧排除记录只作为历史查看标记读取，不继续参与数量责任计算。

## 9. 回货SLA统一规则

### 9.1 标准节点

| 任务类型 | 30% | 70% | 100% |
|---|---:|---:|---:|
| 独立车缝 | 第4个计时日 | 第8个计时日 | 第9个计时日 |
| 车缝＋烫包 | 第5个计时日 | 第9个计时日 | 第10个计时日 |
| 裁剪＋车缝＋烫包 | 第6个计时日 | 第9个计时日 | 第12个计时日 |

里程碑数量统一为：

```text
节点目标件数 = ceil(执行任务有效分配件数 × 节点比例)
节点实际件数 = 该执行任务后道有效最终确认数量累计
```

### 9.2 起算与周日

- 直接派单：分配完成即视为有效接单，分配时间和接单时间相同；
- 竞价／投标：以工厂实际确认接单时间起算；
- 起算事件所在自然周的周日不占用计时日；
- 若起算日就是周日，下周一为第1个计时日；
- 跨入下一周后的周日正常计入；
- 本轮不处理其他节假日、暂停、延期、中止、撤销或重派后的继承规则；
- “生成单全流程耗时”的实际耗时仍是两个真实时间点直接相减，不扣周日；周日规则只用于计划截止日和临期／延期判断。

两套现有SLA投影必须共用同一纯函数和同一规则版本，避免回货页、工作台和耗时明细给出不同截止时间。

## 10. “生成单全流程耗时”详细方案

### 10.1 页面定位

该页面一行代表一张生产单，回答“每个环节实际从何时到何时、实际用了多久、依据哪些单据”。它不是工作台、综合查询、超时排名或可视化看板。

列表左侧固定生产单／款式，右侧固定“查看全链明细”，中间十个节点在表格容器内横向滚动。每个节点单元格只显示：

1. 开始时间；
2. 结束／达成时间；
3. 实际耗时，或尚未结束时的已用时。

不显示额外抽象状态。没有可靠时间时显示“—”，原因只在节点明细中说明。

### 10.2 十个节点的来源与计算

| 节点 | 开始时间 | 结束／达成时间 | 当前来源与实施要求 |
|---|---|---|---|
| 面辅料采购 | 当前有效采购单中最早下单时间 | 生产单全部必需面辅料首次全部完成入库的时间 | 增加生产单→BOM需求→采购行→仓库有效收货的只读适配；当前碎片化来源不能用静态时间补齐 |
| 面料加工 | 生产准备阶段最早有效单据生成时间 | 全部适用准备单据最晚完成时间 | 聚合染色、印花及其他裁剪前面料准备单据；作废／替换单只进历史明细 |
| 裁剪配料 | 生产单所需裁剪物料在中转仓首次整体配齐时间 | 全部裁剪配料任务最晚确认完成时间 | 从中转仓收货／库存和`production-material-prep`确认记录推导；必须区分“已配齐”和“已配料” |
| 完成裁剪 | 裁剪工厂首次有效领料时间 | 所有有效裁片单下全部铺布单最晚`cuttingCompletedAt`，含补料裁剪 | 读取领取记录、裁片单、铺布／裁剪事件和补料关联；仍有有效补料裁剪未完成时不形成最终结束 |
| 特殊工艺加工 | 全部辅助／特种工艺单最早“确认接收”时间 | 全部适用加工单最晚完成时间 | 读取`managementDomain`和`nodeRecords`；不包含后道工艺；无适用单据显示“—” |
| 裁片放行 | 第一条有效且放行量大于0的放行版本确认时间 | 累计有效放行齐套数量首次达到当前有效目标的版本时间 | 同一生产单一张放行记录、多次版本；明细显示每版前后数量、风险、目标变化和选取理由 |
| 外发加工派单 | 所有适用执行任务的门禁最后满足时间 | 所有适用执行任务最晚完成分厂时间 | 前两类取放行可用量和车缝配料的较晚时间；裁剪组合取裁剪配料和车缝配料的较晚时间 |
| 30%回货 | 全部有效执行任务中最早有效接单时间 | 各任务分别首次达30%，再取最后一个达成时间 | 只累计后道最终确认；一厂超回不能抵另一厂未达 |
| 70%回货 | 同上 | 各任务分别首次达70%，再取最后一个达成时间 | 任务分支明细展示各自目标、接单、达成和实际耗时 |
| 100%回货 | 同上 | 各任务分别首次达100%，再取最后一个达成时间 | 100%只认后道确认收货，不认工厂登记、质检完成或成衣入仓 |

### 10.3 有效事实与版本

节点计算只使用当前有效业务事实：

- 被撤销、作废或正式替换的记录不参与主表；
- 旧记录仍进入明细并说明失效原因和替代记录；
- 重复同步或重复确认按稳定事件ID去重；
- 目标、BOM、任务或放行发生版本变化时重新计算当前主表，但保留旧计算依据；
- 不适用和数据缺失都在主表显示“—”，明细分别说明“该路径不需要”或“缺少哪个来源事实”，不能混为一个状态标签。

### 10.4 多执行任务聚合

回货节点先按执行任务计算，再聚合生产单：

```text
单任务节点达成 = 后道最终确认累计 >= ceil(任务分配数 × 比例)
生产单节点达成 = 所有当前有效执行任务分别达成
生产单节点结束 = 各任务首次达成时间中的最晚值
生产单节点开始 = 各任务有效接单时间中的最早值
```

独立车缝分多厂时，节点明细必须逐任务／工厂展开。生产单总跨度只用于全流程耗时展示，不替代每家工厂自己的SLA判断。

### 10.5 节点明细抽屉

点击任一节点打开同一套明细抽屉，至少包含：

- 节点口径和本行计算结果；
- 来源单据类型、单号、物料／工序／SKU、执行任务、工厂；
- 每张单据自身状态和原始时间字段；
- 是否入选开始／结束／首次达成，及明确原因；
- 作废、替换、订正和版本历史；
- 返回来源页面的入口；
- 缺失数据的具体对象和补录来源，不提供在耗时页直接篡改来源时间的入口。

裁片放行抽屉额外展示目标、当前齐套、每次放行、前后累计、风险原因、操作人和版本。回货抽屉额外展示每个执行任务的比例目标、后道批次、确认版本和达成时间。

### 10.6 查询、列和导出

筛选至少包括：

- 生产单号／SPU；
- 普通PPIC或团队PPIC；
- 三方车缝工厂；
- 任务类型；
- 订单交期；
- 指定耗时节点；
- 节点开始／结束时间范围；
- 实际耗时范围。

必须有“查询”和“重置”；编辑条件不立即改变表格。页面不设置统计卡片，也不强行制造状态Tab。

导出当前查询范围的全部数据而不是当前页，至少两张表：

1. 生产单耗时汇总：一生产单一行，十节点开始、结束和耗时；
2. 节点来源明细：一来源事实一行，包含原始时间、状态、版本、是否入选、原因和来源入口。

### 10.7 数据范围

- 普通PPIC查看本人当前负责执行任务所关联的生产单，并能回溯该生产单已经发生的上游历史；
- 同一生产单属于多个PPIC时，每人都可看到生产单，但明细必须清楚标出本人和他人执行任务；
- 凌云、婕哥查看团队全部生产单并可按PPIC筛选；
- 尚未分配、尚无任务PPIC的生产单只进入负责人团队范围；
- 原型Mock用于覆盖关系与场景，不要求导入真实20多名PPIC、600多家工厂或生产数据。

## 11. 页面一致性与交互规则

### 11.1 标准列表

除“我的工作台”和明确的详情页外，9个菜单中的8个专业页使用现有标准列表骨架：

```text
页面标题＋主要动作
业务Tab（确有互斥分类时）
筛选区：字段＋查询＋重置
列表区：标题／列表动作＋表格
分页区
抽屉／弹窗
```

统一要求：

- Tab和搜索区分开；
- Tab数量就是该互斥业务分类的数量，不再复制统计卡片；
- 没有互斥分类的耗时页不制造Tab；
- 搜索字段变化只更新草稿条件，点击查询才应用；
- 重置清空筛选但保留当前业务Tab；
- 操作列固定右侧，生产单／款式列固定左侧；
- 宽表只在表格容器内部滚动，页面主体不得横向溢出；
- 当前页不持久化，列显示、列顺序、冻结和每页条数按路由持久化；
- 弹窗、抽屉、Tab、行操作做局部DOM更新，不用`root.innerHTML`整页重绘。

### 11.2 图片

凡出现款式或物料：

- 图片与款号／名称放在同一单元格；
- 一条记录一张真实对应图片，不能所有款式共用通用衬衫占位图；
- 点击缩略图查看大图，支持遮罩、关闭按钮和Esc；
- 加载中、失败和缺图状态可见；
- 缺少对应素材的Mock不得以“已完成”交付，必须记录素材缺口。

### 11.3 文案与颜色

- 不显示英文技术状态码；
- 红色仅用于错误／阻断，黄色用于待处理／风险，绿色用于已完成／一致，蓝色用于主动作和信息；
- 删除“系统投影、有效齐套、责任版本”等难懂的首屏解释长文，复杂口径放入帮助说明或详情；
- “产前版样衣”只指三方工厂实物，“批版建议”只指业务动作和结果；PCS对象统一为“首单样衣”。

## 12. Mock场景设计

Mock必须支撑完整阅读和数据操作，至少覆盖以下互不等价场景：

1. 独立车缝单厂，门禁齐备、尚未分配；
2. 独立车缝按完整SKU分给两厂，一厂30%达成、一厂未达；
3. 车缝＋烫包有裁片放行但辅料未配齐，提交派单被阻断；
4. 裁剪＋车缝＋烫包裁剪配料已齐、车缝配料未齐，无裁片欠片；
5. 未交出任务；
6. 分批交出后不欠片；
7. 分批交出且整个部位欠缺，严格齐套与参考查看并列；
8. 裁床补料中、部分补交、补齐和不再补料；
9. 产前版样衣多图接收、待批版、有问题但不再次批版、有问题且再次批版、已反馈工厂；
10. 回货按三类任务分别在30%／70%／100%前后，包含欠辅料／欠裁片的非工厂责任；
11. PPIC创建退仓申请、仓库少收异常、已入仓且不调责任、已入仓且有明确责任调整；
12. 凌云或婕哥移交未完任务，原PPIC历史不被覆盖；
13. 一张生产单包含多采购单、多准备工序、多裁片单、多铺布单、多次放行和多工厂回货；
14. 上游来源作废／替换、节点不适用和关键时间缺失；
15. 领料单首次打印、补打、失效二维码、重复扫码、分批扫码和数量差异。

每个Mock必须使用稳定ID，图片与对象对应，且数据来源能在详情中逐条解释，不能在查询函数中无条件重复播种导致刷新后数量翻倍。

## 14. 分阶段实施计划

### WP0：冻结范围与建立现状契约

**修改：** 不改业务代码；建立任务边界、原子需求清单和旧行为最小复现。

**验证证据：** 分支／HEAD、任务diff清单、8个现有页面和任务分配工作台的基线截图。

**完成条件：** 每个需求编号都能映射到后续工作包；现有用户无关差异不进入任务diff。

### WP1：菜单、路由和标准列表收口

**业务目标：** 形成9个直接菜单并统一专业页布局。

**文件／符号：** D19、D21和8个现有专业页面。

**修改：** 新增耗时菜单／路由；移除业务迁移审计入口；Tab与筛选分区；补查询／重置；删除非工作台统计卡；保留详情辅助路由。

## 15. 历史兼容与原型边界

### 15.1 兼容策略

- 保持现有8个业务路由不变，只新增耗时路由；
- 保持现有有效分配、裁片放行、样衣／批版、退仓、责任移交和后道确认记录的外部标识；
- 旧部位排除版本按“历史参考查看标记”只读展示，不参与新公式；
- 旧退仓记录中的排除原因保留原文，但新建单不再提供该原因，不由其直接减少最终应回；
- SLA增加规则版本，旧Mock按新规则重新投影，不静默混用自然日与新算法；
- 删除业务迁移审计页不等于删除开发期一致性检查；需要的检查迁入脚本并只输出原型数据质量结果；
- “生成单全流程耗时”只读现有事实；发现缺少生产单关联或历史时间时，在相应来源域补最小字段／关联，不在耗时页面维护第二份手工时间。

### 15.2 原型边界

本项目是产品原型：

- Mock用于证明字段、关系、状态和交互；
- 不要求导入真实20多名PPIC、600多家工厂和真实生产数据；
- 不把Mock操作写成生产系统已经发生；
- 不实现真实后端、数据库、完整鉴权、离线队列或自动重试基础设施；
- 但原型内部必须保持角色、数量、单位、版本和幂等关系正确，才能用于业务评审。

## 16. 明确不纳入本轮

- 上游六／七个环节的标准周期和超时判定；
- 订单、工厂、部门、采集超时原因、排名和可视化看板；
- 三方工厂月产能、日产能、产品等级和自动排期／交期计算；
- JT、T指标；
- 核价、工价审批、议价和工厂价格确认；
- 新电子合同或合同门禁；
- 除起算周周日外的节假日、延期、中止、撤销和重派时效继承；
- 部位排除审批；
- 裁床不再补料审批；
- 扣款、申诉、最终结算数量和金额公式；
- 产前版样衣问题对真实后道回货的阻断；
- 后道工艺纳入特殊工艺查询；
- PPIC绩效排名。

## 20. 正常场景、边界场景与全流程数据验证

实施完成后至少用以下数据链路验证，不得只看静态页面或只运行构建：

1. **独立车缝单厂正常链：** 未配齐→放行与辅料齐备→可分配未分配→PPIC填价选厂→打印两类领料单→两仓扫码交出→样衣多图→批版建议→后道分批回货→30%／70%／100%→任务完成。
2. **独立车缝多厂正常链：** 按完整SKU分给两厂，生成两个执行任务；分别计算交出、欠片、批版、回货和SLA；生产单里程碑必须等待两厂都达成。
3. **车缝＋烫包欠片链：** 已放行但部位少交；欠片、补料、参考查看、非工厂责任和后续补交联动，不能让不完整成衣进入后道。
4. **裁剪＋车缝＋烫包链：** 裁剪配料与车缝配料一项未齐时阻断；两项齐备后开放分配；只打印／交出面料和辅料，无裁片欠片。
5. **领料交接边界链：** 分批扫码、少交、多交、补打、重复扫描、旧版本二维码、非交出仓身份和PPIC代确认均逐项验证。
6. **批版边界链：** 多图分次追加；有问题四类意见至少一项；有问题但不再次批版仍允许后道回货；明确要求再次批版时新增轮次且旧轮次可追溯。
7. **退仓边界链：** 工厂线下申请→PPIC建单→仓库少收异常→恢复后入仓；实物退仓量和责任调整量分别变化并有原因。
8. **SLA边界链：** 三类任务逐一验证起算周周日；起算日为周日；跨到下一周周日；比例目标向上取整；23:59:59边界；后道确认版本作废／替换。
9. **责任边界链：** 工厂主数据换PPIC不改变未完任务；凌云／婕哥显式移交后新责任生效；原责任、剩余事项和操作历史仍可见。
10. **生产单耗时正常链：** 多采购单、多准备工序、中转仓整体配齐、多裁剪配料、多铺布／补料、辅助／特种工艺、多次放行、多执行任务和三档回货均能回溯来源。
11. **生产单耗时边界链：** 来源单作废／替换、目标数量修改、不适用节点、必要时间缺失、一个工厂超回而另一工厂未达、未分配生产单权限范围逐一验证。
12. **查询与导出链：** 修改筛选不立即改清单；查询后生效；重置保留当前业务Tab；翻页和每页数量正确；耗时汇总表与来源明细表导出当前筛选全部记录而非当前页。

每条链必须在当前分支、同一工作树、同一运行服务上完成“创建／变更→列表结果→详情来源→刷新后仍存在→相邻角色读取”的闭环。涉及物理交接时还必须覆盖PDA扫码；涉及款式／物料时覆盖缩略图、失败态和大图；涉及打印时覆盖实际打印预览与二维码内容。

## 22. 实施顺序和依赖

推荐严格按以下依赖推进：

1. WP0先冻结当前事实、需求编号和删除边界；
2. WP1只先搭好目标菜单／路由／列表骨架，不提前填假数据；
3. WP2先统一任务对象、PPIC责任、可分配门禁和价格，形成下游共同主键；
4. WP3在执行任务稳定后扩展打印和扫码交接；
5. WP4以真实交出事实重算欠片、参考查看、补料和退仓；
6. WP5独立完成样衣／批版闭环，但使用同一执行任务和角色事实；
7. WP6基于后道最终确认收口回货与SLA；
8. WP7最后组合工作台汇总，避免再次由卫星记录反推任务全集；
9. WP8在上游和PPIC节点事实稳定后汇总十节点；
10. WP9执行两遍追踪、命名页面、PDA、打印、图片、治理和任务收据验证。

不得颠倒成“先把工作台和耗时宽表画出来，再补底层事实”。否则页面看似完整，刷新、跨页面、分批、作废替换和多任务聚合时仍会失真。

## 25. 最终调整结论

车缝外发协同的正确迭代方向，是保留当前原型已经形成的FCS外壳、八个业务页面、统一任务分配、裁片放行、配料、打印、PDA交接、批版、退仓和后道确认能力，把错误的对象关系和自动模拟动作局部重写，再新增一个只读的“生成单全流程耗时”页面。

页面不会换一套视觉或技术体系：原路由能保留的保留，原列表能优化的优化，只有任务全集、可分配门禁、部位参考、自动接收、全任务回货、SLA和十节点聚合等与业务冲突的核心投影才干净重写。最终判断不是“页面做出来了”，而是三类任务从配齐／放行、人工派单、领料交接、样衣批版、欠补退料、后道回货、责任移交到生产单十节点耗时，都能在同一执行任务和共享事实源上被操作、回看、刷新和逐项解释。
