## 0. 文档目的与结论先行

### 0.1 本版首先纠正什么

本版必须同时撤销两类错误结论：

1. **本项目业务中不存在把已裁衣片送去做“印花”的裁片印花工序。** 裁片上的相似图案工艺是烫画、直喷。
2. **准备加工对象不等于只有面料。** 技术包 BOM 中的面料、纱线、花边及其他适用物料，都可能分别触发染色、印花等准备需求。用户已明确举例：纱线会染色，花边也会染色；“非面料 BOM 触发印染”本身不是错误。

按已经确认的 HiGood 业务词典：

| 业务名称 | 本项目中的操作对象 | 所属阶段 | 正确理解 |
|---|---|---|---|
| 染色 | 具体 BOM 原物料分支，例如面料、纱线、花边等适用物料 | 准备阶段 | 由该条 BOM 的染色需求触发；同款不同物料可分别需要或不需要染色 |
| 印花 | 裁剪或投入生产前的具体 BOM 原物料分支，不是已经按纸样裁出的衣片 | 准备阶段 | 由该条 BOM 的印花需求触发；不能把所有命中物料合并成一个“面料”对象，也不能退化为裁片印花 |
| 水溶 | 具体 BOM 原物料分支 | 准备阶段 | 是否需要由该条 BOM 的技术要求决定，不能仅凭“面料/辅料”大类一刀切 |
| 烫画 | 指定裁片/裁片部位，或指定成衣 BOM/SKU | 生产阶段 | 两种对象都真实存在：裁片烫画按纸样部位和菲票承接；成衣烫画按成衣 BOM 适用 SKU、件数承接。二者工艺名相同，但路线节点、投入来源、单位和交出去向不能混成一个 occurrence |
| 直喷 | 指定裁片/裁片部位，或指定成衣 BOM/SKU | 生产阶段 | 两种对象都真实存在：裁片直喷按纸样部位和菲票承接；成衣直喷按成衣 BOM 适用 SKU、件数承接。不能因为对象为裁片就改叫印花，也不能因为对象为成衣就跳过显式 BOM 绑定 |
| 花朵 | 指定裁片部位 | 生产阶段 | 当前业务是用该裁片部位做花朵；加工后仍沿该裁片分支交接，不建模成独立采购花饰辅件 |
| 布包扣 | 制作包布钮所需材料/半成品，产出布包扣辅件 | 生产阶段的辅件制作支线 | 不是把扣子安装到成衣；旧代码映射到“装扣子”属于待删除的错误兼容 |
| 压褶 / 打褶 | 各自适用的指定裁片部位 | 生产阶段 | 两者是不同工法、两个独立权威词条，不做同义归并 |
| 曲牙绣 | 指定裁片部位 | 生产阶段 | 只保留“曲牙绣”；旧“曲牙→车缝”映射不再具有业务效力 |

因此，本项目不能出现以下推理：

1. 不能因为行业中存在不同载体的印制技术，就把准备阶段的 `PRINT` 扩成“BOM 原物料或已裁衣片均可”；它可以属于不同 BOM 原物料分支，但不能落到本项目所说的已裁裁片。
2. 不能因为代码类型允许 `objectType = 裁片` 或 `isPiecePrinting = true`，就说系统“预留了合理的裁片印花能力”。在本业务中，这些字段是错误业务概念的残留面，不是待实现需求。
3. 不能把烫画或直喷固化为单一对象。用户已明确两者都存在裁片加工和成衣加工；当前字典把烫画固定为成衣、把直喷固定为裁片，而专项 operation 种子和回归检查又把两者都收口为成衣，属于代码内部口径冲突，不是业务只能二选一。
4. 不能把后道 QC 的瑕疵原因“印花”误认为后道存在印花工序；那只是对成衣外观问题的原因分类。

### 0.2 行业校验如何使用，为什么仍以本项目词典为准

行业资料通常按载体区分连续面料、裁片/成衣以及转印膜等不同印制方式。Kornit 官方将 direct-to-fabric 与 direct-to-garment 明确列为不同解决方案；Brother 的 DTG 说明明确以成衣装载到台板为加工对象；Mimaki 的 DTF 说明则明确先在转印膜成像、再热压转移到服装或织物。这些资料共同证明：**工艺名称不能脱离载体、工法和工序位置来建模。**参考：[Kornit Printing Solutions](https://www.kornit.com/for-brands/printing-solutions/)、[Brother DTG](https://brotherindustrialprinting.brother-usa.com/)、[Mimaki DTF workflow](https://india.mimaki.com/application/solution/dtftfx150-75.html)。

但外部行业分类不能覆盖企业自己的分工和命名。本项目已经确认“BOM 原物料的印花=准备加工；已裁衣片上的图案加工=烫画/直喷；成衣也可能做烫画/直喷”。这里的 BOM 原物料不只包含面料，也可能包含具有相应工艺需求的辅料；系统必须同时保留工艺、对象类型和具体来源身份，而不是追求一个看似通用、实际上让现场混淆的“大印花”模型。

CottonWorks 的成衣制造资料还把裁剪形成的衣片、辅料成包送入缝制作为清晰的对象转换来描述。这与本项目的面料主干一致，但一款衣服还可能同时存在“纱线准备 → 毛织”和“花边/其他辅料准备 → 后续实际使用节点”等独立分支，不能用单一“面料 → 裁片”主干覆盖。参考：[CottonWorks Garment Construction](https://cottonworks.com/learning-hub/garment-manufacturing/garment-construction/)。

### 0.3 本文采用的服装加工对象状态链

要避免再次按工序名称猜业务，必须先看每一步实际拿在手里的东西是什么：

| 对象状态 | 从哪里来 | 可以进入什么加工 | 不能被误写成什么 |
|---|---|---|---|
| 待准备 BOM 物料 | BOM 对应的原面料、纱线、花边或其他待处理物料 | 该条物料明确需要的水溶、染色、印花等准备加工；工艺集合和先后均由本款该物料分支决定 | 已裁裁片；也不能被统一改名成“面料” |
| 已准备面料 | 上一道准备加工实际交出的面料批次 | 该面料分支的下一道准备工序或裁剪 | 仅因颜色/花型变化就必须新建技术包物料身份 |
| 已准备纱线 | 上一道准备加工实际交出的纱线批次，例如已染纱线 | 该纱线分支的下一道准备工序或毛织 | 面料、普通裁片 |
| 已准备花边/其他辅料 | 上一道准备加工实际交出的花边或其他辅料批次 | 该辅料分支的下一道准备工序、仓储交接或实际装配/车缝使用节点 | 普通衣片主线上的裁片 |
| 已裁裁片 | 面料按纸样、部位、颜色、尺码裁成并以菲票识别 | 绣花、压褶、打揽、烫画、直喷等该裁片所需工艺；或直接待交车缝 | 印花面料、成衣 |
| 已加工裁片 | 特定裁片完成其一项或多项辅助/特种工艺后回到裁床待交出链 | 同一裁片的下一道工艺，或与其他裁片一起交车缝 | 新成衣 SKU；它仍是原裁片的加工状态 |
| 毛织横机片/毛织部位 | 部位毛织加工单由纱线产出 | 回裁床待交出仓，与其他裁片一起交车缝 | 整件成衣 |
| 捆条、盘扣、定长橡筋、花边等辅料半成品 | 各自转换型加工分支产出 | 在后续车缝或已确认的使用节点汇入 | 主衣片路线上的普通裁片 |
| 车缝成衣 | 车缝厂接收裁片、毛织片及必要辅料后形成 | 普通生产单回货到后道工厂；KOL 整单不走这条链 | 已经自动完成所有后道项目的成品 |
| 整件毛织成衣 | 纱线经整件毛织直接形成 | 普通生产单回货到后道工厂 | 需要再走普通裁剪或普通车缝的半成品 |
| 待烫画/直喷成衣 | 成衣 BOM 对应的成衣，或路线中已形成且明确要继续做图案加工的成衣 | 成衣烫画、成衣直喷 | 裁片；也不能与同名裁片工艺合并为一个任务项 |
| 已烫画/直喷成衣 | 成衣烫画/直喷加工单实际交出的成衣批次 | 本款路线中的后续成衣节点；普通生产单在已分配生产任务完成并实际回货时进入回货/后道，KOL 整单不因此进入普通后道 | 新物料 SKU；工艺改变的是加工状态，实际替换仍由生产执行层记录 |
| 后道回货成衣 | 普通生产单的车缝、整件毛织或合法成衣专项加工按批次交回 | 到货确认、唯一到货 QC、必要时动态后道处理、后续交接 | 为了套“加工前/加工后”而虚构两个成衣物料身份 |

这里要同时区分三件事：**对象类型**回答“面料、纱线、花边/其他辅料、裁片、毛织片还是成衣”；**对象身份**回答“哪条 BOM、哪张纸样、哪个部位/颜色/尺码/SKU”；**执行批次**回答“哪次接收、多少数量、哪次交出”。工艺路线必须保留具体 BOM 对象分支，但最多约束对象类别、适用工艺和分支拓扑，不能锁死生产单实际替换后的 SKU/批次；加工单和交接账才记录本次实际身份与数量。

本次核查不是只看“工序工艺字典”或“技术包工序工艺”页面，而是沿着以下完整链路逐项核查：

`工序工艺字典 → 技术包 BOM / 物料与纸样关系 → 技术包工艺路线 → 生产单技术包快照 → 生产任务 → 各类加工单 → 接收 / 加工 / 交出 → 成衣回货 → 后道到货质检 → 动态处理 / 后续交接`

核查后的核心结论如下。

1. **当前代码已经有“准备、生产、后道”三个阶段，但执行事实没有形成协调一致的两类模型。** 三阶段只在工序字典和技术包路线中统一；进入执行后，染色/印花/水溶、裁床、毛织、辅助/特种工艺、花边、车缝、后道分别使用不同的数据结构、状态、数量口径和交接逻辑。目标也不应把三阶段强塞进一套加工单，而应分别收口准备/生产加工转换与后道动态处理。
2. **工艺路线与执行承接不能分开，但也不能把同一组字段机械套给三个阶段。** 准备、生产阶段属于加工转换，可按“需求来源、实际投入、实际产出、任务明细、前置任务项、后置任务项”理解；后道是普通生产单成衣回货后的现场处理阶段，应该按“回货批次、本次三方任务范围、到货质检最终项目、动态处理明细、处理结果、后续去向”理解。后道前后通常仍是同一成衣，硬造“加工前成衣/加工后成衣”没有业务价值；KOL 整单不进入这条后道链。
3. **技术包当前已经能汇集两类主要工艺来源，但并不等于完整且唯一。** BOM 上每一条具体物料的印花、水溶、染色要求会自动形成准备阶段路线项；纸样、裁片部位、捆条行和部分成衣/辅料 BOM 关系会形成生产阶段工艺。裁剪、毛织、车缝、后道又存在字典、品类种子、人工路线、运行时任务和专项域的补充来源；采购投影花边单甚至完全不进入技术包路线。
4. **字典正式承认水溶、染色、印花三种准备工序，但当前路线和执行会按“工序码”压扁物料分支。** 自动路线每个工序码只保留一个节点并聚合所有命中 BOM；正式生产快照又分别把全部 `DYE`、全部 `PRINT` 路线项扁平汇总，要求被合并物料只有一个数量单位，并各生成至多一张加工单。于是纱线染色、花边染色、不同面料染色可能被错误合并或因单位不同直接报错，更无法保留它们各自的前后顺序。独立水溶、合并染色、工厂端印花和旧染印兼容记录又继续形成多条并行链。
5. **生产阶段至少包含五套执行模型。** 正式生成裁片单与旧裁片单并存；捆条、毛织、辅助/特种、花边各有独立加工单域；车缝主要仍是 `ProcessTask + 分配 + 配料/交出/袋/交接`，没有同构的独立车缝加工单；另有两类固定合并生产任务和 KOL 整单任务。
6. **辅助/特种工艺代码列出 13 种辅助工艺和 4 种特种工艺，共 17 种加工入口，捆条另归裁床；但烫画/直喷对象口径彼此冲突。** 字典最终值是“烫画=成衣、直喷=裁片”，operation 种子和现行专项检查又要求两者全部为成衣，部分测试中还人为构造双对象输入后断言裁片单不得生成。已确认业务恰恰要求两者都支持裁片与成衣，因此不能继续靠单一默认对象覆盖另一种合法路线。
7. **普通生产单的后道不是第三组预排加工转换，项目默认规则却并非完全自由。** 若三方只承接车缝，回货质检时系统固定勾选开扣眼、装扣子、烫包且不允许修改；若三方承接车缝＋烫包或裁剪＋车缝＋烫包，质检时默认不勾选任何后道项目，但允许现场手动调整。返厂/退回三方也由这张到货 QC 产生和确认。现行新后道全流程已实现默认值、可编辑性及 QC 返厂记录，但只覆盖有限 Mock；并且当最终项目为空时，代码仍自动创建复检单，和“本批无需我方处理则不复核、整单直接对接成衣仓”的确认规则冲突。KOL 样衣、KOL 小单走整单任务，明确不进入普通后道阶段。
8. **准备、生产阶段当前没有通用的“前置任务项”和“后置任务项”，而目标必须补齐。** 个别专项域能通过来源任务号、加工单号、菲票或仓库记录局部串联，但没有稳定、逐任务明细的加工承接。目标上，每个准备/生产加工单都要展示前置和后置任务项；底层以一条关系事实双向投影，不能让两边各自维护而产生冲突。前置实际有可交出数量后，本单即可确认接收并自动开工；同一对象允许多次交出、多次接收，不增加质量放行、齐套或复杂许可门禁。后道不套用这组字段，而使用回货批次、分配范围、质检项目和后续去向。
9. **“系统不能自动完成加工单/生产单”的业务口径没有完全落实，但必须把加工执行单、生产任务容器和配套单据分开。** 独立水溶加工单在收货一致或差异确认后自动进入 `DONE`，这是加工单被系统代替人工完成的直接冲突。辅助/特种工艺的源 `ProcessTask` 会在所有子加工单完结后自动完成，正式染色/印花足量收货会自动完成关联移动任务；这两类是任务/交接投影的状态耦合风险，是否也必须人工完结需按它们究竟代表“加工责任”还是“汇总/移动结果”分别判定，不能与加工单自动完成混为同一结论。后道任务总览、回货送货单等状态同理，不能误算成系统自动完成后道处理单。
10. **当前最大问题不是缺少画布，而是业务词典、物料分支、路线拓扑和执行事实同时割裂。** 即使立即把现有排序界面换成 LogicFlow，也只能把当前 `routeStepNo + routeLaneNo` 画得更直观；如果仍把同一工序码下的面料、纱线、花边等分支合并，并保留“裁片印花”、把烫画/直喷固化成单一对象、把装扣子主对象写成辅料、把布包扣误归装扣子或让旧“曲牙”与“曲牙绣”并存，画布只会把错误表达得更漂亮，不能补齐准备/生产的对象与数量承接，也不能形成后道唯一的回货判定事实链。

## 1. 核查口径

### 1.1 五种结论标签

本文用以下口径区分事实与目标：

- **【代码事实】**：当前分支代码能够直接证明的结构或行为。

### 1.3 本文所说的“加工单”

当前项目对“任务单、加工单、工单、裁片单、后道任务”的命名并不统一。为避免漏项，本文同时核查三类对象，但明确分类：

| 分类 | 定义 | 例子 |
|---|---|---|
| 真加工执行单/处理单 | 承载明确加工或处理对象、数量，并有接收、加工/处理、完工或交出动作 | 染色加工单、裁片单、毛织加工单、辅助工艺加工单；QC 有项目时生成的后道处理单 |
| 生产任务/分配容器 | 用于把一段责任分配给工厂；可能再生成一张或多张加工单 | 车缝任务、特殊工艺源任务、车缝+烫包合并任务 |
| 辅助或下游业务单据 | 支撑领料、仓储、质检、交接、复检、出货，但本身不是加工动作 | 铺布单、菲票、交接单、QC 单、复检单、出货单 |

本文“不遗漏任何一个加工单”是指不遗漏当前代码中任何独立加工单类型、来源变体、并存兼容模型和会被页面当作加工责任的任务类型；不按 Mock 种子逐条抄录单号。种子记录只用于说明页面场景，不是现实生产台账。

### 1.4 三个阶段必须使用两套业务分析框架

此前把所有阶段统一放进“加工前、需求来源、加工后、任务明细”四项关系，适合用来检查代码字段有没有缺失，却不适合作为最终业务模型。重新校正后，本文使用以下两套框架。

#### 框架 A：准备、生产阶段的加工转换

| 字段 | 本文定义 | 不能混淆成什么 |
|---|---|---|
| 需求来源 | 为什么需要生成这张加工单，例如生产单、备货、补料或采购需求 | 不是本次实际收到的实物 |
| 前置任务项 | 哪一张上游加工单的哪条任务明细会把产出交给本任务明细；首节点可以为空，并明确由仓库/采购等非加工来源直接供料 | 不是“上一工序名称”，也不是整张生产单的粗依赖 |
| 实际投入 | 本单真正接收并准备加工的对象、批次、数量和单位 | 不能只写上一道工序名称或技术包物料 |
| 实际产出 | 本单实际完成并可交出的对象、批次、数量和单位 | 不能只写计划目标或下一张任务 |
| 任务明细 | 本单内部可追溯的物料、纸样、部位、颜色、尺码、SKU 或执行行 | 不能等同于路线节点，也不能只保存汇总数量 |
| 后置任务项 | 本任务明细的产出将由哪一张下游加工单的哪条任务明细承接；末节点可以为空并明确最终仓库/回货去向 | 不是人工重复维护的第二条关系，也不是产出对象本身 |

【业务已确认】页面上要同时看见“前置任务项”和“后置任务项”，但数据上只保存一条有方向的承接关系：`前置任务明细 → 后置任务明细`。当前任务的前置列表和后置列表都从这条关系反向/正向计算，避免 A 说后置是 B、B 却说前置是 C。路线快照负责生成计划关系，实际交出/接收记录负责累计本次真实数量；二者不能互相替代。

在引用当前页面原文或现有字段时，本文仍可能使用“加工前/加工后”；其业务含义分别等同于“实际投入/实际产出”。

#### 框架 B：后道阶段的回货判定与动态处理

| 字段 | 本文定义 | 不能混淆成什么 |
|---|---|---|
| 回货批次 | 哪个生产单、哪家工厂、第几次回货、哪些成衣 SKU、各多少件 | 不是后道加工投入 SKU |
| 回货登记与实收 | 当前采用“三方车缝工厂自助回货登记 → 后道人员另行确认实收”；未来若采用扫码回货登记，扫码登记本身即可完成实收 | 不能把当前不存在的扫码即实收写成已实现，也不能在自助登记后省掉确认实收 |
| 本次三方任务范围 | 本次任务分配是仅车缝、车缝＋烫包，还是裁剪＋车缝＋烫包 | 不是技术包静态后道路由；它直接决定 QC 项目默认值和是否允许修改 |
| 到货质检判定 | 回货现场记录成衣质量，并按本次三方任务范围应用后道项目规则：仅车缝固定勾选且不可改；含烫包默认不勾选但可调整；需要返厂/退回三方的数量、原因和接收工厂也在此产生并确认 | 不是普通加工单完工质检，也不是让质检员忽略任务范围从空白自由设计路线；后道处理完成时不得再新建一轮返厂判断 |
| 动态处理明细 | 单头冻结本批需要我方执行的开扣眼、装扣子、烫包等项目集合；明细按 `SKU × 数量` 记录 | 不拆成 `SKU × 项目 × 数量`，也不能由技术包款式默认节点锁死；多个项目的执行先后属于 QC/后道处理内部安排，不进入技术包工艺路线 |
| 处理结果 | 各项目人工确认已处理数量、剩余数量、操作人和时间 | 不再重复录入一轮合格/瑕疵/返厂质量结论 |
| 后续去向 | 处理完成后进入待交出、成品仓或已确认的下一节点 | 不是虚构一个“加工后成衣”新身份 |

因此，普通生产单存在后道回货阶段，但后道处理单不一定存在：最终项目为空时不再生成复检或扫码点数节点，而是按整单形成对接成衣仓的数量交接；项目非空时才形成一张处理单，单头保存项目集合、明细保存 `SKU × 数量`。KOL 样衣、KOL 小单的整单任务是明确例外，不进入普通后道阶段。

## 2. 当前代码里的阶段、路线、任务和加工单关系

### 2.1 阶段定义并不只有一套

【代码事实】工序工艺字典定义了三阶段：

| 阶段 | 字典说明 | 主要对象 |
|---|---|---|
| `PREP` 准备阶段 | 印花、水溶、染色等产前处理 | 业务上是具体 BOM 原物料分支，可包括面料、纱线、花边等适用物料；当前代码却只在“面料”与宽泛 `BOM_MATERIAL` 之间二选一 |
| `PROD` 生产阶段 | 裁片、绣花、压褶、毛织、车缝、特殊工艺 | 布料、裁片、纱线、辅料、半成衣 |
| `POST` 后道阶段 | 成衣到货确认后执行开扣眼、装扣子、烫包；质检/复检不属于工序字典 | 成衣 |

依据：`src/data/fcs/process-craft-dict.ts:853-872`。

【业务已确认】三阶段在业务性质上并不对称：准备、生产阶段按款式路线组织加工转换；普通生产单的后道是成衣回货处理阶段，KOL 样衣/KOL 小单整单任务不进入该阶段。普通生产单是否产生后道处理单，由回货质检时最终项目是否为空决定；项目的默认值和可编辑性取决于本次三方任务范围，而不是完全由质检员从空白自由判断。因此“进入后道”不等于“预先生成三个技术包路线节点”，也不等于“每个款都有一张后道加工单”。准备阶段的操作对象是**尚未进入对应生产转换的具体 BOM 原物料**，不只面料：纱线、花边等辅料也可能有染色或印花要求。是否需要某项准备工艺，以该条 BOM 的显式技术要求为准，而不是按“面料/辅料”大类预判。当前 `BOM_MATERIAL` 的方向比强制 `FABRIC` 更接近业务，但仍然过于宽泛，因为它没有保留面料、纱线、花边等实际类别和具体 BOM 分支。

但是兼容任务类型仍使用七段枚举：`PREP / CUTTING / SEWING / POST / SPECIAL / MATERIAL / WAREHOUSE`，并通过映射把三阶段字典压到旧阶段中，见 `src/data/fcs/process-types.ts:15-70`。因此页面筛选、任务 stage 和技术包 stage 不是同一个枚举体系。

### 2.2 字典已经删除跨款式默认顺序，但仍保存默认拆分规则

【代码事实】当前字典没有“水溶→染色→印花→……”这类跨款式固定序列。活跃字典行只按：

1. 阶段顺序；
2. 工序中文名；
3. 工艺中文名；

进行结果展示，见 `src/data/fcs/process-craft-dict.ts:1839-1856`。

但字典仍给每种工序写有默认分配粒度和明细拆分维度：

| 工序 | 默认分配粒度 | 默认明细维度 |
|---|---|---|
| 印花 | 颜色 | 花型 + 物料 SKU |
| 水溶 | 生产单 | 物料 SKU |
| 染色 | 颜色 | 成衣颜色 + 物料 SKU |
| 裁片 | 生产单 | 成衣颜色 + 纸样 + 物料 SKU |
| 绣花、压褶、特殊工艺 | 生产单 | 纸样 + 物料 SKU |
| 毛织、车缝 | SKU | 成衣 SKU |
| 开扣眼、装扣子 | SKU | 成衣 SKU |
| 烫包 | 生产单 | 成衣 SKU |

依据：`src/data/fcs/process-craft-dict.ts:776-837`、`1068-1102`。

【核查判断】默认顺序已删除，不代表字典已经完全变成“纯定义字典”。这些默认粒度仍会影响任务明细和任务分配语义，而且部分规则与后续专项加工单的实际粒度不同。

【清理核查】本轮明确要求彻底移除的两条停用历史工序，已不再出现在当前源码、页面文案、脚本或项目文档中；对其两个中文名称做全项目精确检索结果为 0。仓库仍有 `ONLINE_WASHING_STANDARD`，其值是成衣 SKU 标签上的执行标准 `GB/T 2660 2017`，属于成衣标签标准字段，不是生产工序、任务或加工单，不能因为英文名称相似而误删。

还要区分“全局默认顺序已删除”和“局部硬编码先后仍存在”：

- BOM 自动追加准备节点时，代码顺序仍固定为“水溶、染色、印花”；
- 同一 BOM 的水溶被强制早于染色，移动、并行或确认路线时会校验；
- 同一 BOM 的染色又被强制早于印花；补料路径还单独注册染色为印花前置。

依据：`src/pages/tech-pack/bom-process-linkage.ts:87-104`、`src/data/tech-pack-process-route.ts:70-126`、`src/pages/tech-pack/events.ts:523-645`。因此“两款都需要染色和印花，但顺序可以不同”尚未完整实现：当前没有全款式固定序列，却仍有强制的同 BOM 局部序列。

### 2.3 技术包当前实际是“受控列表排序”，不是图模型

【代码事实】技术包每条 `TechnicalProcessEntry` 保存：

- 工序、工艺、阶段；
- 默认单据类型和分配粒度；
- 作用对象；
- 关联 BOM 行、纸样；
- `routeStepNo`、`routeLaneNo`、并行组 ID/名称；
- 路线来源、维护人和维护时间。

见 `src/data/pcs-technical-data-version-types.ts:354-403`。

当前界面能力是：

- 上移、下移；
- 与上一步并行、与下一步并行、移出并行；
- 按步骤卡片展示；
- 批量表格查看步骤；
- 查看该路线项关联的 BOM、纸样或作用对象；
- 人工确认路线。

见 `src/pages/tech-pack/process-domain.ts:34-85`、`254-417`，动作写回见 `src/pages/tech-pack/events.ts:4400-4429`。

当前页面标题仍是“工序工艺”，按钮是“确认工艺路线”；尚未改名为“工艺路线”。`package.json` 也没有安装 LogicFlow。换言之，我们已经讨论并确认“使用 LogicFlow 的受控工艺路线编排器”，但当前代码尚未实现。

当前“来源关系查看”还有一处直接语义错误：只要路线项带 `targetObjectName`，且 `selectedTargetObject` 不是“成衣”，页面就把来源写成“裁片部位工艺”。因此，目标对象为面料、纱线、花边等 BOM 原物料的印花/染色路线，都可能被这一通用分支标成“裁片部位工艺”。依据：`src/pages/tech-pack/process-domain.ts:296-327`。这不是显示小问题，而是会把准备阶段物料工艺误导成生产阶段裁片工艺，必须在后续路线页面中按真实 BOM 物料来源分别显示。

### 2.4 当前路线能表达什么、不能表达什么

| 能表达 | 不能表达 |
|---|---|
| 一条路线项排在第几步 | 节点 A 的哪条产出明细进入节点 B 的哪条投入明细 |
| 同一步有几条并行工艺 | 汇合是等待全部对象还是按交出批次滚动承接 |
| 路线项来自 BOM、纸样、部位工艺或人工 | 某次实际接收、某次实际交出的批次和数量 |
| 节点的抽象作用对象 | 生产单发生原料替换后的实际投入对象 |
| BOM/纸样关联 ID | 稳定的逻辑物料槽位或半成品身份 |

任务依赖的生成也只是“本步骤所有任务依赖紧邻上一步的所有任务”，见 `src/data/fcs/process-tasks.ts:332-381`。它是步骤级全连接，并不是对象级承接：

- 两个并行裁片分支会被后一步整批依赖；
- 无法表示后一步只消费其中一个裁片部位；
- 准备加工单没有进入同一个任务列表，因此生产任务依赖图不能真正依赖某张染色/印花加工单的交出；
- 没有前置加工单明细 ID 和后置加工单明细 ID。

这些“对象级前后置承接”问题主要属于准备、生产阶段。目标不仅要有任务头级 `dependsOnTaskIds`，还要在任务明细级形成通用的“前置任务项/后置任务项”，并用实际交出与接收流水记录可承接数量。技术包路线进入普通成衣回货之后，只表示切换到后道规则；本次分配给三方的任务范围由任务分配承载，本批项目在 QC 时依任务范围应用“固定勾选不可改”或“默认不勾选可调整”。KOL 整单在此处直接走自身交付闭环，不进入普通后道。

还必须增加一个对抗性约束：路线节点的“对象类型”不能靠工序大类兜底推断。准备阶段的 `PRINT/DYE/WATER_SOLUBLE` 必须继承其来源 BOM 的实际物料类别与分支，不能一律写成面料，也不能落成已裁裁片；烫画、直喷都必须在每个路线 occurrence 上明确选择“裁片部位”或“成衣”，前者绑定纸样部位，后者绑定成衣 BOM 及适用 SKU；装扣子处理的是成衣并消耗扣子辅料，不能只因 BOM 来源是扣子就把工序对象写成“辅料”。如果一个节点同时有主加工对象和消耗物料，应分别表达“主加工对象”和“消耗物料类型”，不能只保留一个模糊 `targetObject`。

当前 `targetObject` 实际还承担了互不相同的含义：`PRINT/DYE` 用它描述加工投入载体，却没有保存来自哪一种 BOM 物料类别；`CUT_PANEL` 的“裁片部位”更接近裁剪产出；`WOOL` 用它描述毛织产出；`BUTTON_ATTACH` 又错误地用它描述被消耗的扣子辅料。一个字段有时表示投入、有时表示产出、有时表示消耗品，不能成为路线连线的可靠依据。【分析建议】路线节点应在**类型级**分别说明 `inputObjectType`、`outputObjectType`，需要消耗辅料时另列 `consumedMaterialType`，同时以 `sourceBomItemId/routeBranchId` 保留来源物料分支；这里不绑定实际 SKU、批次或数量，仍符合技术包不锁死生产单换料的边界。

### 2.5 两条“从技术包生成执行事实”的并行主线

当前至少有两条生成主线。

#### 主线 A：通用生产产物/任务

`generateProductionArtifactsForOrder()` 读取生产单绑定的技术包快照路线：

- `PREP` 路线项转成 `PREPARATION_ORDER` 产物；
- 非 `PREP` 且允许外部任务的路线项转成 `TASK` 产物；
- 再由 `process-tasks.ts` 转成运行时生产任务。

见 `src/data/fcs/production-artifact-generation.ts:783-815`、`src/data/fcs/process-tasks.ts:785-880`。

这条主线中的 `PREPARATION_ORDER` 多数只是通用产物对象，不等于染色/印花专项页面中的真加工单。生产任务统一把任务头数量写成生产单成衣数量、单位 `PIECE`、标准价单位“件”，虽然明细行可能使用其他单位，见 `src/data/fcs/process-tasks.ts:817-855`。

#### 主线 B：各专项加工单域

准备、裁床、毛织、辅助/特种工艺、花边、后道又分别有自己的生成器和状态存储。它们会引用生产单、技术包快照或源任务，但并不统一消费主线 A 的产物。

【核查判断】当前“同一工艺”经常同时存在三层身份：

1. 技术包路线项；
2. 生产任务或通用产物；
3. 专项加工单。

三者不是稳定的一对一关系，也没有统一主键贯穿到底。

### 2.6 “这个款需要哪些工序”不能只用一条来源规则回答

此前讨论中的“本款全部工序是否都来自技术包 BOM 和物料与纸样关系”，只能回答一部分。对抗性复核后，必须把**显式工艺要求、由产品结构必然派生的核心节点、生产责任分配，以及回货后现场判断**分开：

| 工序/阶段事实 | 业务上的权威来源 | 当前代码实际来源 | 对抗性结论 |
|---|---|---|---|
| BOM 原物料的水溶、染色、印花需求 | 技术包 BOM 对该条**具体物料**的显式加工要求；面料、纱线、花边等都可能存在，每条物料的工艺集合可以不同 | 三个触发字段位于通用 `TechnicalBomItem`；BOM 页面只排除“成衣”；联动 DTO 不带物料类型，随后把 `PRINT/DYE` 强制标成面料、把水溶标成宽泛 BOM 物料 | 允许非面料配置本身不是错误，通用字段也不能据此判为错误。真正缺口是路线丢失来源物料类别和分支：合法的纱线染色、花边染色会被误标或混并 |
| 各 BOM 物料准备工序的集合与先后 | 本款、该 BOM 物料分支经工艺师确认的路线 | BOM 联动按水溶、染色、印花顺序追加，路线归一化又强制共享 BOM 水溶早于染色、染色早于印花；每个工序码只生成一个固定 ID 自动节点，并把所有命中 BOM 合并到该节点 | 不仅两款不能有不同顺序；同一款内 A 面料可“染→印”、B 面料可仅染色、C 纱线可染色、D 花边也可有自己的准备工序。同名工序必须允许按 BOM 物料分支出现多个有稳定身份的路线节点 |
| 裁剪 | 只要是需要按纸样形成衣片的布料就派生裁剪；纯整件毛织款的成衣主干例外，部位毛织或混合款的毛织分支不等于整款免裁 | 当前裁片单是否生成，仍依赖任务摘要名称中能否识别“裁片/裁剪/裁床”，再结合颜色物料映射和纸样 | 裁剪不是 BOM 上再勾一个“工艺”才存在，也不应靠任务中文名猜；它是由材料形态和产品结构派生的核心转换 |
| 裁片辅助/特种工艺 | 技术包“物料与纸样关系”中，具体纸样部位绑定的工艺 | 专项生成器读取纸样部位工艺，同时还扫描部分成衣/辅料 BOM 和路线项 | 裁片来源大方向成立；烫画、直喷必须保留裁片对象变体，不能被成衣默认覆盖。“花朵”已确认是用指定裁片部位制作，当前裁片对象方向成立 |
| 成衣烫画/直喷 | 技术包 BOM 中的成衣物料行及其适用 SKU；该行只允许选择烫画、直喷 | 当前 BOM 选择成衣后会清空并隐藏印花、水溶、染色，却继续显示裁片/印花/染色/车缝/烫包等通用“使用工序”；成衣烫画主要靠另一个工艺编辑器关联成衣 BOM。字典、operation 种子和测试又对烫画/直喷对象给出互相冲突的单一默认 | 当前 BOM 入口不符合目标。应在成衣 BOM 行直接只呈现烫画、直喷；所选项各生成绑定该成衣 BOM 的生产阶段 route occurrence，与纸样部位来源的同名工艺分开 |
| 捆条 | 纸样捆条配置、来源面料和捆条规格 | 从满足条件的裁片单和纸样捆条行生成独立捆条单，另有旧捆条事实源 | 属于由纸样结构派生的辅料转换支线，不应当作普通裁片同对象工艺 |
| 整件/部位毛织 | 技术包纸样类别、毛织资料及款式结构 | 毛织路线项和纸样类别共同生成毛织任务/加工单 | 纯整件毛织款主干派生“纱线→成衣”并跳过普通裁剪/车缝；同款若还有需裁面料或拼接部件，其分支仍要裁剪/车缝。部位毛织派生“纱线→毛织片”，仍需与其他裁片汇入车缝 |
| 车缝 | 款式结构在具备待缝部件时必然需要的核心成衣形成节点；纯整件毛织款主干例外 | 当前主要由技术包/种子路线生成 `ProcessTask`，再由任务分配和裁片交接域共同执行 | 车缝不是纸样上每个裁片各自绑定的一道辅助工艺。本项目没有独立 `ASSEMBLY/组装` 节点；若“组装”只是衣片/部件缝合成衣的口语，应归入车缝，只有未来确认独立装配工位时才另建节点。当前没有统一车缝加工单 |
| 盘扣、定长橡筋、花边等转换型辅料 | BOM/纸样配置、采购事实及实际使用关系的组合 | 盘扣来自捆条专项链，橡筋进入通用特种工艺，花边由 PMS 采购投影生成且不进入技术包路线 | 不能强称它们全都来自 BOM 或物料与纸样关系，也不能全部压到衣片主线；它们是并行支线，必须在真实消费节点汇合 |
| 后道阶段适用范围 | 普通生产单形成成衣后进入回货处理；KOL 样衣、KOL 小单整单任务不进入普通后道 | 字典、静态后道路由、新旧后道模型能表达后道，但新全流程只使用三张独立 Mock，未从生产单任务边界统一派生，也未显式排除 KOL | 不能再写成“所有成衣生产单必经”；应由生产单任务类型明确决定是否适用普通后道 |
| 本批后道具体处理项目 | 本次三方任务范围先决定默认项目和是否可改：仅车缝固定三项且不可改；车缝＋烫包、裁剪＋车缝＋烫包默认空且可调整；QC 提交时冻结最终项目 | 新全流程 `resolvePostFinishingResponsibility()` 与 `completePostFinishingQcTask()` 已实现；旧域逐 SKU 规则、静态路线默认项目仍并行 | 新规则本身是最新口径，不是错误“提前决定”；缺口是它没有成为所有普通生产单唯一事实，并仍受旧模型干扰 |
| 采购/备货/补料来源加工 | 对应采购需求、库存待加工事实或原裁片单补料事实 | 正式染色/印花支持备货和补料；工厂端另一套印花含采购 Mock；花边有真实采购投影；水溶和辅助/特种没有同等通用来源能力 | “来源”是为何产生本次需求，不等于技术包节点，也不等于上一步实际交出的投入；当前各专项域覆盖不一致 |

因此，目标上的完整答案不是“全部来自 BOM 和物料与纸样关系”，而是：

1. BOM 和物料与纸样关系提供本款的**显式加工要求**；
2. 裁剪、毛织形态、车缝和普通生产单后道适用性还要由**产品结构、任务类型与生命周期规则派生**；KOL 整单明确绕过普通后道；
3. 采购、备货、补料提供某次执行需求的**业务来源**；
4. 生产责任分配决定“本次由谁做”，不能反过来改写款式本来需要什么；
5. 后道最终项目在**本批回货 QC**提交时冻结，但默认值和可编辑性必须先服从本次三方任务范围，不能在技术包中固定，也不能让 QC 无规则自由改写仅车缝任务。

代码证据：`src/data/pcs-technical-data-version-types.ts:415-442`，`src/pages/tech-pack/bom-domain.ts:270-304`、`419-423`、`545-584`，`src/pages/tech-pack/bom-process-linkage.ts:16-21`、`87-104`、`175-234`、`264-324`。这些区段共同证明 BOM 触发 DTO 缺物料类型，且自动节点按 `processCode` 聚合而不是按 BOM 分支生成独立 occurrence。

### 2.7 成衣 BOM 的烫画、直喷入口当前确实缺失

【代码事实】当前技术包虽然已经有“成衣”BOM 类型，但它没有按业务要求提供成衣工序工艺选择：

1. `normalizeGarmentBomItem()` 会把成衣 BOM 的印花、水溶、染色全部清空，并固定名称、单位用量、单位和损耗率；这部分用于排除准备阶段印染，方向成立。
2. BOM 列表对成衣行直接隐藏印花、水溶、染色编辑，方向同样成立。
3. 但新增/编辑 BOM 的“使用工序”仍对所有物料类型统一展示裁片、印花、染色、车缝、烫包五项；成衣并没有专属“烫画、直喷”选项，也没有只允许这两项的校验。
4. 现有成衣烫画能力来自另一个“工序工艺”编辑器：先选择成衣作用对象，再关联成衣 BOM。它不是从成衣 BOM 行直接产生，而且直喷能否选择成衣还受到字典与 operation 冲突影响。
5. `TechnicalBomItem` 目前只有 `usageProcessCodes` 和准备印染字段，没有一组能明确保存“此成衣 BOM 选择了烫画/直喷”的专属字段或受约束工艺引用。

直接证据：`src/pages/tech-pack/context.ts:227-275`、`834-857`、`889-895`，`src/pages/tech-pack/bom-domain.ts:270-304`、`393-586`，`src/pages/tech-pack/events.ts:2401-2432`、`2662-2711`、`4039-4165`，`src/data/pcs-technical-data-version-types.ts:415-442`。

【业务已确认】目标行为应明确为：

- 当 BOM 物料类型不是成衣时，继续按该物料自身规则维护准备需求和使用关系；不能把烫画/直喷当作通用准备“印花”。
- 当 BOM 物料类型是成衣时，“工序工艺”只允许选择**烫画、直喷**，不展示裁剪、准备印花、染色、车缝、烫包等无关选项。
- 成衣 BOM 可以只选烫画、只选直喷、两者都选；若两者都选，其先后仍由本款该成衣 BOM 分支的工艺路线决定，不写死全局顺序。
- 每个选择都生成独立的生产阶段 route occurrence，并自动绑定该成衣 BOM 及适用 SKU；它与纸样部位上同名的裁片 occurrence 是不同节点。
- 字典层把烫画、直喷的“支持对象”都改为裁片、成衣；路线节点必须保存本次明确选择的对象，不能用一个默认对象覆盖全部场景。
- 技术包只约束对象类型和来源分支，不锁死生产单执行时的实际替换物料 SKU、批次和数量。

【结构建议】不要继续复用语义含混的 `usageProcessCodes` 存这两项。应保存受字典约束的工艺引用，例如“工艺代码 + 作用对象=成衣 + 来源 BOM 行 ID”；页面可仍只显示两个简单复选项。这样技术包路线、生产单快照和加工单生成都读取同一事实，不需要再由另一个编辑器人工重复关联。字段名仍可在实施设计中确定，但唯一性至少应是：`技术包版本 + 成衣 BOM 行 + 工艺代码 + 作用对象 + route occurrence`。

## 4. 准备阶段：全部加工单现状

### 4.1 准备阶段共同来源与通用模型

【代码事实】BOM 的三个触发字段直接决定技术包准备阶段路线项：

| BOM 字段 | 路线工序 | 抽象作用对象 |
|---|---|---|
| `printRequirement` 非“无” | 印花 | 面料 |
| `waterSolubleRequirement = 是` | 水溶 | BOM 物料 |
| `dyeRequirement` 非“无” | 染色 | 面料 |

同步函数会自动新增、更新或移除准备路线项，并写入关联 BOM 行 ID；有人工内容时不直接删除，而标记待确认。见 `src/pages/tech-pack/bom-process-linkage.ts:87-104`、`121-170`、`259-331`。

上表是**当前代码的生成标签**，不是正确业务对象表。`TechnicalBomItem` 把三类字段放在面料、纱线、辅料、包装材料、成衣、其他所有类型上；BOM 表格和编辑弹窗只对“成衣”隐藏/禁用，其他非成衣类型都可选择。这个入口宽度不能直接判为错误，因为纱线染色、花边染色，以及其他经确认的辅料印染都是真实需求。

真正的代码缺陷有三层：

1. 传给同步器的 `BomProcessLinkageBomRow` 不包含 `type`，路线节点无法保留和展示来源物料究竟是面料、纱线、花边还是其他辅料；
2. `getBomDrivenProcessMeta()` 又把 `PRINT`、`DYE` 强制标成 `FABRIC/面料`，把所有合法非面料加工对象改错；水溶虽然标成 `BOM_MATERIAL`，仍丢失具体物料类别；
3. 页面允许每条非成衣 BOM 显式选择这些需求，这一点本身与已确认业务并不冲突；不能再把它列作缺陷，也不能用物料大类白名单替代 BOM 技术要求。后续若需要防误选，只能是可维护的提示或校验，并以已确认企业工艺规则为依据。

所以 P0 不是“限制为合法面料”或新建一张未经确认的物料白名单，而是“以每条 BOM 的显式需求为事实，保留实际物料类别和独立路线分支”。依据：`src/data/pcs-technical-data-version-types.ts:415-442`、`src/pages/tech-pack/bom-domain.ts:270-304`、`419-423`、`545-584`、`src/pages/tech-pack/bom-process-linkage.ts:16-21`、`87-104`。

字典里的三项共同配置为：`stageCode = PREP`、`processRole = PREPARATION_ORDER`、默认单据“加工单”、需要任务二维码和交接单、工厂移动端整单执行、`generatesExternalTask = false`。通用生产任务生成逻辑还会按 `PREP` 阶段排除这些节点；字典标志与这一结果一致，但不能单凭该标志推导执行模型。当前真正的执行单分别由染色、印花、水溶专项域生成。

统一展示层 `ProcessWorkOrder` 只覆盖三类：`PRINT / DYE / WATER_SOLUBLE`；其类型契约允许以下来源：

- `PRODUCTION_ORDER`：生产单自动生成；
- `STOCK`：备货手动创建；
- `CUT_PIECE_SUPPLEMENT`：裁片补料生成。

见 `src/data/fcs/process-work-order-domain.ts:42-66`。

这三个枚举不是三类加工单共同具备的来源能力：独立水溶当前只映射生产单来源；正式染色/印花实际覆盖生产单、备货和裁片补料；另一套工厂端印花模型另有生产、采购、备货和补料四类来源，但不属于同一正式事实源。

但是三类加工单并没有真正共享同一生成和执行模型：

- 水溶由独立水溶域映射进统一展示；
- 染色和印花各自有专项域，再被映射进统一展示；
- 正式生产单统一生成注册表只支持 `DYE / PRINT`，不支持 `WATER_SOLUBLE`，见 `src/data/fcs/process-work-order-generation-registry.ts:11-38`；
- 正式生产快照派生也只查染色和印花路线项，见 `src/data/fcs/production-process-snapshot-derivation.ts:30-103`。

通用 `task-detail-rows.ts` 只为 `GeneratedTaskArtifact` 生成任务明细；准备阶段路线被转成 `GeneratedPreparationOrderArtifact` 并排除在普通生产任务之外。因此字典里写的“按颜色/花型/物料 SKU 拆明细”并没有自动变成三类正式准备加工单的统一明细表。

### 4.2 水溶加工单（PREP-007）

#### 4.2.1 生成条件和粒度

【代码事实】只有 BOM 行“需要水溶、但不需要染色”时，通用生产产物链才按 BOM 行生成独立水溶加工单产物；同一 BOM 同时需要水溶和染色时，不生成独立水溶单，水溶被染色加工单吸收。见 `src/data/fcs/production-artifact-generation.ts:695-755`。

当前独立水溶是一条 BOM 行一张加工单，来源只映射为生产单，尚无备货来源或裁片补料来源。统一视图会保存：生产单、技术包版本、BOM 行、物料、计划数量/单位、任务码、交接单和操作日志，见 `src/data/fcs/process-work-order-domain.ts:247-305`。

#### 4.2.2 需求来源、实际投入、实际产出、明细与去向

| 项目 | 当前代码现状 |
|---|---|
| 加工前 | BOM 物料；页面/模型没有统一批次级前置加工单明细 |
| 需求来源 | 生产单 + 技术包版本 + 单个 BOM 行 + 水溶要求 |
| 加工后 | 仍以相同 BOM 物料和相同数量单位记录完成数量；没有统一的实际产出批次/加工状态。这里不要求另建“水溶后 SKU” |
| 任务明细 | 基本是加工单头上的一条 BOM 物料事实，没有通用 `demandLines` |
| 加工后去向 | 技术包路线中可能还有后续步骤，但水溶执行单既不保存也不推进后继路线节点；“完成后继续下一节点”目前只是目标规则 |

#### 4.2.3 关键现状

- 独立水溶和“水溶+染色”不是两张连续加工单。
- 技术包路线仍会同时有水溶节点和染色节点，并强制同 BOM 水溶在染色之前；执行层却用一张染色加工单承载连续加工。
- 水溶没有进入正式染色/印花统一生成事务，因此正式生产单页面调用统一生成服务时不能仅凭该服务证明水溶单已生成。
- 水溶 PDA 仍有独立接单/拒单；接单与“原料接收”不是同一个动作，也没有实现“上游交出后自动接收并开工”。
- 状态链为“待分配 → 待原料 → 待水溶 → 水溶中 →（数量不足时生产暂停）→ 待交出 → 交出待收货/收货差异 → 已完成”。
- 当前代码明确禁止部分交出，提示“本期不支持部分交出”；收货一致或差异被主管确认后会自动进入 `DONE`。这同时违背“可多次交出/接收”和“单据必须人工完成”两项已确认口径。
- 水溶生成键只有 `productionOrderId::bomItemId`，不含技术包版本、路线步骤或路线节点；同一生产单同一 BOM 在版本变化或路线重排后仍会命中原执行身份。
- 通用移动任务的标准单位枚举会把“米”和“码”都映射成 `METER`；原水溶单及 `qtyDisplayUnit/sourceQtyUnit` 仍保留原单位，但只读标准枚举的下游会混淆米和码。

依据：`src/data/fcs/water-soluble-task-domain.ts:14-72`、`384-408`、`476-731`，PDA 交出区段见 `src/data/fcs/pda-handover-events.ts:4230-4540`。

### 4.3 染色加工单

#### 4.3.1 生产单来源染色单（PREP-004）

生产单创建后，正式服务从该单冻结的技术包快照查找 `DYE` 路线项，再汇总其关联 BOM。幂等键是：

`PRODUCTION_ORDER + DYE + 生产单 ID + 技术包版本 ID + 排序后的 BOM 行 ID 集合`

同一生产单的关联染色 BOM 会聚合成一张加工单；所有 BOM 单位必须相同，水溶属性混合会阻断生成。这里不会区分“面料 A 染色”“纱线 B 染色”“花边 C 染色”各自是哪一个路线 occurrence，也不会保留它们各自的后续去向。实际粒度既不是字典写的“按颜色分配、按成衣颜色+物料 SKU 拆明细”，也不是业务所需的“先按 BOM 物料分支形成路线节点，再按执行条件决定是否合批”。

生成键和执行快照都不保存技术包路线节点 ID、步骤号或并行组。`FormalProductionOrderMaterialItem` 也只保存 `sourceBomItemId/materialId/materialName`，不保存 BOM 物料类别或路线分支。若同一工序以相同 BOM 集合出现在不同路线位置，执行层无法区分“第几次染色”，也不能从加工单反查真实前后路线节点；即使保存了多个 `materialItems`，也只证明一张单聚合了哪些物料，不能还原各物料各自的顺序。

依据：`src/data/fcs/production-process-snapshot-derivation.ts:16-103`、`src/data/fcs/process-work-order-domain.ts:68-97`、`src/data/fcs/process-work-order-generation-key.ts:40-104`、`src/data/fcs/production-process-work-order-service.ts:50-171`。

#### 4.3.2 备货来源染色单（PREP-005）

平台在染色列表人工执行“按备货创建”，只能选择当前染厂、工序为 `DYE`、已经进入待加工仓、差异为零、物料/单位一致且数量不超可用量的备货。

备货幂等键中包含本次创建时间，因此同一库存物料在另一次点击时会得到新键。当前创建链没有同步扣减、冻结或占用备货可用数量，存在同一备货重复开单风险。

依据：`src/pages/process-dye-orders.ts:175-309`、`src/data/fcs/process-work-order-stock.ts:1-71`、`src/data/fcs/dyeing-task-domain.ts:3565-3632`。

#### 4.3.3 补料来源染色单（PREP-006）

裁床补料页校验原裁片单、冻结技术包、BOM、图片、用量、损耗和单位后，按补料 BOM 行创建染色单。幂等键包含：

`CUT_PIECE_SUPPLEMENT + DYE + 补料记录 + 原裁片单 + 技术包版本 + BOM 行集合`

若同一补料 BOM 还需要印花，当前代码会额外注册“染色加工单 → 印花加工单”前置关系；这是仓库里唯一真正把两张准备加工单做显式前后依赖的路径，但不是从通用技术包路线边生成，且只覆盖补料。

依据：`src/pages/process-factory/cutting/supplement-management.ts:2870-3290`、`src/data/fcs/supplement-print-prerequisite.ts:1-103`。

#### 4.3.4 加工转换关系、内部节点与执行

| 项目 | 当前代码现状 |
|---|---|
| 加工前 | 正式生产单生成稳定写入聚合物料 ID/名称、目标色、计划量、单位和目标中转区域；专项类型虽预留成分、幅宽、克重等可选字段，但正式生成没有稳定赋值；也没有绑定某张前置单的某次交出或实际投入批次 |
| 需求来源 | 生产单/备货/裁片补料；生产单来源固化技术包版本和 BOM 行集合 |
| 加工后 | 当前领域模型按“染色后的面料”处理，这会把纱线、花边等合法染色对象写错；正确对象应仍是来源 BOM 物料的染后状态。代码还缺少统一实际产出批次、染后状态/属性和下游分配事实，只能由各节点 `inputQty/outputQty/lossQty` 和最终交接量推断。染色前后不一定需要更换逻辑物料 SKU |
| 任务明细 | 主要是加工单头聚合字段和冻结快照中的 `materialItems`；不是可独立承接的正式逐 BOM 需求行 |
| 加工后去向 | 染色专项单保存目标中转区域；待交出仓属于仓储交接域，二者没有统一成同一个加工单字段，也没有后置任务项 |

染色加工单内部固定节点为：

`样衣/色卡 → 原料到位 → 排缸 → 可选水溶 → 染色 → 脱水 → 烘干 → 定型 → 打卷 → 包装 → 交出`

这些是同一加工单内部步骤，不是十张独立加工单。状态还包含测样、暂停、待审核、驳回、部分/全部交出和收货差异。整张加工单只分配给一个染厂；包含水溶时，该工厂必须同时具备染色与水溶能力。PDA 另有接单/拒单，接单不会自动开工。

交出函数表面接受本次交出数量，但只允许单据处于 `WAIT_HANDOVER`；第一次交出后状态变成 `HANDOVER_WAIT_RECEIVE`，不能再次交出。因此当前正式染色单实际上只能成功交出一次。足量收货会自动把关联移动任务改为 `DONE`，差异则写入质量阻断。

依据：`src/data/fcs/dyeing-task-domain.ts:59-180`、`2765-2853`、`2940-3094`、`3633-3697`、`4238-4392`。

#### 4.3.5 水溶后连续染色（PREP-008）

当关联 BOM 同时需要水溶和染色时：

- 染色加工单保存 `requiresWaterSoluble = true`；
- 工艺路线仍显示水溶、染色两个先后节点；
- 执行加工单仍是一张染色单；
- 水溶不是可单独分配、单独交出、由染色单接收的前置加工单。

这说明当前“路线节点粒度”和“加工单粒度”已经不一致。

#### 4.3.6 合并染色任务（PREP-009）

合并染色是把多张既有染色加工单编入同一次染色执行的任务/编组，不是重新生成新的业务需求。它只允许生产单来源，至少两张单，且当前要求同一染厂、同一“面料”、同一目标色、同一染色工序、同一单位；每个成员又必须来自不同生产单。代码实际用 `materialId` 判断是否同物料，但校验提示和快照字段把它一律称为“面料”。因此纱线、花边等即使技术上能以物料 ID 进入，也会被错误命名；目标语义应是“同一可合批 BOM 物料”，而不是“同一面料”。

任务状态只有 `WAIT_DYEING / COMPLETED / DELETED`。完结时一次填写实际投入、实际产出，系统按生产单下单时间先后把产出分配给各成员需求，记录满足、部分满足、未满足和余量；已完成结果可以留原因后更正版本。它没有独立的多次接收/多次交出明细账。

删除后的任务仍会被有效满足量计算纳入（查询同时统计 `COMPLETED` 与 `DELETED` 且保留当前分配版本），但删除又会释放“活动成员占用”，允许另建合并任务。当前因此可能出现已删除分配仍占满足量、新任务再次分配的语义叠加。

被合并后，生产变更同步会保护原加工单快照而不是直接覆盖。它需要在总清单里保留，但不应被误认为第四种准备加工单。

依据：`src/data/fcs/combined-dyeing-domain.ts:1-736`、`src/data/fcs/dye-work-order-combined-dyeing-view.ts:1-73`。

#### 4.3.7 染色在线记录不是另一张加工单

`DyeWorkOrderOnlineRecord` 和 `DyeWorkOrderOnlineView` 用于把同一张染色加工单映射成 PFOS/PDA/入库动作与列表视图；它们不是第四类染色加工单来源。本文把对应文件纳入逐行核查，但不在总登记册重复计数。

### 4.4 印花加工单

#### 4.4.1 生产单来源印花单（PREP-001）

正式服务读取生产单冻结技术包中的 `PRINT` 路线项，将全部关联 BOM 汇总成一张印花单。幂等键是：

`PRODUCTION_ORDER + PRINT + 生产单 ID + 技术包版本 ID + 排序后的 BOM 行 ID 集合`

当前不是按 BOM 物料分支、颜色、花型或物料 SKU 真正拆单。正式生成路径把不同来源对象统一硬编码为面料，保存版号/版次、汇总物料、计划数量和冻结 `materialItems`，但没有正式逐路线节点、逐物料分支、逐花型需求行。

与染色相同，印花执行快照和生成键不保存路线节点身份。两个相同 BOM 集合、但位于不同路线位置的印花节点，当前不能稳定生成和追溯为两次不同加工。

更关键的是，`deriveFormalProductionOrderProcessSnapshots()` 先按 `DYE`、`PRINT` 两个工序码取数，再把该工序码下所有路线项的 `linkedBomItemIds` 去重扁平化；每个工序码只返回一个快照，并强制所有被聚合 BOM 只有一个数量单位，计划量则把它们全部相加。见 `src/data/fcs/production-process-snapshot-derivation.ts:30-103`。这会出现两种错误结果：

- 面料、纱线、花边等不同分支恰好同单位时，可能被合成一张无法表达各自前后顺序的加工单；
- 不同分支单位不同（例如米、公斤）时，直接以“多种单位无法合并”为由生成失败。

共享染缸、同厂批量加工可以是执行层的后续编组，但不能替代技术包中的独立路线节点，也不能先按工艺码吞掉物料分支。

#### 4.4.2 备货来源印花单（PREP-002）

平台人工“按备货创建”，只允许选择当前印花厂、`PRINT` 工序、已入待加工仓、无差异、物料/编码/单位一致且数量足够的备货。它与备货染色一样把本次时间写进唯一键，也没有创建后库存占用或扣减事实，存在重复开单风险。

依据：`src/pages/process-print-orders.ts:186-325`、`src/data/fcs/printing-task-domain.ts:2380-2465`。

#### 4.4.3 补料来源印花单（PREP-003）

裁床补料路径按补料记录和 BOM 行生成。一张补料记录内，不同 BOM 分别建单；同一 BOM 最多一张印花单。计划量按“补片数 × 单件用量 × 损耗”计算，补料页会把大于 1 的损耗值按百分数、小于等于 1 的值按比例归一。

若同一补料 BOM 同时染色和印花，印花开工前会检查前置染色单：必须 `COMPLETED`、无差异、有大于零的 `qualifiedQty`、数量和单位足够。这里的字段和提示文案称“染色合格输出”，但已确认业务并不在准备阶段做质量放行；它实际读取的是染色收货量或最后一个完成节点的输出量。因此这不是合理的“合格产出”门禁，而是把“前置已交出/下游已收到的可用数量”错误命名成质量结果。常规染色足量收货首先形成 `FULL_HANDOVER`；若没有额外完成推进，还可能一直达不到 `COMPLETED` 门禁。

#### 4.4.4 “裁片印花”应清理，但 `PRINT` 也不能被收窄成只有面料

【业务已确认】本项目中的 `PRINT` 属于准备阶段，不能作用于已经按纸样裁出的衣片；裁剪后的图案类工艺使用烫画或直喷。但准备阶段的印花对象不能因此被收窄成只有面料，它应当是技术包中明确具有印花需求的具体 BOM 原物料分支，包括经业务确认可印花的辅料。当前印花执行数据只能证明**代码主链被做成了面料印花**，不能证明业务只允许面料：

- 工序字典和 BOM 自动路线把 `PRINT` 固定放在准备阶段，但把目标对象强制写成 `FABRIC/面料`；
- 正式生产单、备货、补料生成入口均按面料印花单结构创建；
- 独立工厂端 `PrintingMaterialIdentity` 更严格地把 `objectType` 限定为 `'面料'`，投入和产出均为面料；
- 当前种子全部写入 `objectType: '面料'`、`isFabricPrinting: true`。

但通用正式印花域仍保留了与业务冲突的类型面：

- `PrintWorkOrder.objectType?: '面料' | '裁片'`；
- `isPiecePrinting`、`isFabricPrinting` 两组布尔字段；
- `getProcessObjectType()` 在缺少明确对象时，会把 `PRINT` 默认回退为“裁片”；
- 平台结果视图把一切非“面料”的对象都压成“裁片”；
- 印花交出又按“单位是否等于米”反推 `FABRIC/CUT_PIECE`，把以 `Yard` 计量的面料误判成裁片。

依据：`src/data/fcs/printing-task-domain.ts:77-100`、`927-1009`、`2097-2134`、`2696-2727`，`src/data/fcs/process-quantity-labels.ts:58-96`，`src/data/fcs/process-work-order-domain.ts:311-391`，`src/data/fcs/platform-process-result-view.ts:519-552`，以及严格限定面料的 `src/data/fcs/printing-work-order-business.ts:70-89`。

【对抗性结论】`isPiecePrinting` 和裁片回退不是“未来可以做裁片印花”的扩展点，必须清理；但把 `PRINT` 恒定成面料也不正确。目标模型应让 `PRINT` 的主加工对象恒为**来源 BOM 原物料分支**，保存实际物料类别并排除已裁衣片；烫画/直喷各走生产阶段专项工艺，不通过 `isPiecePrinting` 复用印花单。具体哪条辅料需要印花，以该条 BOM 的显式需求为准；系统不能对所有“辅料”一概允许、禁止或合并。

#### 4.4.5 加工转换关系、内部节点与执行

| 项目 | 当前正式印花代码 | 正确业务边界 |
|---|---|---|
| 加工前 | 原面料/待印面料 | 该路线节点绑定的实际 BOM 原物料批次；可以是经确认适用的面料或辅料，但不能是已裁衣片 |
| 需求来源 | 生产单/备货/补料 + 技术包 BOM 印花要求 | BOM 印花要求说明为什么需要加工，不等于本次实际投入 |
| 加工后 | 已印花面料 | 仍为同一 BOM 物料分支的加工后状态，应记录本次实际产出批次、数量和后续承接；不能统一改名成面料 |
| 任务明细 | 正式生成稳定保存版号/版本、物料、颜色、数量和单位；计划卷数只是可选字段/Mock，并非正式单必有 | 按路线 occurrence 和 BOM 物料分支拆清；不应出现纸样裁片/菲票明细，那属于烫画或直喷加工单 |
| 去向 | 中转区域/仓储交接域；没有明确后置任务项 | 按该 BOM 分支路线进入下一道准备工序，或进入裁剪、毛织、车缝使用/辅料仓等真实消费节点 |

正式印花节点依次包含花型测试、打印、转印、交出，状态细分为待花型、待测色、待打印、打印中、待转印、转印中、待交出、交出待收货、部分/全部交出、收货差异、待审核、驳回和完成等。

- 加工单整单分配给一个印花厂；PDA 有独立接单/拒单，接单不会自动开始花型测试或打印。
- 部分执行函数只读取加工单，没有统一校验 `acceptanceStatus = ACCEPTED`，存在绕过接单直接执行的代码路径。
- 与染色相同，交出函数只允许 `WAIT_HANDOVER`；第一次交出后不能再次调用，故不能真正多次交出/接收。
- 足量收货会自动把关联移动任务设为 `DONE`；差异按 `QUALITY` 原因阻断。
- 印花交接对象没有继承来源 BOM 的实际物料类别，而是用“单位等于米则面料，否则裁片”反推；以 `Yard` 计量的面料会被错误写成裁片，按公斤计的纱线或按条计的花边也没有合法类别可落。这是对象分类缺陷，不是裁片印花能力。

依据：`src/data/fcs/printing-task-domain.ts:54-160`、`1853-2083`、`2527-2788`。

### 4.5 准备阶段共同状态、交接和数量问题

三类准备加工单都能投影成统一列表对象，但字段完整度不同：水溶虽然可保存交接单 ID，统一对象的结构化 `handoverRecords` 固定为空；正式染色/印花又主要把已有交接汇成一条虚拟批次。因此统一视图不能稳定呈现三者的逐次交接记录，执行状态也仍来自三个专项域。

通用 PDA 开工前置判断并没有真正检查 `acceptanceStatus`、当前工厂是否已接单、实际投入是否已接收或仓库交接是否发生；除补料印花的专门阻断外，通常只要找到关联加工单就判定满足。染色/印花仍允许先做调色、排缸、花型核对或试印准备，真正加工前再要求投入到位；水溶域动作也主要按加工状态而非统一接单门禁判断。当前“接单、接收投入、开工”没有形成一套强门禁。

| 能力 | 正式印花 | 正式染色 | 独立水溶 |
|---|---|---|---|
| PDA 接单/拒单 | 域内有，但通用开工门禁未强制验证已接单 | 域内有，但通用开工门禁未强制验证已接单 | 域内有，物料与开工动作也未统一依赖接单事实 |
| 多次接收 | 状态/适配层不统一 | 状态/适配层不统一 | 不支持目标业务所需的任意多批 |
| 多次交出 | 数量参数看似支持，状态实际只允许一次 | 数量参数看似支持，状态实际只允许一次 | 明确禁止部分交出 |
| 实际产出批次/加工状态 | 无统一事实 | 无统一事实 | 无统一事实 |
| 人工完成 | 与收货/移动任务自动推进混杂 | 与收货/移动任务自动推进混杂 | 收货或差异确认后自动 `DONE` |
| 中间质量判断 | 差异写 `QUALITY` 阻断 | 差异写 `QUALITY` 阻断 | 差异需主管确认 |

这与已确认业务口径有三处直接冲突：现场需要反复交出/接收；前置产出交付后，下游确认接收应自动开工；整个生产只在成衣回后道工厂时做质检，准备加工收货不应包装成质量放行。

统一准备页面适配器还会把多条交出记录合并成一个虚拟批次。即使底层某个域保存了多次交出，平台视图也无法按真实批次逐条呈现，见 `src/data/fcs/page-adapters/process-prep-pages-adapter.ts:269-320`。

当前还存在计划数量公式不一致：

- 独立水溶产物按 `成衣数量 × 单耗 × (1 + 损耗率 / 100)` 计算，见 `src/data/fcs/production-artifact-generation.ts:637-685`；
- 正式染色/印花快照按 `生产单全部 SKU 数量 × 单耗 × (1 + lossRate)` 计算；该派生函数没有统一校验损耗率范围，也没有按 BOM 的 `applicableSkuCodes` 筛选适用 SKU，见 `src/data/fcs/production-process-snapshot-derivation.ts:25-69`；
- 通用任务明细候选也使用 `1 + lossRate`，见 `src/data/fcs/task-detail-rows.ts:157-175`。

补料 BOM 解析路径另行要求损耗率在 0～100；独立水溶路径只校验有限且非负并使用 `/100`。所以当前至少存在两套计算口径和不同校验规则。若 BOM 中 `5` 表示 5%，正式 DYE/PRINT 和通用任务明细会按 `1 + 5` 放大；当前代码不能证明全链使用同一口径。

正式 DYE/PRINT 忽略 `applicableSkuCodes` 还会带来独立的数量问题：某 BOM 只适用部分颜色/尺码时，仍按生产单全部 SKU 汇总；独立水溶和部分通用明细路径却会按适用 SKU 筛选，三者结果可能不同。

计价/执行单位也不统一：正式印花、染色派单价格单位固定为 `Yard`，没有随加工数量单位变化；独立水溶的通用移动任务又把米和码都映射成 `METER`，虽然原单和显示/来源单位仍保留。数量、计价和只读标准枚举的移动任务之间可能不是同一口径。

### 4.6 准备阶段的生成断点

生产单任务拆分页面的实际写操作主要调用生产任务 upsert；预览只展示已经存在的印花/染色加工单，它本身不负责生成准备加工单。正式生产单创建时会调用 `buildFormalProductionOrderProcessSnapshots()` 和批量 `prepareProcessWorkOrdersForFormalProductionOrders()`，再在同一事务中提交 DYE/PRINT 加工单；没有生产调用方的只是单生产单包装函数 `ensureProcessWorkOrdersForFormalProductionOrder()`，不是整条正式生成链。独立水溶则通过生产产物同步链惰性生成。

因此当前不能把“生产单完成任务拆分”理解为准备加工单的统一生成时点；DYE/PRINT 在生产单创建链生成，水溶在另一条产物同步链生成，任务拆分预览和各专项执行单仍可能不一致。

### 4.7 另一套工厂端印花生产单（PREP-010）

`src/data/fcs/printing-work-order-business.ts` 还实现了一套与平台正式印花单不同的 `PrintingWorkOrderBusinessRecord`。它的来源枚举直接包含：生产单、采购、备货、补料；Mock 种子也覆盖这四类来源。

这套模型具备平台正式印花域缺少的能力：

- 显式计划投入和实际投入；
- 明确花型及固定加工后物料；
- 开工前替换投入物料；
- 多次投入接收，首次接收自动开工；
- 多次交出、多次收货；
- 卷码、批次及信息单/确认单/批次单/卷标打印。

它把加工状态和交接状态分开：加工状态为待分配、待投入接收、加工中、加工完成、已取消；交接状态为未开始、待交出、部分交出、交出待接收、部分接收、已接收。这也是它能表达多批数量、而平台正式印花单的单一状态机容易卡住第二次交出的原因。

但是它没有接入正式生产单加工单生成注册表，当前主要依赖种子记录。工厂路由 `/fcs/craft/printing/work-orders` 读取这套模型，平台路由 `/fcs/process/print-orders` 读取 `printing-task-domain.ts`；两端名义上都叫印花加工单，却不是同一事实源。页面适配器中“同源”的说明与实际代码不符。

依据：`src/data/fcs/printing-work-order-business.ts:1-876`、`src/pages/print/templates/printing-work-order-template.ts:1-212`、`src/data/fcs/page-adapters/process-prep-pages-adapter.ts:269-320`。

### 4.8 旧染印加工单兼容域（PREP-011）

旧模型支持 `PRINT / DYE / DYE_PRINT`，状态为草稿、加工中、部分返回、完成、关闭。它能保存生产任务、加工方、计划数量和多次返回，却没有物料身份、单位、来源快照、路线边、明确投入/产出或任务明细。

种子文件明确把它标为兼容快照、非主真相。`dye-print-orders` 页面模块及全局事件处理器仍残留，但当前路由总表和菜单没有注册可达入口，属于孤儿/兼容代码而非现行菜单页面。当前情况登记册必须记录它，不能假装它不存在；目标清理则应在确认没有存量数据、动态入口、handler 和测试消费者后，把整套旧记录、页面、处理器、文案与契约删除。

依据：`src/data/fcs/store-domain-quality-types.ts:176-255`、`src/data/fcs/store-domain-quality-seeds.ts:345-368`、`src/pages/dye-print-orders.ts:1-744`。

### 4.9 生产物料准备/领料任务（PREP-012，非加工单）

`production-material-prep.ts` 处理 BOM 备料、仓库/采购/染色/印花来源提示、领料、暂存、确认、退回和多次领料会话。它不加工物料，因此不是第四种正式 PREP 加工单。

不过，这套仓储准备域承担了部分“染印是否回货、裁床是否可继续”的就绪判断，与准备加工单自身交接并存；两者没有统一到同一条实际投入记录。

### 4.10 采购需求与花边加工的阶段缺口

正式 `ProcessWorkOrderSourceType` 只有生产单、备货、裁片补料，没有 `PURCHASE`。所以“采购备货需求来源的加工单”在通用准备模型中目前无法表达。

在本次核查覆盖的准备阶段及辅料加工专项域中，明确由 PMS 采购单投影生成加工单的是花边专项域：它有明确投入行、输出花边 SKU、多次加工填报、多次交出/收货和人工完结，但没有 `PREP/PROD` 阶段、技术包路线节点或通用加工单来源。为避免重复，它在 6.11 作为 `PROD-027` 完整展开。

## 5. 生产阶段：任务层共同现状

### 5.1 生产任务不是加工单

技术包非准备路线项先生成 `GeneratedTaskArtifact`，再生成 `ProcessTask`。任务负责：

- 分配到工厂；
- 接单、开始、交出和完成等协作状态；
- 保存路线步骤和任务明细；
- 在部分工序下再关联专项加工单。

但不同工序的“任务与加工单”关系不同：

| 工序 | 当前关系 |
|---|---|
| 裁剪 | 一个裁剪生产任务可生成多张裁片单 |
| 毛织 | 上游毛织任务与毛织加工单并存，执行进度以毛织加工单为准 |
| 辅助/特种工艺 | 一组同生产单、管理域、工艺、作用对象的需求行生成一张专项加工单；`sourceTaskId` 可以后补，不能概括为严格“一源任务一加工单” |
| 车缝 | 生产任务自身就是主要分配/履约对象，没有统一车缝 `WorkOrder` |
| 烫包 | 当前代码把它实现为可分配、可执行的独立生产任务，也可被固定合并任务吸收；在最新后道规则中，任务含烫包时 QC 默认不勾选我方项目但允许调整，任务仅车缝时则固定由我方执行三项。旧任务和静态路线仍可能另行解释烫包，尚未收口为唯一规则 |

通用 PDA 任务完成入口还要求填报量位于目标量的 80%～120% 区间。该比例门槛不是裁片、毛织、花边、捆条或后道各专项域共同认可的规则，不能作为所有加工单的统一完成条件。

### 5.2 当前通用任务明细

通用 `TaskDetailRow` 只支持四个维度：成衣颜色、成衣 SKU、纸样、物料 SKU；每行保存数量、单位和部分来源引用，见 `src/data/fcs/task-detail-rows.ts:20-75`。

这套明细有以下限制：

- 没有通用加工对象类型；
- 没有前置/后置任务项 ID；
- 没有接收、完成、交出累计数量；
- 没有批次、菲票或仓库库存行主键；
- 对不支持的组合会回退为成衣 SKU；
- 默认单位经常回退为“件”，无法覆盖片、米、个、条、张等所有加工单。

所有新建 `ProcessTask` 的任务头数量还统一取生产单成衣总件数，单位固定 `PIECE`，计价单位固定“件”；所以路线节点即便实际处理面料米、裁片片、纱线公斤、捆条米、盘扣个或橡筋条，任务头仍显示成衣件数。技术包路线已经提供 `linkedBomItemIds/linkedPatternIds`，但通用明细生成还会重新扫描整份技术包，匹配失败时回退为全部合格 BOM，可能把无关物料/纸样带入任务。

### 5.3 当前任务依赖

同一生产单内，步骤 N 的每张任务依赖步骤 N-1 的全部任务。并行只表示相同步骤号，不表达对象汇合。准备加工单不在这张依赖图中。由此可见，当前 `dependsOnTaskIds` 只能作为展示型粗依赖，不能作为“前置有产出，当前加工单即可接收并自动开工”的执行依据。

任务分配策略文件称独立车缝应按 SKU、固定合并任务应按整单；运行时基础任务却都先初始化为 `ORDER`，只有用户再执行“按明细/SKU/颜色拆分”才出现子任务。因此“字典/策略写了分配粒度”不等于生成结果已经按该粒度落地。

## 6. 生产阶段：逐类加工单现状

> 本节先建立完整目录；各专项领域的精确状态、页面和数量规则按当前代码逐项说明。

### 6.1 裁片单（PROD-001）

#### 6.1.1 单据定位与生成粒度

裁片单是裁床的真执行主单。它从生产单、技术包快照、颜色物料对应和纸样关系生成，稳定保存：

- 生产单和源裁剪任务；
- 面料/BOM 身份；
- 纸样文件和适用 SKU；
- 裁片部位、颜色、尺码和片数；
- 来源类型、回仓方式和内部工艺策略。

生成键包含生产单、款式、技术包版本、完整物料身份和完整纸样身份，不直接包含成衣 SKU。同一生产单会因物料/颜色或纸样身份、版本、门幅不同生成多张裁片单；多个 SKU 如果映射到同一物料和纸样，会汇入同一张裁片单，SKU 只有在间接导致物料或纸样身份不同的情况下才拆单。见 `src/data/fcs/cutting/generated-cut-orders.ts:20-82`、`303-596`。

生成并非只要 BOM 有布料就发生，当前同时要求：

- 生产单有正式发布的技术包快照；
- 生成边界判定“需要裁剪”；
- 技术包有颜色物料映射，且物料不是成衣；
- 能匹配纸样文件和裁片部位行。

其中“是否需要裁剪”并不是直接用“需按纸样形成衣片的布料默认裁剪、纯整件毛织成衣主干例外”的规则，而是在任务摘要的 `coveredProcessNames/taskTypesTop3` 中搜索“裁片、裁剪、裁床”。所以当前代码尚未稳定落实该业务规则。

#### 6.1.2 加工转换关系

| 项目 | 当前代码现状 |
|---|---|
| 加工前 | 面料/里料等可裁物料；通过配料、接收和待加工仓进入裁床 |
| 需求来源 | 正式生成记录只接受独立裁剪任务或“裁剪+车缝+烫包”合并任务，并绑定冻结技术包物料和纸样；补裁/补料属于另行记录和旁路，不能写成该正式裁片单的生成来源 |
| 加工后 | 按纸样、部位、颜色、尺码形成裁片及菲票 |
| 任务明细 | 裁片单下的物料、纸样、SKU 范围和裁片部位矩阵；后续铺布单进一步承载实际铺布/裁剪执行 |
| 加工后去向 | 可能进入辅助/特种工艺，返回裁床待交出仓后与其他裁片一起交车缝；无工艺的裁片直接待交出 |

数量还有一个关键口径问题：裁片单头 `requiredQty` 是把生产单成衣 SKU 计划件数相加，并不是“部位片数”；真正部位片数在裁片部位/菲票明细内。因此不能用单头数量直接代表裁片总片数。

裁床运行时事件账还把中文单位“米”归一为英文 `yard`，并非仅做展示翻译，而是错误改变单位语义，见 `src/data/fcs/cutting/cutting-runtime-event-ledger.ts:809-815`。

#### 6.1.3 裁床相关单据的边界

以下均与裁片单有关，但不是新的加工单类型：

- 唛架方案：排版方案；
- 铺布单：实际铺布/裁剪执行批次；
- 菲票：裁片包/工艺流转标识；
- 转运袋：物理装袋载体；
- 裁片交接单/交出记录：责任和数量转移；
- 待加工仓、待交出仓记录：库存投影；
- 裁片放行、退仓、补料、关闭记录：异常和补充流程。

【核查判断】这些单据不能从总文档中省略，但不能把每张铺布单或菲票都称为“加工单”，否则任务、加工单、执行批次和物理载体会再次混淆。

实际链路为：

`裁片单 → 唛架/铺布 → 裁剪完成事件 → 实际裁片产出 → 菲票 → 裁片待交出仓`

生成菲票要求已有实际产出、裁剪完成、数量大于零、物料/纸样身份完整、无待处理差异且尚未生成菲票。每个颜色尺码批次再按每一裁片部位及部位实例生成菲票；菲票保存卷号、颜色、尺码、部位、扎号、适用 SKU、同套裁片和特殊工艺。

依据：`src/data/fcs/cutting/generated-fei-tickets.ts:458-489`、`1374-1485`、`1769-1980`。

#### 6.1.4 并存的旧裁片单与演示进度（PROD-002）

正式 `GeneratedCutOrderSourceRecord` 之外，仓库仍有旧 `CutPieceOrder` 运行时数据；裁床进度页又按记录序号套用演示进度模板，而非完全由实际裁剪事件投影。页面、菲票、仓库或进度如果读取不同来源，可能对同一裁片单给出不同状态。

依据：`src/data/fcs/cutting/cut-piece-orders.ts:1-599`、`src/data/fcs/cutting/order-progress.ts:287-354`。

### 6.2 捆条加工单（PROD-003）

捆条在当前代码里有双重身份：

1. 字典中代码为 `AUX_BINDING_STRIP`，属于辅助工艺，但管理域为裁床厂；
2. 当前页面实际执行使用独立 `BindingProcessOrder`，入口位于裁床“特殊工艺/捆条加工单”。

此外，同一 `special-processes-model.ts` 还保留旧 `SpecialProcessOrder`：其 `processType` 目前只接受 `BINDING_STRIP`，状态为草稿、待执行、执行中、已完成、已取消，并使用独立本地存储键。该旧工艺单及其范围行、执行日志、后续动作投影与现代 `BindingProcessOrder` 并存；它不是第二种业务捆条工艺，却是第二套代码事实源。

其加工转换关系为：

| 项目 | 当前代码现状 |
|---|---|
| 加工前 | 面料，通常由关联裁片单/纸样捆条配置和捆条规格决定 |
| 需求来源 | 生产单技术包纸样的捆条行；也可能成为补料链的来源 |
| 加工后 | 捆条，计划和交出通常按米；另生成捆条菲票 |
| 任务明细 | 捆条规格、裁法、宽度、长度、条数、来源物料和关联裁片单 |
| 加工后去向 | 当前仓库联动交中央辅料仓；盘扣加工单可选择捆条菲票作为投入。后续如何被车缝消费尚未形成显式承接关系 |

捆条与盘扣不能合成同一加工单：捆条是“面料→捆条”，盘扣是“捆条菲票→盘扣成品”。

并非每张裁片单都生成捆条加工单。当前只对“允许生成内部工艺单、且不是三方仅回报裁剪结果”的裁片单继续检查纸样捆条配置；纸样不存在、捆条行为空、门幅无效或计算后数量无效时都不会生成。符合条件时一张裁片单对应一张捆条加工单，单内可以有多条捆条规格。计划量使用“长度 × 宽度 ÷ 门幅 × 1.3”，并设置至少 4 米的下限。仓库联动为：

`待加工面料库存 → 加工消耗 → 待交出捆条库存 → 中央辅料仓`

它支持多次接收、多次加工填报和多次交出，但“加工中且存在任意正数产出”就允许人工完成，不要求计划全部完成或产出全部交出。`sourceTaskId` 还由 `TASK-BIND-{cuttingTaskId}` 临时拼接，不是通用生产任务的稳定外键。

依据：`src/pages/process-factory/cutting/binding-strip-orders.ts:102-205`、`296-375`、`946-1274`，仓库联动见 `src/data/fcs/binding-process-warehouse-linkage-service.ts:58-138`。

### 6.3 毛织加工单

毛织按技术包纸样类别和路线项区分两类。本项目不存在名为 `ASSEMBLY/组装` 的独立核心节点；若现场口语中的“组装”只是把衣片、毛织片和辅料缝合成衣，它属于车缝形成成衣的工作内容，不能为了名称听起来不同而再造一层路线。只有未来确认确实存在与车缝分离、独立交接和独立承担责任的装配工位时，才有新增节点的业务依据。

#### 6.3.1 整件毛织（PROD-004）

| 项目 | 当前代码现状 |
|---|---|
| 加工前 | 纱线/毛织物料 |
| 需求来源 | 技术包毛织路线、成衣 SKU 数量和冻结毛织资料 |
| 加工后 | 成衣 SKU，单位件 |
| 任务明细 | 按成衣 SKU；加工单中还会关联机器、领料、进度和交出 |
| 加工后去向 | 后道工厂，不经过裁剪和普通车缝 |

这与已确认的“纯整件毛织款主干：纱线 → 成衣”一致。这里的免裁剪、免普通车缝只适用于该整件毛织成衣主干；如果同一款还存在需裁面料、梭织拼接部件或另行车缝组合的分支，这些分支不能因为同时有一张 `WHOLE_GARMENT` 毛织单就被全局删除。

毛织任务生成后默认分配给自有毛织厂并自动接单；加工单内部仍要分批接收纱线、填报产出、交出。纱线单位为公斤，成衣产出单位为件。它支持多次纱线接收、多次产出填报、多次交出和下游逐次确认，最终加工单由人工点击完成。

但人工完成条件只要求存在任意正数交出，不要求计划全部完成、全部交出或全部被下游接收。每次交出生成独立 A4 交出单；若缺真实款式图，打印会被禁用。

#### 6.3.2 部位毛织（PROD-005）

| 项目 | 当前代码现状 |
|---|---|
| 加工前 | 纱线/毛织物料 |
| 需求来源 | 毛织纸样、部位、颜色尺码和生产数量 |
| 加工后 | 毛织横机成片/毛织部位 SKU |
| 任务明细 | 纸样 + 成衣 SKU，并生成稳定部位码/产出 SKU |
| 加工后去向 | 当前毛织单只保存 `downstreamTarget = 裁床待交出仓`；“再与其他裁片汇合交三方车缝”是业务方向，现有车缝配料链尚未消费毛织产出 |

当前字典把整件毛织目标设为成衣、部位毛织目标设为“裁片部位”，见 `src/data/fcs/process-craft-dict.ts:1167-1192`、`1308-1313`。但毛织专项域把部位毛织产出明确建模为独立 `WOOL_PANEL`，见 `src/data/fcs/wool-domain/types.ts:1-22`、`src/data/fcs/wool-domain/tech-pack-source.ts:207-215`。**毛织片去裁床待交出仓，不等于它在对象身份上就是普通裁片**；当前字典的通用目标对象压扁了二者，后续若按“裁片”统一统计、补料或生成工艺，可能误套普通面料裁剪来源和菲票规则。

部位毛织存在两套计划数量：通用任务明细按“成衣数量 × 每件毛织部位片数”生成，单位片；毛织加工单却把每个部位计划量直接等于成衣数量，单位件，忽略 `pieceCount`。同一需求因读取层不同会出现片数和件数差异。

依据：`src/data/fcs/wool-domain/tech-pack-source.ts:118-216`、`244-426`，执行见 `src/data/fcs/wool-domain/commands.ts:448-724`、`1252-1313`，查询见 `src/data/fcs/wool-domain/queries.ts:450-600`。

### 6.4 独立车缝任务（PROD-006）

当前车缝主要由 `ProcessTask` 和三方车缝外发域承担，不存在与染色、毛织、特殊工艺相同结构的统一“车缝加工单”。

当前实际共同承担车缝执行的对象是：

- `ProcessTask`：路线、分配和任务状态；
- `EffectiveTaskAssignment`：工厂及 SKU 的有效分配；
- `CuttingSewingDispatchOrder`：裁片配料/交出任务；
- `CuttingSewingDispatchBatch`：颜色尺码交出批次；
- `CuttingSewingTransferBag`：中转袋；
- `PdaHandoverHead/Record`：实物交出记录；
- `SewingSampleApprovalSuggestion`：样衣确认配套单据。

另外还有两套不能漏掉、但也没有统一进上述主链的事实：

- `SewingMaterialHandoverContext/Event`：只为“裁剪+车缝+烫包”合并任务初始化并记录分批物料交接，不是所有独立车缝任务的通用辅料承接；
- `SewingCutPieceResponsibilityContext/Projection`：冻结 `SKU × 裁片部位` 责任并记录裁片交出，齐套可生产件数按各必需部位最小值计算；它与 `sewing-dispatch.ts` 的配料/袋/交出投影并存。

| 项目 | 当前代码现状 |
|---|---|
| 加工前 | 当前独立车缝主链主要能证明裁床交出的多种裁片；辅料只在合并任务专用物料交接域局部表达，毛织部位尚未接入统一车缝消费链 |
| 需求来源 | 生产单车缝路线项和任务分配 |
| 加工后 | 车缝成衣 |
| 任务明细 | 通用任务默认按成衣 SKU；裁片交接存在 `sewing-dispatch` 与逐 SKU/部位责任投影两套事实，辅料交接只覆盖特定合并任务 |
| 加工后去向 | 回货到后道工厂；也可能由固定合并任务继续承担烫包责任 |

【业务已确认】裁片交给三方车缝工厂后，系统应自动为三方完成接收并开工，不需要“收到任一裁片还是全部齐套”的门禁判断。

【代码事实】当前车缝域仍存在独立任务接收、裁片交接、物料交接、回货、补料、责任转移等多套记录；“交出裁片即自动接收并开工”尚不能由一条统一写回链证明：

- 直接分配车缝任务时，系统在“分配”这一刻就写成已接收，而不是等待实际裁片交出；
- 裁片交出单和中转袋提交没有可靠回写同一车缝任务开工；
- PDA 仍要求人工打开任务、填写时间/证明并点击开始加工。

`sewing-dispatch.ts` 这一路配料允许“缺少部位、特殊工艺未完成”作为非阻断提示后继续提交；其“可折算成衣数”取各裁片部位数量的最大值，可能高估不齐套裁片能生产的成衣件数。另一套 `sewing-cut-piece-responsibility.ts` 投影则按各必需部位最小值计算，但两者没有统一为同一事实。这里的数量缺陷与业务口径“系统不需要因齐套阻止三方开工”并不矛盾：不阻断开工，不代表数量换算可以错误。

裁片交给车缝厂时生成的交接单还被写成“接收方类型=后道工厂、阶段=后道阶段”，单头任务 ID 使用裁片配料单 ID 而非车缝生产任务 ID，存在明确的对象、阶段和关联键错误。

依据：`src/data/fcs/effective-task-assignments.ts:15-205`、`src/data/fcs/cutting/sewing-dispatch.ts:913-943`、`1566-2149`、`2808-3154`、`src/data/fcs/sewing-material-handover.ts:85-221`、`src/data/fcs/sewing-cut-piece-responsibility.ts:207-323`、`421-608`、`src/data/fcs/runtime-process-tasks.ts:3089-3268`、`src/pages/pda-exec-detail.ts:3624-3869`、`6260-6331`。

#### 6.4.1 裁片交出、退仓和跟单责任配套对象

第二轮沿“菲票 → 中转袋 → 裁床待交出仓 → 三方车缝厂”继续逐行反查，确认这条链保存了非常细的实物事实：菲票、铺布批次、裁片单、颜色尺码、部位、扎号、片数、袋周期、来源库位、接收工厂、车缝任务引用、交出和接收差异。整袋交出还会校验同袋菲票是否属于同一生产单、同一任务和同一工厂；特殊工艺回仓后，全部必需工艺已经返回的菲票才会被标记为可继续交车缝。见 `src/data/fcs/cutting/handover-orders.ts:13-309`、`1513-2006`，`src/data/fcs/cutting/transfer-bag-operations.ts:32-164`、`415-585`、`3834-4050`，`src/pages/process-factory/cutting/wait-handover-runtime.ts:938-1130`、`1757-1967`。

但这些证据只能证明裁片已经按袋、票、部位和数量离开裁床，不能证明同一正式 `ProcessTask` 随即被自动接收和开工：普通整袋交出路径没有调用车缝任务接收/开工写回；载具周期的 `startedAt` 只是袋的使用周期开始；页面模型还可能根据唛架、裁片单或款式合成 `sewing-task-*` 引用，甚至注入演示菲票，不能当作正式任务外键和真实库存。见 `src/data/fcs/cutting/transfer-bag-runtime.ts:75-152`、`456-568`，`src/pages/process-factory/cutting/transfer-bags-model.ts:1741-2185`、`2463-2645`。

此外还有三类相邻对象，均不应重复计算为车缝加工单：

- 车缝裁片退仓单：把已交三方的裁片退回裁床仓；只有正式调减、取消或转派类原因在仓库实收后才减少工厂回货责任，普通多交、错发、换片不减少责任，见 `src/data/fcs/sewing-cut-piece-return-workflow.ts:19-148`、`266-507`。
- 车缝 PPIC 责任版本：只转移同一工厂任务的跟单负责人和剩余事项，不转移工厂、实物或加工数量；且只允许 PPIC 团队负责人操作，见 `src/data/fcs/sewing-outsourcing-responsibility.ts:1-216`。
- 车缝成衣回货跟踪：聚合任务分配、裁片责任、申报/确认数量和后道确认版本；当前初始化是三类任务的演示投影，不是生产单实时生成器，见 `src/data/fcs/sewing-outsourcing-return-tracking.ts:40-202`、`204-260`。

### 6.5 固定合并生产任务

当前只支持两种固定合并类型：

#### 6.5.1 车缝 + 烫包（PROD-007）

- 必须选择同一生产单的车缝和烫包源任务；
- 源任务必须未分配、未开工、未拆分、未被其他合并任务吸收；
- 合并后按整张生产单分配；任务明细可展示，但不是逐行选择分配；
- 裁剪仍独立，中央辅助/特种加工单仍可生成。

#### 6.5.2 裁剪 + 车缝 + 烫包（PROD-008）

- 必须选择同一生产单的裁剪、车缝、烫包源任务；
- 按整张生产单分配；
- 裁片单和唛架仍保留作为三方执行依据；
- 中央辅助/特种加工单被边界规则抑制，由三方整单责任吸收。

见 `src/data/fcs/merged-production-task.ts:1-41`、`src/data/fcs/task-generation-boundaries.ts:30-87`。

两类合并任务的定义文案提前宣称覆盖开扣眼、装扣子、烫包以及部分辅助/特种工艺，但运行时结构化 `coveredProcesses` 实际只保存用户选中的裁剪、车缝、烫包源任务；另用硬编码旧工序码吸收/禁用部分来源任务，并没有冻结一份完整、结构化的全部责任清单。提前保存“三方原约定承担什么”本身不与到货 QC 冲突；冲突发生在代码把这项说明用于吸收/抑制专项加工单，或把责任当成已经完成、必然需要我方处理的事实。

合并识别还要求源工序集合精确等于上述两项或三项；只要同一选择里多出其他工序，就不会识别为合并任务。`裁剪+车缝+烫包` 的运行时任务吸收代码仍主要识别旧概括码 `EMBROIDERY / PLEATING / SPECIAL_CRAFT`，没有覆盖现在 17 个具体工艺 code；所以“责任范围宣称吸收全部辅助/特种工艺”与实际可能残留的专项任务不一致。

### 6.6 KOL 整单任务（PROD-009）

KOL 样衣/样品小单会让所有准备阶段加工（水溶、染色、印花）保持独立，把其余可生成的生产任务覆盖进一张固定整单任务：

- 自动分配给 KOL-GOTO；
- 自动接收；
- 整单固定总价；
- 首次领料自动开工；
- 可多次交出；
- 交出数量作为加工完成数量；
- 不生成普通裁片单，也不生成中央辅助/特种工艺加工单；
- 作为 KOL 样衣/KOL 小单的整单特例，不进入普通生产单的后道回货与处理阶段。

整单任务的生成、分配和接收身份见 `src/data/fcs/process-tasks.ts:684-782`；首次领料自动开工、多次交出和完成数量等执行事实见 `src/data/fcs/kol-goto-pda-domain.ts:146-305`、`344-569`。

它是特殊销售类型的整单责任任务，不是普遍加工单模型，也不应被用来推导普通生产单的生成规则。

- “花朵”按裁片菲票和裁片部位承接，与本轮确认业务一致；这里不再作为对象不确定项。后续只需确保任务明细保存具体纸样/部位和前后置任务项。
- “绣花、压褶、贝壳绣”既有旧顶层工序/工艺映射，又出现在现代辅助工艺清单，存在同一业务名生成普通任务或专项加工单的双重入口。
- 现代辅助工艺“曲牙绣”是确认保留的唯一词条；基线 `77cd316a` 曾把旧名称归入普通车缝。2026-09-07 续作已删除该映射及可操作旧词条；当前旧工序编码和旧词条定义精确检索均为零，`check-process-craft-final-taxonomy` 已验证旧值 `262144` 不再解析。禁止恢复旧选项、映射、文案和支持其执行的测试。压褶与打褶则是两个不同且都要保留的工法，不能因为名称相近而合并。

旧顶层 `EMBROIDERY`、`PLEATING` 以及概括性的 `SPECIAL_CRAFT` 仍可生成通用 `ProcessTask`；它们不是三种额外的加工单模型，真正执行仍应落到具体辅助/特种工艺加工单。当前旧码和 17 个具体工艺码并存，也是合并任务吸收不完整的重要原因。

### 6.8 盘扣专用加工流（PROD-019）

盘扣虽然使用辅助工艺加工单模型，却有独立的专用流，不能只按普通“裁片→裁片”工艺理解：

- 一张生产单 + 技术包快照 + 盘扣工艺生成一张盘扣任务/加工单；
- 系统汇总该生产单下的捆条加工单；
- 加工前按捆条菲票/批次接收，计量是“张”；
- 加工后按盘扣成品交出，计量是“个”；
- 支持分批接收菲票和分批交出盘扣。

当前限制/冲突：填报加工前要求所有菲票先全部接收，不能真正做到边收边加工；人工完成只要求全部菲票已接收且存在正数产出，不要求全部产出已交出；加工单 `sourceTaskId` 指向自身，不是排程任务 ID。

依据：`src/data/fcs/button-loop-craft-flow.ts:121-294`、`src/data/fcs/special-craft-task-orders.ts:1954-2153`。

### 6.9 辅助/特种工艺加工单的共同生成、明细和执行

#### 6.9.1 来源与生成粒度

生成器从生产单绑定的技术包快照读取：

- 纸样裁片部位的工艺配置；
- 颜色、尺码、每件片数；
- 成衣 BOM/辅料 BOM 关联；
- 成衣或辅料类路线项；
- 菲票、捆条和盘扣关系。

需求行包含生产单、SKU、纸样、部位、颜色、尺码、每件片数、计划片数、工艺、作用对象、菲票、来源 BOM、投入计划量/单位和产出单位，见 `src/data/fcs/special-craft-task-orders.ts:81-122`。

当前代码分组键是：

`生产单 + 管理域 + 工艺 operationId + 作用对象 + WAIT_ASSIGN`

同组所有需求行合并到一张加工单，见 `src/data/fcs/special-craft-task-generation.ts:1157-1195`。分组键本身不含路线节点、裁片分支/部位范围、工厂责任范围或源任务 ID，加工单创建时 `sourceTaskId` 还可以为空。因此准确的**代码现状**是“同生产单、同管理域、同工艺、同作用对象就合并”，绝不能把它提升成正确业务规则。

这里也不能反向武断成“前片和袖片只要部位不同就必须拆成两张单”。同一工厂、同一工艺、同一交接责任的一张加工单可以包含前片、袖片等多条 `demandLines`；当前明细本身仍保存部位。真正缺失的是：每条明细没有自己的 route occurrence、对象分支前后承接和责任工厂身份，而整张单又只能承接一个工厂。后续应先确认业务合单规则；无论最终同单还是拆单，每条明细都必须保留路线节点与部位分支，分给不同责任工厂时必须能拆单，不能仅靠当前宽分组键决定。

当前正式生成来源枚举只有 `PRODUCTION_ORDER`，见 `src/data/fcs/special-craft-task-orders.ts:73-75`。生产单补料和采购/备货来源没有进入同一正式生成器；部分补料加工单是运行时根据既有加工单另行追加，不等于完整来源模型。

#### 6.9.2 加工转换关系

| 项目 | 当前代码现状 |
|---|---|
| 加工前 | 当前代码允许裁片、成衣、捆条或辅料；烫画、直喷两者都必须允许裁片和成衣，并按每个路线 occurrence 明确对象；盘扣/橡筋等转换型辅料另走支线；花朵明确使用指定裁片部位 |
| 需求来源 | 生产单 + 技术包快照 + 纸样/部位/成衣 BOM/辅料 BOM；源生产任务可后补绑定 |
| 加工后 | 大部分同对象同单位；盘扣和橡筋是对象/单位转换 |
| 任务明细 | `demandLines` 很细，但不同对象仍共用大量可选字段 |
| 前置任务项 | 当前没有通用明细级引用；`sourceTaskId` 多为生成/所属任务身份，不能等同于“谁的哪条产出供给本明细” |
| 后置任务项 | 当前没有通用明细级引用；裁片、成衣和辅料转换产物多靠固定仓库去向或专项交接推断 |
| 加工后去向 | 裁片、成衣都应读取后置任务项；盘扣/橡筋等转换产物进中央辅料仓或真实消费节点。当前成衣工艺一律送后道、裁片工艺一律回裁床的固定规则只能作为现状，不能替代本款路线 |

裁片工艺还存在菲票级执行链：

`待交出裁片菲票 → 工艺派出 → 工厂接收 → 加工完成 → 退回裁床 → 裁床接收 → 下一道工艺`

即当前代码不是上一工艺直接交下一工艺，而是强制每一道裁片工艺先回裁床再派下一道。另一个通用执行写回入口却会在交出时直接模拟裁床已接收，两套行为也不一致。

#### 6.9.3 状态与多次数量

加工单状态只有：`待接收 → 加工中 → 已完结`。明细进度能累计：

- 多次接收：不得超过计划未接收数量；
- 多次完工填报：不得超过累计实收未完工数量；
- 多次交出：不得超过累计完工未交出数量。

见 `src/data/fcs/special-craft-task-orders.ts:2587-2619`。

盘扣另有完整动作：确认接收、加工填报、发起交出、人工完成加工单，见 `src/data/fcs/special-craft-task-orders.ts:2450-2585`。

但当前一般成衣专项 Web 动作还存在“必须一次覆盖全部 SKU”的接口，见 `src/data/fcs/special-craft-task-orders.ts:2300-2377`；不同入口对“部分接收/部分完工”的能力并不一致。

#### 6.9.4 生成清理、源任务和人工完成冲突

- 裁片类加工单由生成器先创建，真实菲票要在裁剪完成后才产生；但初始化代码会删除所有尚未绑定 `feiTicketNos` 的裁片类生成加工单。真实加工单可能刚生成就被当作无效记录清掉。
- 加工单自身通常通过人工动作进入“已完结”；但所有子加工单完结后，系统会自动把来源 `ProcessTask` 设为 `DONE`，任一子单重开时又自动改回进行中。
- 工艺加工单自身、通用动作写回和菲票专项流采用不同完成门槛：精确 SKU 数量、任意正数完成、全部菲票返回等口径并不统一。

依据：`src/data/fcs/special-craft-task-orders.ts:2157-2435`、`src/data/fcs/process-action-writeback-service.ts:1154-1302`、`src/data/fcs/cutting/special-craft-fei-ticket-flow.ts:1170-2356`。

| 特种工艺 | 工艺代码 | 当前默认加工前 | 当前默认加工后 | 单位 | 当前去向 |
|---|---|---|---|---|---|
| 模板工序 | `SPECIAL_TEMPLATE_PROCESS` | 裁片 | 已加工裁片 | 片 | 返回裁床链 |

### 6.11 生产阶段相邻的花边辅料加工单（PROD-027）

花边链是独立于 17 种辅助/特种工艺的采购驱动辅料加工域。把它放入 `PROD-027` 是本文为了不遗漏生产相邻加工而做的分类，不代表代码已经把它标为生产阶段：

- 上游采购单必须有效，供应商必须映射到启用花边厂；
- 同一采购单、同一 SKU 至少有一行物料类型为花边；
- SKU、数量、单位、交期、仓库、款式图和默认加工投入必须完整；
- 同 SKU 多行的身份字段和默认投入必须一致；
- 生成键为“采购单 ID + 花边 SKU ID”，同 SKU 多行汇总成一单。

| 项目 | 当前代码现状 |
|---|---|
| 加工前 | 显式 `inputLines`：投入物料/SKU、规格、颜色、图片、单位、单位用量及计划投入量 |
| 需求来源 | 有效 PMS 采购单 + 采购 SKU，不是生产单技术包通用任务 |
| 加工后 | 显式 `processingOutput`：花边 SKU、名称、规格、颜色、图片、计划数量和单位 |
| 任务明细 | 采购 SKU、全部计划投入行、计划产出和采购单位 |
| 加工后去向 | 每次交出由中央辅料仓/WLS 分别确认收货 |

状态为 `待接收 → 加工中 → 已完结`，另有取消。确认投入接收后进入加工中；可调整投入数量但不能改变投入行数；可多次上报完成量、多次交出、逐次收货；必须人工完结，也可撤销完结。差异、凭证和超收二次确认均有记录。它是当前各类加工单中投入/输出身份、多次交接和人工完成建模较完整的一套。

仍有明显边界：

- 没有 `stageCode`、技术包路线节点、通用任务 ID/二维码或 PDA 任务绑定；
- 没有通用前置/后置加工单关系和专用打印模板；
- 采购单同步不检查花边单已经加工中或完结，仍会覆盖计划数量、交期、目标仓、输出量和投入量；
- 采购投影枚举虽写了花边、拉链、织带、布包扣、其他，真正生成只处理含“花边”的分组，当前没有通用其他辅料加工单。

依据：`src/data/fcs/lace-factory-purchase-projection.ts:528-715`、`src/data/fcs/lace-factory-domain.ts:71-150`、`857-925`、`1043-1483`。

## 7. 后道阶段：回货判定、动态处理与全部当前单据

### 7.1 后道的业务性质、字典和流程节点

【业务已确认】后道是普通生产单的成衣回货处理流程，不是一组与染色、裁剪同性质的预排加工转换；KOL 样衣、KOL 小单整单任务不走这条链。普通生产单至少要关联“回货批次、回货登记/实收、本次三方任务范围、到货 QC、最终后道项目、处理结果和后续去向”七类事实；当前主链是据此整理的骨架：

`三方车缝工厂自助回货登记 → 后道确认实收 → 读取本次三方任务范围 → 唯一到货 QC → 按任务范围带出默认项目和可编辑性/确认返厂 → 冻结最终后道项目 → 项目为空则整单直接生成成衣仓交接；项目非空才生成处理单 → 人工确认处理完成 → 当前后续交接链`

扫码回货登记是另一种业务模式：扫码登记过程本身就完成实收，不再增加“确认实收”。但当前原型只有前一种自助登记后确认实收的链，因此本文不能把扫码即实收表述为当前已实现功能。

其中“处理决定”至少要区分：

- 本次只分配车缝：QC 固定勾选开扣眼、装扣子、烫包，不允许修改，因此会生成我方后道处理单；
- 本次分配含烫包：QC 默认不勾选任何项目，但允许现场调整；保持为空时不生成处理单，手动选中后生成处理单；
- 返厂/退回三方是正式业务分支，由到货 QC 对相应 SKU 数量、原因和接收工厂产生并确认；后道处理完成时不应再次产生一套返厂判断；
- 一张处理单的项目集合保存在单头，任务明细按 `SKU × 数量` 保存。这就是当前确认粒度，不要求改成 `SKU × 项目 × 数量`。

因此，普通生产单的后道阶段存在，但处理单只在 QC 最终项目非空时存在。技术包不能固定本批后道项目；真正直接控制 QC 默认值与能否调整的是本次任务分配。KOL 整单不适用上述判断。

【代码事实】后道字典只有三种工序：

- 开扣眼：内部产能节点，不生成独立外部任务；
- 装扣子：内部产能节点，不生成独立外部任务；
- 烫包：外部任务，可分配、接收、填报和交出。

见 `src/data/fcs/process-craft-dict.ts:1024-1065`。

这里还有两个容易被忽略的对象错误：`resolveProcessCraftTargetObject()` 对 `BUTTON_ATTACH` 返回 `ACCESSORY/辅料`，对 `BUTTONHOLE` 没有专门分支，最终兜底为 `CUT_PIECE_PART/裁片部位`，见 `src/data/fcs/process-craft-dict.ts:1277-1313`。装扣子当然会消耗扣子辅料，但现场被加工的主对象是回货成衣；开扣眼处理的也应是本批回货成衣，不是回到生产阶段的一片裁片。“成衣主对象”和“扣子消耗物料”是两条事实。如果字典只展示“作用对象=辅料/裁片”，路线、数量和处理单都会接错对象。开扣眼、装扣子、烫包都应按同一回货成衣批次记录处理数量；装扣子再附带扣子实际领用/消耗。

到货确认、QC、复检和后续交接是当前代码中的后道流程节点，不属于工序字典，见 `src/data/fcs/post-stage-taxonomy.ts:1-30`。其中“复检”是代码现状：当 QC 判定本批无需我方处理时，目标流程已经明确不保留任何复检/扫码点数节点，整单直接形成成衣仓交接；当确有后道处理时，当前代码仍会进入复检，但它不得再形成第二次质量结论，因为整个生产只有到货 QC 这一处质量判断。

但后道执行层并未只使用这套定义，而是并行存在以下模型。

### 7.2 三套后道事实源

| 模型 | 当前主要用途 | QC 后的处理单实体 | 主要问题 |
|---|---|---|---|
| 新后道全流程 | 当前大部分 Web 列表、QC、仓库、复检、出货 | `PostFinishingPostTask` | Mock 场景强约束、只允许部分环节一次性交接 |
| 旧后道域 | 通用 PDA、通用交接、详情回退和部分写回 | `PostFinishingWorkOrder` | 与新模型不共享状态，仍有旧接单和旧完成动作 |
| 静态后道路由 + 通用回货 QC | 路线展示、跨工序回货质检 | 无统一真加工单 | 与新旧后道域均非同一事实源 |

【核查判断】当前页面看似已经形成完整后道闭环，实际上同一生产单可能在三套模型中出现不同的后道项目、状态和数量。新全流程中“仅车缝固定三项、含烫包默认空且可改”是已确认最新规则；静态 `PostProcessRoute` 无条件给缺省项目补三项才是应淘汰的旧默认，二者不能混为一谈。

新、旧两套后道处理单的数据结构和页面解释都倾向于把“QC 合格成衣”当作后道加工投入、把“处理后成衣”当作加工产出。业务上这两个对象仍是同一批成衣；真正发生变化的是处理决定、待执行项目、已处理数量和去向，而不是物料身份发生了新的转换。静态 `PostProcessRoute` 只有节点和状态，没有实际投入/产出实体，不能把同一批评泛化到它。

### 7.3 独立烫包运行时任务（POST-001）

技术包可直接包含 `IRON_PACK`，并生成独立 `ProcessTask`；它也可以作为两类固定合并任务的源任务。代码把它抽象成“成衣加工为成衣”的整单任务，但它不是后道专区由 QC 生成的后道处理单。

所以当前至少存在两个“烫包”概念：

1. 生产任务层的独立烫包责任；
2. 回货 QC 后，后道加工单内的烫包项目。

两者没有唯一互斥或承接关系。

【业务已确认】生产任务层保存“三方本次是否承接烫包”，并直接决定 QC 表单规则：只分配车缝时固定带出我方三项后道项目；含烫包时默认空、允许质检员调整。任务范围不是三方已经实际完成的证明，但不应再被弱化成只读提示。

### 7.4 新全流程后道处理单（当前页面称“后道加工单”，POST-002）

#### 7.4.1 本次任务范围决定 QC 默认值和可编辑性

新模型只演示三种任务范围：仅车缝、车缝+烫包、裁剪+车缝+烫包。

- 仅车缝：系统固定包含开扣眼、装扣子、烫包；质检员不可改。当前源码字面值仍是“熨烫和包装”，属于待统一的旧展示名。
- 车缝＋烫包、裁剪＋车缝＋烫包：系统默认项目为空；质检员可以手动勾选或调整实际仍需我方处理的项目。

见 `src/data/fcs/post-finishing-full-flow.ts:75-122`。

这不是“具体项目全部由 QC 无约束判断”。准确规则是：任务类型先确定默认值和编辑权限，QC 再在允许编辑的情形下作现场调整，并在提交时冻结最终项目。

#### 7.4.2 回货、确认和 QC

当前实现对应“三方车缝工厂自助回货登记后，后道人员另行确认实收”。一张生产单可以按 `returnIndex` 登记第 1～5 次回货，每次：

- 必须包含生产单全部 SKU；
- 每个 SKU 必须是正整数；
- 必须由工厂/送货人员操作；
- 必须有送货人和现场凭证图；
- 自动创建送货单和一条初始不可用的后道待加工仓记录。

见 `src/data/fcs/post-finishing-full-flow.ts:1580-1685`。它是固定五个批次槽，不是无限次、任意部分 SKU 交出。

自助登记本身不等于后道实收。后道最终确认逐 SKU 点数；超过 5% 差异要求二次点数和授权。确认后自动创建该回货批次唯一 QC，见 `src/data/fcs/post-finishing-full-flow.ts:1739-1883`。因此当前代码已经落实第一种模式，但没有“扫码登记时同时确认实收”的第二种入口。

QC 状态为：`待送检 → 待质检 → 质检中 → 质检完成`。逐 SKU 保存合格、瑕疵、返厂数量、返厂原因和接收工厂。该返厂/退回三方分支已经得到业务确认，产生和确认点就是到货 QC；这部分当前方向成立。QC 完成后：

- 有后道项目：自动生成一张后道加工单；
- 无后道项目：当前代码直接生成复检单，但目标必须改为不生成复检、不再扫码/点数，按整单直接生成对接成衣仓的交接。

接口虽然有 `needPostFinishing`，实现实际只看最终项目数组是否为空；仅车缝时忽略前端选择并强制三项，含烫包时采用质检员选择；项目为空便直接创建复检单，见 `src/data/fcs/post-finishing-full-flow.ts:2281-2435`。因此要把结论拆开：默认/可编辑规则和 QC 返厂分支符合已确认业务；无项目分支的后续路由不符合，且整套新链尚未成为所有普通生产单唯一入口。

#### 7.4.3 当前处理单粒度与正确业务解释

一张 QC 最多生成一张后道处理单。开扣眼、装扣子、烫包不会拆成三张单；项目集合放在单头，明细只按 `SKU × 数量` 保存应处理件数。这一粒度与本轮业务确认一致，不再把缺少项目级数量列为产品缺口。

| 当前代码字段/事实 | 正确业务解释 | 当前缺口 |
|---|---|---|
| QC 对应的送货单 | 上游回货批次 | 只允许第 1～5 次且每次必须全 SKU 正数，不符合任意分批回货 |
| 任务范围类型 | 三方本次被分配的整单任务范围，同时决定到货 QC 的项目默认值和可编辑性 | 新模型的规则与本轮确认一致；缺口不是这条规则本身，而是它只绑定三张独立 Mock，尚未从所有普通生产单的有效任务分配统一派生 |
| QC 合格成衣 SKU、件数 | 本批待处理成衣及数量 | 不应命名为新的“加工前对象” |
| `任务后道/质检补加工` 来源类型 | 处理单触发类别 | 仅车缝产生“任务后道”，含烫包任务在 QC 手工勾选后产生“质检补加工”；具体项目保存在 `processItems`，但这套来源只存在于新 Mock 链，尚未成为全项目唯一事实 |
| 单头项目数组 | 本批动态处理项目集合 | 当前源码项目名仍使用“熨烫和包装”，需统一为“烫包” |
| SKU 应加工件数 | 已确认的 `SKU × 数量` 处理明细 | 粒度本身成立；不得因为旧域更细就强制拆成项目级数量 |
| 完成时的合格/瑕疵/返厂数量 | 代码中的第二次质量结果 | 与“质量和返厂只在到货 QC 产生、确认”的业务口径冲突 |
| 自动创建复检单 | 当前代码后续节点 | 无项目分支必须删除该节点并整单直达成衣仓交接；有实际处理的分支仍需确保复检不再重复判质量 |

所以，这张单据从业务上更适合统一叫“后道处理单”；“后道补做单”只适用于三方责任未完成的一个分支，不宜作为所有处理单的名称，也不宜继续用与染色、裁剪同构的投入/产出加工单来解释。

同一批需要多个后道项目时，它们的先后属于 QC/后道处理模块内部执行顺序，与技术包工艺路线无关。当前 `processItems` 是单头集合，开始/完工按整单和 SKU 行提交；本文只把这一现状与技术包路线隔离，不把“项目级串并行编辑器”擅自扩成工艺路线需求，也不改变已确认的 `SKU × 数量` 明细。依据：`src/data/fcs/post-finishing-full-flow.ts:88-104`、`2352-2417`、`2753-2813`。

状态为：`待后道 → 后道中 → 后道完成`。开始需要人工扫码/点击；完成需要人工提交，完整逻辑见 `src/data/fcs/post-finishing-full-flow.ts:2714-2873`。

当前问题：

- 后道完成时再次录入合格、瑕疵、返厂，等于在唯一 QC 后又做质量和返厂判断；目标应只读取 QC 已确认的返厂结果，处理完成节点不得新增或改写返厂；
- 完成数量可以小于应加工数量，但整单仍直接完成并创建复检，余量没有继续加工载体；
- 辅料未入库只提示，不阻止开始；
- 不存在“确认接收即自动开工”，只有单独开始动作。

### 7.5 旧域后道处理单（当前页面称“后道加工单”，POST-003）

旧域仍然被通用 PDA、交接和详情回退使用，并不是完全无效的历史代码。

#### 7.5.1 上游与 QC

旧域能接收：

- 车缝厂成衣；
- 整件毛织成衣；
- 成衣类特殊工艺产出。

它能按部分 SKU/部分数量创建后道待加工库存，并从库存多次抽取数量生成多张 QC。但待质检范围又被硬编码限制在三张 Mock 生产单上。

旧域 QC 是逐 SKU 判断开扣眼、装扣子、烫包及数量，装扣子还区分人工/机器；只要需要开扣眼或装扣子，又会强制追加烫包，见 `src/data/fcs/post-finishing-domain.ts:87-130`、`1100-1127`、`1392`。

#### 7.5.2 旧处理单粒度与正确业务解释

旧域也是“一张 QC 最多一张后道处理单”，内部明细为 `SKU × 后道项目`，比新模型更接近动态处理需要，但仍不应该解释为成衣物料的前后转换。

| 当前事实 | 正确业务解释 | 当前缺口 |
|---|---|---|
| QC 判定需要相应项目的成衣 SKU 数量 | 到货质检产生的待处理数量 | 基本方向合理 |
| 旧域 QC 逐 SKU 后道判断 | 动态处理触发依据 | 又用代码规则强制追加烫包，现场判断不完全自由 |
| `SKU × 开扣眼/装扣子/烫包` | 后道处理明细 | 比新模型细，但没有与回货批次和本次三方任务范围统一的主键 |
| 每项目完成数量 | 人工处理结果 | 通用整单入口可直接自动补足计划数量，削弱人工事实 |
| 同一成衣 SKU | 原成衣在处理后的状态 | 没必要新建“加工后 SKU” |
| 全部项目完成后生成复检单 | 当前代码后续节点 | 仍有重复质量判断风险 |

见 `src/data/fcs/post-finishing-domain.ts:2397-2553`。

旧域同时存在逐项目完成和“通用整单完成”入口；后者会直接把全部项目完成数量补到计划数量，见 `src/data/fcs/post-finishing-domain.ts:3604-3650`。

旧域另有生产单级后道任务的接单/拒单；接单不会自动开始，见 `src/data/fcs/post-finishing-domain.ts:1022-1084`。

### 7.6 三方工厂内后道任务（POST-004）

`SewingFactoryPostTask` 表示旧模型中车缝厂内部继续做后道，或将成衣交我方后道。它不等于回货 QC 后生成的后道处理单，也不能被当作权威“本次计划执行/责任分配”。

它当前只是从旧域静态 `SOURCE_CONTEXTS` 和既有后道单反向派生的 Mock 上游状态对象：`needFactoryPostFinishing` 由是否已经存在旧后道处理单推导，状态又按数组序号预设；开始、完成、转交只修改自身状态。它没有 PPIC 分配快照，也不保存开扣眼、装扣子、烫包的具体责任项目。因此它最多是旧演示链的状态投影，不能作为到货 QC 的责任对照源。真正可表达责任快照的是新模型的 `PostFinishingResponsibilitySnapshot`，但它目前也只覆盖三类 Mock 任务范围。

当前固定合并任务、新后道责任快照和旧后道任务都在描述“谁负责后道”，但只有新模型明确实现了本轮确认的默认/可编辑规则。并行结果是：

- 技术包路线可能已有烫包任务；
- 三方合并任务可能宣称已承接三项；
- 新后道 QC 按任务类型形成固定项目或可调整项目；
- 旧后道 QC 又可逐 SKU 生成三项明细。

这些判断没有统一到同一张生产单的有效任务分配；其中旧 `SewingFactoryPostTask` 甚至不是可靠责任事实。清理时应保留新责任规则的业务含义，将其接到正式任务分配和正式回货批次，再删除旧状态投影与静态默认，而不是把新规则也一并推翻。

### 7.7 开扣眼、装扣子在动态处理明细中的位置（POST-005、POST-006）

它们在工序字典里是后道内部产能节点，不生成外部任务、二维码和交接单。因此当前没有“开扣眼加工单”和“装扣子加工单”。它们只可能：

- 被合并任务责任文字吸收；
- 作为新后道加工单单头项目；
- 作为旧后道加工单的项目明细。

字典的作用对象还存在不准确：装扣子被映射为“辅料”，开扣眼落入默认“裁片部位”；实际后道加工单处理的是成衣，见 `src/data/fcs/process-craft-dict.ts:1277-1313`。

旧字典还把“布包扣”直接映射到 `BUTTON_ATTACH`，见 `src/data/fcs/process-craft-dict.ts:1147-1152`。业务已经确认，“布包扣”指**制作包布钮辅件**，不是把扣子安装到成衣。因此它应是生产阶段的辅件制作支线：输入为本次制作所需的材料/半成品，输出为布包扣辅件；具体投入字段和规格应由后续专门方案定义，本文不凭名称虚构。旧 `BUTTON_ATTACH` 映射会把辅件制作错画成后道成衣装扣，必须连同旧选项、文案和测试删除。

同一个后道项目在代码中还有两种名称：字典、旧后道域和合并任务主要称“烫包”，新全流程称“熨烫和包装”。新模型会把输入的“烫包”归一化为“熨烫和包装”，见 `src/data/fcs/post-finishing-full-flow.ts:738-742`。业务名称现已确定统一为**烫包**；“熨烫和包装”只作为当前代码冲突的引用，不应继续作为页面选项、存储新值或兼容后的权威名。

【业务已确认】开扣眼、装扣子、烫包不需要为了与准备、生产阶段对齐而各自生成一张独立加工单。一张回货批次经 QC 判定后只生成一张后道处理单：单头保存项目集合，明细维持 `成衣 SKU × 数量`。班组级或项目级执行记录不在本轮确认范围内，不能据此改写处理单粒度。

### 7.8 当前“复检、出货和接收”与目标后续去向（POST-012～POST-015，关联 POST-007）

新模型后道完工后自动创建复检单；复检逐 SKU 扫正确条码并人工提交合格/瑕疵数量。至少一件合格后，系统自动创建唯一出货单和后道待交出仓记录，见 `src/data/fcs/post-finishing-full-flow.ts:3183-3260`。

新模型成衣仓接收是一次性的：整张出货单提交全部 SKU 实收后，出货单、待交出仓和原回货送货单被一次性推进完成；再次调用只返回原记录，见 `src/data/fcs/post-finishing-full-flow.ts:3256-3340`。

旧域则支持按 SKU 多次后道交出，并逐次记录接收方实收，见 `src/data/fcs/post-finishing-domain.ts:3900-4009`、`5184-5249`。两套能力不共享状态。

旧域的“多次”还存在两项不能忽略的实现风险：通用 PDA 发起后道交出时没有按用户明确选择的 SKU 定位明细，而是取第一条库存足够的记录，可能把交出数量记到错误 SKU；随后这条记录会继续持久化并回写旧后道域。复检完成后，旧域一边生成自己的待交出仓，`process-execution-writeback.ts` 又会生成通用仓库投影，形成并行仓库事实。

出货也不只有新全流程 `PostFinishingOutboundOrder`：`post-finishing-outbound-orders.ts` 另有一套旧域 localStorage 出货实体。后道出货、待交出仓和接收因此同样不是唯一事实源。

【业务已确认/核查判断】这些对象都不应被包装成新的加工单。目标必须按两条路径拆开：

1. QC 最终项目为空：不生成后道处理单，也不生成复检/扫码点数动作；系统按整单直接创建对接成衣仓的数量交接，随后由成衣仓完成正常接收和责任转移。
2. QC 最终项目非空：生成一张后道处理单；当前原型后续仍经过复检、出货、待交出仓和成衣仓接收。这里可以保留后续交接结构，但复检不得再次生成合格/瑕疵/返厂等第二套质量事实。

所以当前 `无项目 → 自动复检` 是明确待改代码，不再是待确认问题；出货、待交出仓和成衣仓接收只负责数量与责任转移。

### 7.9 后道辅料调拨单（POST-017）

后道辅料调拨单不是加工单，但影响后道可加工物料：

- 只是新模型中第一张“仅车缝、我方后道负责”Mock 生产单的单个演示种子；列表首次读取时即初始化，不是由本次 QC 判定实时生成；
- 只筛吊牌、吊粒、扣、扣子等后道专用辅料；
- 按成衣计划量 × 单耗计算；
- 状态为申请调拨、待调拨、待入库、已入库；申请、审核、备妥三段是预置历史，当前可操作动作只有整单入库；
- 当前不允许分批入库；
- 合并任务被标记不适用；
- 辅料未入库不会阻止后道加工单开始。

见 `src/data/fcs/post-finishing-full-flow.ts:1050-1168` 和 `src/pages/process-factory/post-finishing/material-transfers.ts:40`。

【核查判断】仅车缝任务在分配时已经确定我方后道固定执行三项，因此相关后道辅料可以在 QC 之前备货，不必等待现场再次选择；含烫包任务默认由三方完成，则不应预生成我方后道辅料调拨。当前种子方向与这条规则基本一致，但它只是首张 Mock 的初始化数据，不是由正式生产单任务分配幂等生成，也没有覆盖后续任务变更、追加调拨和真实分批入库。

### 7.10 静态后道路由和通用回货质检

第三套静态后道路由把流程写为：

`到货确认 → QC → 开扣眼/装扣子/烫包 → 复检 → 后续交接`

并区分三方完成后道或我方后道执行。缺少具体项目时会默认补齐三项；要求后道但项目为空时至少默认烫包，见 `src/data/fcs/post-process-route.ts:200-241`。

另一个通用回货 QC 链还覆盖印花、染色、裁片和车缝回货质检，见 `src/data/fcs/return-inbound-workflow.ts:120-274`。这与已确认的“整个生产只有成衣回到后道工厂时才质检”直接冲突。

此外，`process-work-order-quality-settlement.ts` 会对任何已完成仓库实收且带加工单身份的交出批次创建“加工单质检记录”，要求整批一次质检并按合格量生成结算流水。这一通用质检/结算链同样没有限定“只有成衣回后道”，会把准备、裁片或特殊工艺加工单的仓库实收也纳入质量事实。见 `src/data/fcs/process-work-order-quality-settlement.ts:1-239`。

### 7.11 后道当前事实与正确业务框架的对应结论

| 后道业务维度 | 当前代码能否表达 | 当前主要事实源 | 关键问题 |
|---|---|---|---|
| 回货批次 | 能，但新旧规则不同 | 新送货单、旧待加工仓、PDA 交接 | 新模型最多五次且强制全 SKU；旧域可部分接收 |
| 本次分配给三方的任务范围 | 新模型局部能，旧模型弱 | 新 `PostFinishingResponsibilitySnapshot`、合并任务定义/覆盖；旧 `SewingFactoryPostTask` 只是 Mock 状态投影 | 新模型已正确驱动项目默认值和可编辑性，但只覆盖三张 Mock，尚未由全部普通生产单的有效任务分配统一生成 |
| 回货数量/时效责任 | 局部能 | 最终回货确认版本、有效任务分配、回货履约投影 | 与“谁负责开扣眼/烫包”是另一种责任，当前页面容易混称 |
| 到货质检判定 | 能，但有多套 QC | 新/旧后道 QC、通用回货 QC、加工单 QC | 质检范围和次数冲突 |
| 动态处理明细 | 能表达已确认粒度 | 新模型单头项目 + `SKU × 数量`；旧模型另有 `SKU × 项目` | 新模型粒度符合本轮确认；旧模型更细不是保留理由，其强制追加规则和独立主键应随旧域清理 |
| 无需处理 | 当前能走无项目分支，但去向错误 | QC 完成逻辑 | 当前仍自动转复检；目标已确认是不复检、不扫码点数，整单直接生成成衣仓交接 |
| 处理结果 | 能，但混入第二次质量判断 | 新旧后道完工入口 | 不足量可整单完成，人工事实不统一 |
| 后续去向 | 能，但新旧交接规则不同 | 复检、出货、待交出仓、成衣仓及通用仓库投影 | 新模型一次性；旧域可多次但 PDA 可能串 SKU，且旧/通用仓库、两套出货实体并存 |

【核查判断】后道需要统一的是“同一回货批次的三方任务范围、到货 QC 最终项目和动态处理结果”，不是把开扣眼、装扣子、烫包重新固化成每款必经的技术包加工节点，也不是为同一成衣虚构加工前、加工后两个物料身份。

## 8. 全阶段两类业务模型与执行能力对照

### 8.1 准备、生产阶段的加工转换关系

下表只比较确实存在加工对象转换或加工状态变化的准备、生产阶段。这里需要把工艺路线与需求来源、实际投入、实际产出、任务明细和产出去向一起设计。

| 加工单/任务 | 实际投入是否明确 | 需求来源是否明确 | 实际产出是否明确 | 明细能否承接 | 是否有显式前/后置任务项 |
|---|---|---|---|---|---|
| 水溶 | 代码只标成抽象 BOM 物料；具体类别和批次不统一 | 生产单+BOM 明确 | 同一 BOM 物料的处理后状态，但身份弱 | 否 | 否 |
| 染色 | 代码强制写成面料，无法正确保留纱线、花边等合法对象；批次局部存在 | 三类来源明确 | 业务上应为同一 BOM 物料的染后状态；代码多按染后面料处理 | 否 | 否 |
| 印花 | 正式生成入口和独立工厂端模型以面料为主/限定面料；通用类型及交出入口又可产生错误裁片事实，均不能完整表示适用辅料 | 正式三类来源明确 | 业务上应为同一 BOM 原物料的印后状态；不存在应生成的已裁衣片印花，残留类型和单位回退必须清理 | 正式逐路线 occurrence、物料分支/花型明细不足 | 否 |
| 裁片单 | 面料和纸样较明确 | 正式来源为独立裁剪或裁剪合并任务；补裁/补料是旁路 | 裁片+菲票较明确 | 裁床内部较强 | 跨域否 |
| 捆条 | 面料明确 | 纸样捆条配置较明确 | 捆条明确 | 专项域较强 | 跨域否 |
| 毛织 | 纱线和类型明确 | 生产单+技术包明确 | 成衣/部位 SKU 明确 | 专项域较强 | 跨域否 |
| 车缝 | 一般链能证明多类裁片；辅料只在特定合并域、毛织部位尚未贯通 | 任务明确 | 成衣明确 | 多套配料/责任投影，没有统一工单明细承接 | 否 |
| 辅助/特种 | 作用对象和 `demandLines` 较明确 | 生产单来源明确 | 多数明确，转换型局部明确 | 专项域内较强 | 跨域否 |
| 花边 | 辅料来源较明确 | 采购需求明确 | 花边辅料明确 | 专项域内 | 否 |

这张表没有放后道。后道前后通常仍是同一批成衣，不能因为系统表结构需要统一，就人为制造“处理前 SKU”和“处理后 SKU”。

### 8.2 后道动态处理关系

| 后道维度 | 新全流程模型 | 旧后道域 | 已确认边界/分析建议 |
|---|---|---|---|
| 回货批次 | 最多第 1～5 次，每次全 SKU 正数 | 可按部分 SKU/数量接收和多次抽取 | 应允许真实的多次回货、部分 SKU、部分数量 |
| 回货登记与实收 | 三方自助登记后，后道人员逐 SKU 确认实收 | 旧域另有多套接收动作 | 当前业务按“自助登记与确认实收分开”执行；扫码登记即实收是另一种模式，但当前尚未实现 |
| 计划执行/责任范围 | 由三种 Mock 任务范围预设，并正确决定默认项目和是否可改 | 来源上下文和三方后道任务只是静态/反向状态投影，未形成覆盖全部来源的权威分配事实 | 应由普通生产单的有效任务分配生成唯一快照；它决定 QC 初始状态，但不等于另一张独立后道路由 |
| 到货质检 | 每批最终确认后自动建唯一 QC，并可记录返厂数量、原因和接收工厂 | 从待加工库存选量建 QC | 这是整个生产唯一质量判断及返厂产生/确认点 |
| 动态处理项目 | 仅车缝固定三项且不可改；含烫包默认空且可调整 | 逐 SKU 选择三项和数量，并可能强制追加烫包 | 新模型的默认/可编辑规则已确认；项目集合放在单头，不采纳旧域的逐 SKU 项目粒度 |
| 是否生成处理单 | 项目非空才生成 | 项目非空才生成 | 普通生产单进入后道回货处理，但处理单不一定有；KOL 整单不进入普通后道 |
| 处理明细 | 单头项目集合 + `SKU × 数量` | `SKU × 项目 × 数量` | 新模型粒度即确认口径；旧模型的项目级数量不进入目标主模型 |
| 处理结果 | 再填合格/瑕疵/返厂 | 项目完成量，可被整单入口补足 | 只记录已处理、未处理和人工完成事实；返厂已经在 QC 确认，处理完成不得再产生 |
| 后续去向 | 无项目或处理完成后都自动复检，再出货、一次性成衣仓接收 | 复检后可多次交出/接收 | 无项目时明确跳过复检并整单直达成衣仓交接；有处理时可沿当前交接链，但不得二次质检 |

### 8.3 接收、开工、交出和完成能力对照

| 对象 | 当前接收/开工 | 多次交出/接收 | 当前完成方式 |
|---|---|---|---|
| 独立水溶 | PDA 接单、原料到位、开始水溶分开 | 明确不支持部分交出 | 收货一致或差异确认后自动 `DONE` |
| 正式染色 | PDA 接单与工艺启动分开 | 交出参数可填部分，但状态仅允许成功交一次 | 加工单与关联移动任务推进混杂 |
| 正式印花 | PDA 接单与花型/打印启动分开；部分入口未统一校验接单 | 同染色，状态实际只允许一次 | 足量收货自动完成关联移动任务 |
| 工厂端另一套印花 | 多次投入接收，首次接收自动开工 | 支持多次交出和收货 | 独立演示域口径 |
| 裁片单 | 裁床事件账记录开工、铺布、裁剪 | 通过铺布/产出/菲票/袋分批 | 裁片域事件与通用任务完成未统一 |
| 捆条 | 支持多次接收和加工填报 | 支持多次交出 | 任意正数产出即可人工完成 |
| 毛织 | 任务预先自动接单；加工单再接收纱线 | 支持多次接收、填报、交出、下游确认 | 任意正数交出即可人工完成 |
| 辅助/特种 | 专项域可按明细接收；部分 Web 接口要求全 SKU | 明细账支持累计，多入口规则不一 | 加工单人工完结，但源任务自动完成 |
| 花边 | 确认全部投入后进入加工中 | 支持多次填报、交出和 WLS 收货 | 任意正数完成量即可人工完结，可撤销 |
| 车缝 | 分配时提前自动接收；实际裁片交出未统一开工；PDA 仍人工开始 | 通用交接可分批，未统一到车缝工单 | 无统一独立车缝加工单完成规则 |
| 车缝+烫包合并任务 | 整单责任，但 PDA 仍有人工开始入口 | PDA 可交出；与后道回货链未统一 | 当前是可执行生产任务，不只是责任快照 |
| 裁剪+车缝+烫包合并任务 | 定义称整单，PDA 页面又要求完整 SKU，模型与页面粒度矛盾 | PDA 可交出；专用物料交接可分批 | 当前是可执行生产任务；中央专项单会被部分抑制 |
| KOL 整单任务 | 自动接收；首次实际领料自动开工 | 支持累计多次交出 | 累计交出达到任务量后仍由人工完成 |
| 新后道动态处理 | QC 有项目才建单，之后仍需单独人工开始 | 回货最多五次且每批全 SKU；最终成衣仓接收一次性 | 可不足量人工完成并自动建复检 |
| 旧后道动态处理 | QC 有项目才建单；另有独立接单/拒单，接单不自动开始 | 支持按 SKU 多次交出/接收 | 逐项目完成与整单自动补足入口并存 |

因此不能给全系统一句“现在已经支持部分交出”或“现在都必须人工完成”的结论；必须具体到是哪一套准备/生产加工单，或哪一套后道回货与动态处理模型，以及哪个动作入口。

### 8.4 准备、生产承接为什么必须与路线一起讨论

假设同一款有前片、后片、袖片：

- 前片需要绣花再烫钻；
- 后片只要压褶；
- 袖片无辅助工艺；
- 三类裁片最后一起交车缝。

当前路线只能画成“绣花与压褶并行，然后烫钻，然后车缝”，但不能准确表达：

- 烫钻只消费前片绣花产出，不应等待后片压褶；
- 后片压褶产出和袖片原始裁片直接去车缝；
- 前片可分三次从绣花交出、烫钻分三次接收并自动开工；
- 三方车缝的系统开工不是由路线图判断裁片是否齐套，而是裁床交出后自动接收/开工；
- 每次交出数量如何在三张加工单间守恒。

所以准备、生产阶段至少要把“路线节点的对象类型”与“生产单执行时的实际加工单明细承接”连起来；当前代码尚未做到。

普通生产单的成衣形成并回货后，建模方式应发生切换：款式工艺路线只把生产结果送入“后道阶段”，任务分配先确定 QC 的项目默认值和可编辑性，QC 提交再冻结本批最终项目。它不继续沿用裁片分支的投入/产出边，也不能因为技术包上曾出现烫包就额外生成一套静态后道项目。KOL 整单走自身交付闭环，不进入这条普通后道链。

### 8.5 准备、生产原料替换在当前模型中的影响

【业务已确认】生产单通常替换面料、纱线等原料，不替换半成品；不希望为一次生产单换料去修改技术包、重绑版本并重建所有下游单据。

【代码事实】当前不同加工单处理方式并不一致：

- 正式染色/印花把技术包版本、BOM 行集合和原料编码写进生成键/快照；未执行单可以由生产变更同步，已执行或已加入合并染色的单据则保留原快照并记录影响，见 `src/data/fcs/production-process-work-order-service.ts:95-156`、`180-226` 和 `src/data/fcs/production-order-change-workflow.ts:780-865`。
- 水溶直接按生产单+BOM 行生成，没有稳定“逻辑原料槽位”，见 `src/data/fcs/water-soluble-task-domain.ts:289-363`。
- 裁片、毛织和特殊工艺单广泛保存技术包快照 ID、BOM ID、纸样 ID 和物料编码；跨域没有统一替换映射，见 `src/data/fcs/cutting/generated-cut-orders.ts:411-574`、`src/data/fcs/wool-domain/tech-pack-source.ts:103-154`、`320-360` 和 `src/data/fcs/special-craft-task-orders.ts:742-928`。
- “裁剪+车缝+烫包”合并任务还会把当时技术包快照中的全部面料、辅料 BOM 行复制成三方物料需求明细；这是执行时冻结的具体物料事实，不是可在路线层长期复用的逻辑物料槽位，见 `src/data/fcs/sewing-material-handover.ts:85-125`。
- 另一套工厂端印花模型允许在加工前替换实际投入、记录新旧 SKU 和原因，但该能力未接入平台正式印花单，见 `src/data/fcs/printing-work-order-business.ts:570-635`。
- 花边采购同步方向相反：即使已经开工或完结，仍可能被上游采购变化覆盖计划、目标仓、产出和投入，见 `src/data/fcs/lace-factory-domain.ts:857-925`。

所以当前既没有“技术包只限制对象类型、生产单绑定实际原料”的统一能力，也没有一套一致的变更保护规则。路线若直接把具体物料 SKU 当成永久边条件，确实会把后续换料限制死；但当前代码尚未提供逻辑槽位来替代它。

### 8.6 Web、PDA 和打印覆盖并不一致

| 对象 | Web | PDA | 打印 |
|---|---|---|---|

## 9. 按典型款式理解当前路线

这里不能把“每个款”理解为所有款都执行同一串工序。款式工艺路线由技术包 BOM、物料与纸样关系、毛织类别、裁片部位工艺和产品结构决定；生产任务分配只决定该生产单由谁、以独立任务还是合并任务承接执行，不能反过来改写款式需要哪些工艺或对象先后。尤其不能把“款式需要染色、印花”理解成款式级的一条工序清单：必须先回答**哪一条 BOM 物料需要哪些工艺、按什么顺序走**。以下路线用于解释已确认业务方向，并逐项标出当前代码断点；不能把这些理想链整体当成已经实现。

目标上，普通生产单形成的车缝成衣、整件毛织成衣以及合法的成衣烫画/直喷产出，都应按实际任务后置关系进入同一类后道动态链；KOL 样衣、KOL 小单的整单任务明确除外。当前新全流程只覆盖三张车缝 Mock 生产单，尚未统一接入这些正式生产来源：

`三方自助回货登记 → 后道确认实收 → 读取本次三方任务范围 → 到货 QC 应用默认/可编辑规则并确认返厂 → [最终项目为空：不复检、整单直达成衣仓交接 / 项目非空：生成一张动态处理单并人工完成] → 对应数量交接`

这里的方括号表示 QC 后的业务分支，不是技术包预排的固定工序。若未来启用扫码回货登记，扫码过程直接完成实收，用它替代前两个节点；当前原型只有上面的自助登记后确认实收模式。下面简称“统一后道动态链”。

### 9.1 含多物料分支的普通梭织款

当前可表达的理想化主链是：

`各 BOM 原物料按各自准备路线并行加工 → 分别进入裁剪、毛织或辅料使用节点 → 裁片/毛织片/辅料半成品在真实消费节点汇合 → 车缝 → 成衣 → 统一后道动态链`

同一款可以同时存在下列互不相同的分支，以下只用于说明数据结构，不构成默认顺序：

| BOM 物料分支示例 | 该分支需要的准备工艺 | 该分支后续去向 |
|---|---|---|
| A 面料 | 染色 → 印花 | 裁剪 → 对应纸样裁片 |
| B 配布 | 印花 → 染色（仅用于说明可有不同顺序，以该 BOM 确认为准） | 裁剪 → 对应纸样裁片 |
| C 里料 | 仅染色 | 裁剪 → 对应纸样裁片 |
| D 面料 | 无准备工艺 | 直接裁剪 |
| E 纱线 | 染色 | 毛织 → 毛织片或整件毛织成衣 |
| F 花边 | 染色；若该具体花边另有印花需求，则按其自身路线配置 | 辅料仓/车缝中的实际花边使用节点 |

关键不是预设上述顺序，而是每条路线节点必须同时保留：`routeNodeId（本次出现） + sourceBomItemId（哪条物料） + processCode（做什么） + 前后边（该物料怎样走）`。其中 `processCode` 只是节点类型，不能作为节点唯一身份。

但当前代码实际会跨越多个不统一模型：准备加工单不会成为裁片单的显式前置；裁片专项加工单不会成为车缝任务的逐明细投入；后道又有三套模型。

还要把“同一款”“同一种物料大类”和“同一条 BOM 物料”分清：同为面料的 A、B 可以有不同工艺集合和顺序，面料与纱线/花边等辅料更不能共用一条顺序。即使两款衣服都包含染色和印花，也不能复用全局顺序；即使同一款的多条 BOM 都包含染色，也不能因此合并成同一个路线节点。若工艺师确认某条物料分支是印花后再染色，系统应允许显式编排；这不等于系统默认所有印花和染色都可任意互换。当前代码一方面对共享 BOM 强制染色早于印花，另一方面每个 `processCode` 只保留一个自动节点并聚合所有命中 BOM；正式快照又按工序码继续合并。因此，同款不同物料的工艺集合、顺序、加工单位和执行加工单都无法被完整区分。

### 9.2 裁片图案加工款：裁片烫画/直喷

【业务已确认】这里没有“裁片印花”。正确业务链应按具体裁片分别表达，例如：

`面料 → 裁剪 → 前片菲票 → 烫画或直喷 → 前片回裁床待交出仓`

同款其他裁片可以走不同分支：

`袖片 → 绣花 → 回裁床待交出仓`

`后片 → 无辅助工艺 → 直接进入裁床待交出仓`

最终才是：

`各裁片/毛织部位按实际交出汇入三方车缝 → 成衣 → 统一后道动态链`

当前字典中直喷最终对象为裁片，能够从纸样裁片部位生成需求；烫画却被限定为成衣且不能在纸样部位选择，所以同一套裁片路线对直喷可表达、对烫画不可表达。印花域中的 `isPiecePrinting` 等字段不能用于补这个缺口，必须清理概念后由烫画专项工艺自身承接。

### 9.3 成衣图案加工款：成衣烫画/直喷

【业务已确认】少量款式会在成衣状态执行烫画或直喷，这不是裁片工艺的错误数据，而是同名工艺的另一种合法对象变体。技术包中的来源必须是具体成衣 BOM 行，其路线可表达为：

`成衣 BOM 对应投入，或前一道成衣节点产出 → 成衣烫画/直喷加工单 → 已加工成衣 → 本款后置成衣节点`

若这是普通生产单的最后一道生产加工，后置节点可以是成衣回货/后道；若后面还有另一道成衣工艺，则先交给该后置加工单。技术包只限制输入/输出对象类型为成衣和来源 BOM，不锁定生产单实际替换后的成衣 SKU、批次或数量。

当前 BOM 在物料类型选择“成衣”后，会清空并隐藏水溶、染色、印花字段，却没有在该 BOM 行提供烫画、直喷选择，仍显示一组不合适的通用“使用工序”；现有成衣烫画主要只能通过另一套工艺编辑器间接关联。目标入口应收口为：成衣 BOM 行只显示“烫画、直喷”，允许按该款实际需要选择其一或两者；每个选择分别形成绑定该 BOM 的路线 occurrence。当前字典、专项 operation 默认值和测试对烫画/直喷的单一对象结论彼此冲突，也尚不能同时保留裁片与成衣两个合法变体。

### 9.4 纯整件毛织款（或同款中的整件毛织成衣分支）

业务已确认路线是：

`纱线 → 整件毛织加工单 → 成衣 → 统一后道动态链`

旧后道域能识别整件毛织成衣作为来源；新后道 Web 主模型只覆盖三类车缝 Mock 任务，尚不能完整呈现这条链。

这条短链不能被解释为“只要该款存在整件毛织单，整款所有材料都不裁剪、不车缝”。纯整件毛织款的主干可以跳过普通裁剪/车缝；混合结构款若另有梭织面料、需裁拼接片或需要与其他部件缝合，相关分支仍应保留裁剪和车缝，最后再与整件毛织或其他成衣形成路径按真实结构处理。

### 9.5 部位毛织款

业务链是：

`纱线 → 部位毛织加工单 → 毛织横机成片 → 裁床待交出仓 + 其他裁片 → 三方车缝 → 成衣 → 统一后道动态链`

毛织域只保存“部位毛织下游目标为裁床待交出仓”的方向；现有车缝配料没有消费毛织交出批次，真正入裁床库存、与其他裁片合并并交车缝的跨域链尚未闭环。

### 9.6 车缝+烫包外发款

业务上，这类分配表示三方本次承接车缝和烫包。成衣回货进入 QC 时，系统默认不勾选任何我方后道项目，并允许质检人员按现场情况手动增加或调整。最终仍为空时不生成我方后道处理单、不复检，系统按整单直接生成对接成衣仓的数量交接；最终勾选了项目才生成处理单。本轮核查确认新后道全流程已经实现默认值和可编辑性，但当前空项目分支仍错误地自动生成复检单；整套链还只绑定独立 Mock 任务，没有从正式生产单的有效任务分配统一派生，旧后道规则仍可能产生另一份结果。

### 9.7 裁剪+车缝+烫包外发款

业务上，这类分配表示三方承接裁剪、车缝和烫包；回货 QC 同样默认不勾选我方后道项目，但允许手动调整。最终为空时同样不生成处理单和复检，整单直接形成成衣仓交接。当前系统仍生成裁片单和唛架供三方报告，却抑制中央辅助/特种加工单并吸收这些工艺责任；若同一款不同裁片需不同辅助/特种路线，当前整单吸收会失去我方专项加工单的实际投入/产出链。后道默认规则本身与“车缝+烫包”一致，缺口还包括空项目分支去向错误，以及正式任务分配与新后道 Mock 链没有统一。

### 9.8 仅车缝外发款

业务上，这类分配明确表示三方只承接车缝，因此成衣回货 QC 时系统必须自动勾选开扣眼、装扣子、烫包三项，并且质检人员不可以取消或更改；这不是质检员自由判断，也不是技术包预排的三条路线。QC 提交后生成我方后道处理单。新后道全流程已经实现该规则，但只在一张 Mock 任务范围中生效，尚未成为正式生产单的统一后道入口。

### 9.9 盘扣、橡筋、花边、布包扣与花朵等分支

这些不是主衣片顺序上的普通同对象节点，而是与主线并行生产、在后续装配处汇合的辅料分支：

- 盘扣：`面料 → 捆条加工单 → 捆条菲票 → 盘扣加工单 → 盘扣成品`；
- 橡筋：`橡筋米 → 定长切割加工单 → 定长橡筋条`；
- 花边：`采购单投入行 → 花边加工单 → 花边 SKU → 中央辅料仓`；
- 布包扣：`本次制作所需材料/半成品 → 布包扣辅件制作 → 布包扣辅件 → 后续实际使用节点`。具体投入字段尚需另行设计，但绝不能映射为后道“装扣子”；
- 花朵不是上述独立辅件制造支线，而是 `指定裁片部位 → 花朵加工 → 已做花朵的同一裁片部位 → 该裁片下一生产节点`。

当前盘扣、橡筋和花边分别属于捆条/盘扣专项域、通用特殊工艺域和采购花边域，尚未在工艺路线中表达它们最终在哪个车缝/后道明细汇合；布包扣仍被旧映射错归装扣子；花朵的现代裁片专项方向则与业务确认一致，但仍缺通用前后置任务项。

### 9.10 KOL 整单款

KOL 路线让全部准备阶段加工（水溶、染色、印花）保持独立，把其余可生成生产任务的责任压成一张整单任务；裁剪、裁片工艺、车缝等不按普通加工单链生成。它是特例，不能用来解释普通款式路线。

【业务已确认】KOL 样衣、KOL 小单生成的是整单任务，走该整单任务自身的领料、加工、交出和人工完成闭环，不进入普通生产单后道阶段，也不生成普通后道回货 QC、后道处理单和后道复检链。当前 `ProcessTask`/KOL PDA 已经有独立整单执行路径；新后道全流程没有统一读取正式生产单，因此“当前三张 Mock 恰好不含 KOL”不能替代一个明确的 KOL 排除规则。

### 10.2 新旧/兼容链路不是“文件新旧”，而是运行时事实并存

【代码事实】当前兼容问题至少分为四类，删除方法不同：

1. **并行可写事实源**：同一种加工单或状态有两套独立 ID、数组、状态和写命令，例如正式印花与工厂端印花、新旧后道。
2. **正式主单旁挂可写 sidecar**：主单来自正式域，工厂端另存执行状态、参数和日志，例如染色在线域。
3. **旧页面、旧路由和查新失败回退旧模型**：旧逻辑仍是用户可达路径或同一路由的运行时 fallback，不是注释里的历史代码。
4. **新模型内部的历史字段读取迁移**：虽然变量名可能含 `legacy`，但承担旧持久化数据升级；它不能和旧业务工作流一起直接删除。

CodeGraph 对代表性导出函数做 4 层影响分析后，得到以下结果：旧裁片单 `cloneCutPieceOrderRecords` 仍影响 14 个符号，正式裁片单 `listGeneratedCutOrderSourceRecords` 影响 50 个；旧后道 `listPostFinishingTasks` 仍影响 80 个，当前新后道处理单列表 `listPostFinishingFullFlowPostTasks` 只影响 6 个；静态后道路由 `listPostProcessRoutes` 仍影响 17 个；工厂端独立印花 `listPrintingWorkOrders` 和正式印花 `listPrintWorkOrders` 分别影响 20 个、22 个。这些数字不是业务覆盖率，但足以证明“旧”代码仍有真实消费者，“新”代码也尚未接管全链。

### 10.4 为什么现在不能直接批量删除，以及正确顺序

【核查结论】理想终态确实应只保留已确认的最新业务逻辑和必要的历史数据迁移，但当前不能按文件名执行一次性删除。建议严格按以下依赖顺序形成实施计划和原子需求矩阵：

1. 先冻结工艺字典、对象双变体、三方任务范围/KOL 适用性和路线 occurrence 的正式规则。
2. 建立唯一任务/加工单身份，补齐准备、生产明细级前置任务项和后置任务项。
3. 优先修复印花正式 ID 到工厂详情的身份断裂；随后统一正式印花和染色 sidecar。
4. 把旧裁片单记录、字段别名、PDA fallback 和旧进度页依次迁到正式裁片单，不把四类兼容混删。
5. 把新后道 full flow 接到正式普通生产单和有效三方任务分配，明确排除 KOL；将仓库主数据从旧域解耦。
6. 统一后道 QC、处理单、出库和仓库身份，再迁移通用 PDA、打印、平台投影、扣款和结算消费者。
7. 最后删除页面 fallback、旧菜单/路由、旧 handler、旧 Mock、旧存储写入和保护旧行为的测试；保留带 schema version 的一次性历史读取，直到明确截止版本。
8. 每删除一条链，都要正向验证“最新规则能完成同一业务”，再反向搜索旧实体、文案、路由和存储键为零；不能用“页面看起来正常”替代事实源收口。

上述 18 项目前全部是 `待实施`，不是本说明文档已经完成的代码清理结果。本轮只完成现状确认和删除边界，不会把未迁移的旧消费者直接删断。

## 11. 当前最关键的结构性风险

### 11.1 多套事实源导致“页面有单、主链没单”

准备产物、正式印染加工单、裁床单、专项工艺单分别自行生成；后道的回货、责任、QC、动态处理和出货又分散在新旧模型。某个页面能看到 Mock 加工单或后道闭环，不等于生产单主链已经可靠生成并连接了这些事实。

### 11.2 同名工艺有多种身份

- 绣花、压褶既是顶层生产工序，也是现代辅助工艺；
- 捆条既在特殊工艺字典中，又有独立裁床加工单；
- 烫包既可能属于本次分配给三方的任务范围，也可能由回货 QC 最终确定为我方动态处理项目；两者必须按责任归属和实际处理批次区分；
- 后道处理单同时存在新旧两种结构；
- 印花在当前 BOM 自动路线/工厂端代码中被固化为面料工艺，通用类型和数量工具又保留裁片分支；两边都没有完整表达“具体 BOM 原物料分支，可含适用辅料，但不含已裁衣片”；
- 烫画、直喷都存在裁片和成衣两种合法对象变体，但当前字典、旧映射、operation 种子和测试各自只保留其中一种或给出彼此相反的默认；
- 成衣 BOM 缺少直接选择烫画/直喷的入口，裁片烫画又被字典禁止绑定纸样部位；
- 装扣子把主加工对象成衣与消耗辅料扣子混成一个 `targetObject`。

### 11.3 准备、生产路线步骤不能独自承担数量门禁

路线只给任务排序；加工单接收/交出由各域独立控制。若直接用当前 `dependsOnTaskIds` 做“前置有产出才能接收”，会出现：

- 一条裁片分支被无关分支阻塞；
- 准备加工单完全不在依赖集合；
- 多次交出的第一批无法精确匹配下游明细；
- 生产单替换原料后，旧 BOM ID 关系失效。

这类对象级数量承接只适用于准备、生产加工链。后道不能用“前一步路线是否完成”判断是否生成处理单，而应以本次成衣回货批次和到货 QC 判定为准。

### 11.4 加工累计与后道回货被混成一种“多次交接”

准备、生产加工单需要的是多次接收实际投入、多次填报产出和多次交出；后道需要的是多次成衣回货、每个回货批次一次到货 QC、可选动态处理和后续数量交接。这两类“多次”不能共用一套模糊状态。辅助/特种工艺已有累计数量账，旧后道也有多次交出；新后道和某些逐 SKU API 却要求一次覆盖全部明细。人工完成和系统自动推进规则也分散在各专项域。

### 11.5 后道判定是当前最大冲突点

同一批成衣的后道项目当前可能由：

1. 技术包后道路线；
2. 固定合并任务责任；
3. 新模型任务类型对应的默认值和可编辑性；
4. 新模型 QC 最终提交；
5. 旧模型逐 SKU QC；
6. 静态后道路由缺省值；

共同决定。这里不能把新模型第 3、4 项拆成两套冲突：二者合起来正是已确认的最新规则——仅车缝固定三项不可改，含烫包默认空且可调整。冲突来自它尚未接入正式任务分配，而第 1、2、5、6 项仍可独立产生另一份项目结果。

正确收口点应是“普通生产单有效任务分配 + 回货批次 + 唯一到货 QC 提交”：任务分配决定默认值与是否可编辑，QC 提交冻结本批最终项目并在需要时确认返厂/退回三方。判定结果为空时，不生成后道处理单和复检，整单直接形成成衣仓数量交接；项目非空时只生成一张处理单，单头保存项目集合，明细维持 `SKU × 数量`。项目之间的内部执行先后属于 QC/后道模块，不进入技术包工艺路线。KOL 整单直接排除在这条规则之外。

## 12. 本次当前情况的最终判断

### 12.1 已经成立的基础

- 工序字典已收口为准备、生产、后道三阶段，并删除跨款式统一默认顺序。
- 技术包已有款式级步骤、并行组、BOM/纸样来源和版本快照。
- 独立水溶、染色、印花、裁片、捆条、毛织、17 种辅助/特种和花边加工单均已有不同程度的原型实现。
- 新后道模型已经在三张 Mock 生产单范围内做出三方自助回货登记、后道确认实收、到货 QC、可选处理单、复检、出货和成衣仓接收动态链；“仅车缝固定三项不可改、含烫包默认空且可调整、QC 可确认返厂、最终无项目则不生成处理单”已经存在。
- 裁片、毛织和辅助/特种工艺已经能表达部分真实对象和不同单位。
- 个别专项域已经支持多次接收、完工和交出累计。

### 12.2 尚未成立的核心能力

- “印花、烫画、直喷”尚未形成唯一正确的业务词典：印花仍残留裁片类型面；烫画、直喷虽然都应支持裁片/成衣两种独立变体，当前字典、种子和测试却彼此冲突；成衣 BOM 也没有直接选择入口。
- 准备、生产阶段没有统一的加工单头、任务明细、前置项、后置项和实际投入/产出批次模型。
- 没有从技术包路线到每张专项加工单的唯一、完整生成链。
- 没有按加工对象分支的路线承接；当前只是步骤级全连接。
- 没有统一的接收即开工、人工完成和多次交出/接收规则。
- 没有统一处理原料替换且保持技术包路线稳定的映射方式。
- 后道尚未形成覆盖全部普通生产来源、Web/PDA/仓库的唯一权威动态处理事实链；新 Mock 链的默认/可编辑、登记后确认实收及 QC 返厂规则方向正确，但无项目分支仍错误进入复检，处理完成又能再次填写质量/返厂；处理单、复检、仓库和后续交接还有多套冲突来源，KOL 排除也未成为统一入口规则。
- LogicFlow 工艺路线画布尚未实现。

### 12.3 对“当前系统”的准确一句话描述

当前项目已经分别做出了大量真实感很强的工序、任务、加工单、仓库和后道原型，但它们仍是**多个专项闭环的组合**，而且底层业务词典本身仍有对象污染：准备、生产尚未形成由款式路线驱动、以明细级前置/后置任务项和实际交接逐批承接的执行链；印花、烫画/直喷双对象、装扣子主对象、布包扣辅件制作及曲牙绣唯一词条尚未统一；后道虽在有限 Mock 范围内实现了正确的任务范围默认规则、自助登记后确认实收和 QC 返厂，也尚未形成覆盖全部普通生产来源、各端和仓库的唯一权威事实，空项目直达成衣仓规则尚未实现，KOL 整单亦未在统一入口显式排除。

## 13. 已确认边界与结构化目标理解

本节不是代码已经实现的说明，也不是正式实施计划。每一节继续区分【业务已确认】与【分析建议】；本轮提出的十一项问题已经逐条关闭，凡当前代码尚未达到的均明确写成实现差距。

### 13.1 一张生产单包含两种执行模型

【业务已确认】普通款式生产单按准备、生产、后道三个阶段组织；KOL 样衣、KOL 小单是整单任务特例，不进入普通后道。【分析建议】三阶段不能强行使用同一张加工单模板：

1. 准备、生产阶段使用“路线驱动的加工转换模型”。
2. 后道阶段使用“成衣回货驱动的动态处理模型”。

二者通过“生产阶段最终形成并交出的成衣批次”衔接，而不是让后道继续消费某个预设的“前置工序节点”。

### 13.2 技术包“工艺路线”的职责边界

【业务已确认】技术包标签应改为“工艺路线”，并使用 LogicFlow 做受控的可视化编排；它至少负责回答：

- 本款有哪些准备、生产工艺；
- 每个工艺属于哪个阶段；
- 作用对象是技术包中的哪条 BOM 原物料分支、具体裁片部位、毛织部位还是成衣；准备阶段印花/染色必须继承面料、纱线、花边等实际 BOM 物料类别并排除已裁衣片；烫画/直喷都允许裁片和成衣两种显式对象，裁片变体必须绑定纸样部位，成衣变体必须绑定成衣 BOM，不能脱离来源对象任意改选；
- 哪些节点串行、并行或按不同对象分支；
- 节点来自哪条 BOM、哪个纸样/部位或人工补充事实；
- 该款是否整件毛织，是否跳过普通裁剪/车缝；

【业务已确认】这里的排序粒度是“款式 × BOM 物料分支”，不是“款式 × 工序名称”。同一款中，不同面料之间可以工艺不同、顺序不同；面料、纱线、花边等不同类别之间同样可以各走各的准备路线。画布可以在真实消费节点汇合这些分支，但不能为了视觉整齐把多个 `DYE` 或 `PRINT` 节点合成一个节点。

【业务已确认】技术包中的纽扣、扣眼、包装等产品要求不能直接变成本批实际后道项目或完成事实。实际是否执行后续后道项目，由本批到货 QC 按三方任务范围规则确认；因此这些要求即使在产品资料中展示，也不得进入技术包固定工艺路线并替代 QC 结果。

技术包工艺路线不负责锁定：

- 某张生产单实际换用了哪个面料或纱线 SKU；
- 某一次加工单实际收到了哪个批次、多少数量；
- 某次交出由哪张后置加工单接收；
- 成衣回货后实际还需执行哪些后道项目；
- 后道处理前后两个虚构的成衣物料身份。

【业务已确认】LogicFlow 只承载维护工艺路线所需的业务操作，其他能力不展示给业务人员。【分析建议】第一版具体收口为查看来源、调整先后、设置/取消并行、连接允许的对象分支、查看对象类型和确认路线；最终按钮清单仍应在页面方案中逐项确认。通用流程设计器的任意节点、任意连线、样式、脚本、审批和技术属性不应展示。

### 13.3 准备、生产阶段的合理执行链

【分析建议】准备、生产阶段每张真加工单至少要能形成以下关系：

`需求来源 + 前置任务项 → 本单任务明细 → 实际投入批次 → 加工记录 → 实际产出批次 → 交出记录 → 后置任务项 + 下游实际接收`

其中：

- BOM 中每条适用原物料的水溶、染色、印花原则上分别形成该物料分支的准备阶段需求；不同面料、纱线、花边等可以有不同工艺集合和不同顺序，不使用款式级或全局默认顺序。
- 物料与纸样关系中的裁片辅助/特种工艺原则上形成生产阶段需求；同一款不同裁片可以走不同分支。裁片图案加工必须使用烫画/直喷，不得创建“裁片印花”。
- 成衣 BOM 中的烫画/直喷同样形成生产阶段需求，但必须作为成衣对象 occurrence，与同名裁片 occurrence 分开；成衣 BOM 页面只展示这两个可选工艺，生产执行时仍允许替换实际成衣物料。
- 布料默认需要裁剪；纯整件毛织款主干例外，按“纱线 → 成衣”形成生产结果。普通生产单随后进入后道，KOL 整单不适用；同款另有需裁面料、拼接部件或车缝组合时，其分支仍保留裁剪/车缝。
- 部位毛织的目标方向按“纱线 → 毛织横机片 → 裁床待交出仓 → 与其他裁片一起交车缝”；当前代码只完成到方向字段，跨域承接仍待实现。
- 盘扣、橡筋、花边等转换型辅料加工是与主衣片并行的分支，必须在真正消费它们的生产明细处汇合。
- 同一加工单可以多次接收实际投入、多次填报产出、多次交出；不设置“是否允许部分放行”。
- 对普通准备/生产加工单，前置实际交出形成可接收数量；本单确认接收后系统自动开工。
- 裁片交给三方车缝厂时，系统直接替三方完成接收并开工，不设置裁片齐套门禁；但系统仍必须如实记录每种裁片和数量，不能用最大部位数量虚增可生产件数。
- 系统不能因为数量达到、子单完成或仓库收货，就自动替操作者完成加工单或生产单；实际单据由人工完成。

### 13.4 后道阶段的合理动态处理链

【业务已确认】后道统一主链应按登记方式先分流，再在唯一到货 QC 汇合：

`当前模式：三方车缝工厂自助回货登记 → 后道确认实收 ┐`

`未来扫码模式：扫码回货登记并同时确认实收 ─────────┴→ 读取本次三方任务范围 → 唯一到货 QC（质量 + 返厂确认 + 最终后道项目）`

QC 之后再按最终项目分流：

- 项目为空：`整单直接生成成衣仓数量交接`，不生成后道处理单，不生成复检，也不保留额外扫码/点数动作。
- 项目非空：`生成一张后道处理单 → 人工完成处理 → 当前后续交接链`。处理单单头保存开扣眼、装扣子、烫包等项目集合，明细按 `SKU × 数量` 保存。

其中：

- 普通生产单的车缝成衣、整件毛织成衣和合法成衣烫画/直喷产出进入后道阶段；KOL 样衣、KOL 小单整单任务明确不进入。
- 当前原型只实现第一种回货模式；第二种扫码即实收不能被写成当前能力。
- 仅车缝任务在 QC 固定勾选开扣眼、装扣子、烫包且不可修改；车缝+烫包、裁剪+车缝+烫包在 QC 默认不勾选任何项目，但允许现场手工调整。
- 到货 QC 是整个生产链唯一的质量判断点，也是返厂/退回三方数量、原因和接收工厂的产生与确认点。
- 处理完成只记录实际处理数量、未处理数量、操作人和时间，不再次填写合格、瑕疵或返厂。
- 同批多个后道项目的执行先后属于 QC/后道模块内部安排，与技术包工艺路线无关；本文不据此扩大 LogicFlow 的节点范围。
- 后道辅料调拨只服务已经确认需要执行的项目，不能反向决定处理需求。

### 13.5 后道任务范围、回货批次和 QC 最终项目不能混为一谈

准备、生产阶段的需求来源回答“为什么要生产或加工这批物料”，例如生产单、补料、备货或采购。

后道没有与准备加工完全同性质的“需求来源”。【分析建议】至少要分开以下四层事实，并在“三方回货事实”中保存回货批次、数量和时间；履约责任则由任务分配和交接记录追溯：

- 款式工艺需求：这款从产品上需要什么，不因工厂分配而改变；
- 本次三方任务范围：只分配车缝，还是车缝+烫包/裁剪+车缝+烫包；它直接决定 QC 默认值和是否可改；
- 三方回货事实：谁交回哪一批成衣、各 SKU 数量是多少；
- 我方本批最终处理项目：QC 按任务范围规则提交后的项目集合，可以为空。

此外，上游回货来源回答谁交回了哪批成衣，回货履约责任回答谁对数量和时效负责；它们都不能代替上述四层。

如果继续把这些事实压成一个“需求来源”或一张静态路线，系统就无法区分“这款需要什么”“本次分给三方什么任务”“哪批成衣实际回来了”“QC 最终确定我方做什么”。

### 13.6 页面和现场操作边界

管理端可以完整展示款式路线、加工单来源、批次承接、本次三方任务范围和后道 QC 最终项目，以支持跟单和追溯；一线页面不应要求工人理解整个模型。

准备、生产加工人员只需看到：当前单、当前实物、已收到多少、现在做什么、已完成/待交出多少。后道人员只需看到：当前回货批次、QC 判定的单头项目集合、每个 SKU 多少件、完成确认。系统内部可以保存完整关联，但不能把前置任务图、技术包版本关系或通用状态机暴露成现场必填项。

### 13.7 后续方案必须避免的五个错误方向

1. 不把三个阶段塞进一套完全同构的“加工前/加工后”字段。
2. 不用 LogicFlow 画面上的连线直接代替实际批次、数量和交接账。
3. 不因为技术包记录了产品要求就另建静态后道项目；QC 初始值必须严格读取任务范围：仅车缝固定三项，含烫包默认空且可调整。
4. 不从可选类型、旧种子、Mock 文案或数量单位反推业务对象；先用企业工艺词典确认“拿什么加工、加工后还是什么、交到哪里”。
5. 不建立“万能印花”模型：准备阶段 BOM 原物料印花、裁片烫画、裁片直喷必须是不同工艺和不同执行域；同时也不能把准备印花再次收窄成只有面料。

### 14.3 P2：在业务模型清理后再做的产品呈现

1. 将技术包标签从“工序工艺”改为“工艺路线”。
2. 引入 LogicFlow，但只暴露选择合法节点、连接合法对象分支、调整串并行、查看来源和确认路线等业务动作。
3. 节点卡片必须直接显示“工艺 + 具体作用对象/部位 + 来源”；禁止显示通用流程设计器的节点样式、脚本、任意属性和任意连线。
4. 对已确认非法或失真的组合在数据进入画布前阻断，例如准备节点缺少来源 BOM、路线节点工艺与该 BOM 显式需求不一致、`PRINT + 已裁裁片`、烫画/直喷缺少明确的裁片部位或成衣 BOM 来源、`开扣眼 + 裁片`、`装扣子 + 主对象辅料`。不能再把“非面料 BOM 触发准备印染”整体列为非法，也不能把合法的成衣烫画/直喷阻断。
5. 同一工序码允许按 BOM/对象分支出现多个独立节点 occurrence；画布不能用一个 `DYE` 或 `PRINT` 节点吞掉该款所有面料、纱线、花边等物料分支。
6. 一线执行端不展示路线图、技术包版本关系或前后任务图，只展示当前实物、应收/已收、当前动作、已完成/待交出数量和一个主按钮；完整关联留给管理端追溯。

### 14.4 本次审查后的最终结论

当前原型已经覆盖了大量加工单页面和专项动作，但还不能称为一套服装生产工艺路线系统。原因不只是技术上“没有统一模型”，更是若干业务对象和新旧边界尚未统一：合法的纱线染色、花边染色及其他辅料印染会被强制标成面料；同一款不同 BOM 物料不能拥有各自的工艺集合、同名工序节点和顺序；所有同工序物料又会在正式快照中被提前合并；准备印花还被通用类型污染为可能的裁片工艺；烫画、直喷两种合法对象被字典、种子和测试拆成互相冲突的单一默认，成衣 BOM 又缺少直接入口；开扣眼被错连到裁片、装扣子又把成衣与扣子辅料混为一个对象；布包扣仍被旧码误归装扣子，曲牙绣仍与旧曲牙映射并存；后道最新规则只存在于有限 Mock，空项目仍错误进入复检，处理完成还能再次产生返厂，而旧域、静态路线和通用质检链仍并行。

因此，后续正确顺序不是先把当前节点搬进 LogicFlow，而是：

`先冻结企业工艺词典及“BOM 原物料 / 已裁裁片 / 成衣”等对象状态边界 → 再确认每款、每条 BOM 原物料/纸样部位/成衣 BOM 的独立对象路线 → 再让每个路线 occurrence 生成对应加工需求和明细级前置/后置任务项 → 再按执行条件另行合批并以实际交出/接收批次连接加工单 → 最后把已确认后道规则接入普通生产单、修正空项目直达成衣仓与 QC 唯一返厂事实，并删除旧并行链`

这五层必须作为一个方案一起讨论，但数据职责不能混成一层：技术包工艺路线负责“本款应该怎样走”；生产单/加工单负责“这次实际上拿什么、做多少”；交接记录负责“这批实际从谁到谁”；后道到货 QC 负责“这批成衣回来后实际还要处理什么”。

## 附录 C：容易被重复计数的类型

| 代码类型/对象 | 为什么不另算一种加工单 |
|---|---|
| `GeneratedPreparationOrderArtifact` | 生产单生成过程中的准备产物描述，不是可执行、可交接的正式单据 |
| `ProcessWorkOrder` | 把水溶/染色/印花三个专项域统一成平台视图，不是第四种准备加工单 |
| `DyeWorkOrderOnlineRecord/View` | 同一染色单的在线动作和列表投影 |
| `CombinedDyeingTask` | 把至少两张既有生产单来源染色单编组并分配共同产出，不重新产生业务需求 |
| `GeneratedTaskArtifact` | 技术包路线转生产任务前的生成产物，不是加工单 |
| `ProcessTask` | 通用分配/排序/协作任务；车缝和烫包当前例外地主要靠它执行 |
| `EffectiveTaskAssignment` | 任务分配结果，不是加工单 |
| `CuttingSewingDispatchOrder/Batch` | 裁片配料和交出任务/批次，不是车缝加工单 |
| `ButtonLoopTaskOrder` | 盘扣专用投入/产出流的任务对象，归入同一盘扣加工需求，不再重复算第 18 种中央工艺 |
| 旧 `SpecialProcessOrder` | 仅支持捆条的旧裁床工艺单事实源，已在 `PROD-003` 并存模型中登记 |
| `PostFinishingTaskView` | 旧后道生产单级汇总视图，不是 QC 生成的后道加工单 |
| `ProcessWorkOrderQcRecord` | 加工单仓库实收后的质检/结算记录，本身不加工 |
| 送货单、复检单、出货单、调拨单 | 分别承担到货、质量复核、出库和辅料移动，不是加工动作 |
