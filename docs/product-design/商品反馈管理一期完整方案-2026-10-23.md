### 1.2 一期要回答的业务问题

1. 今天应采哪些店铺，分别由谁负责，哪些没有开始、哪些没有采完？
2. 某人是否按时完成规定范围的采集并交付？数据处理延迟是否来自工具或服务？
3. 某次采集产生多少上报记录，其中新增、更新、重复、排除和异常各是多少？
4. 某条评论来自哪个渠道、店铺、链接、购买规格与订单，其来源和处理过程能否追溯？
5. 哪些商品、规格出现低评分或具体问题？哪些优点值得关注？结论基于多少条评论？

### 1.3 一期范围

包含：采集安排、每日任务、历史补采任务、采集批次和回执、人员事实统计、全星级评论明细、必要商品关联、人工分类与复核、星级和主题汇总、基础趋势、明细追溯、筛选结果导出。

条件包含：平台销量、平台累计评论数和平台评分。当现有工具或既有数据源确实提供对应数据及口径时展示；未提供时显示“未取得”，不阻断本系统已采评论的基础分析。

不包含：退货业务、自动处罚或奖金计算、平台评论发布与删除、自动回复、独立站评论发布管理、自动选品决策、自动改款、工厂责任认定、复杂 AI 自动分析、移动 PDA 专页。现有浏览器拓展和本地应用继续承担采集与提交，不在 PCS 页面重建爬虫。

## 3. 产品架构

### 3.1 产品组成与职责

~~~mermaid
flowchart LR
    A[渠道店铺后台] --> B[浏览器拓展：采集原始评论及执行证据]
    B --> C[现有本地应用：整理与提交]
    C --> D[自有数据服务：接收、去重、保存与回执]
    E[既有店铺及商品档案] --> D
    D --> F[PCS 商品反馈管理]
    G[既有平台指标或订单数据源] --> F
    F --> H[采集任务与人员事实统计]
    F --> I[评论明细与人工分类]
    F --> J[商品汇总与基础分析]
~~~

| 产品组成 | 负责的事实 | 不承担的职责 |
| --- | --- | --- |
| 浏览器拓展 | 实际打开的店铺、采集开始结束、范围、翻页或结束依据、原始评论 | 不用“点击过采集”冒充完成；不自行决定绩效分。 |
| 本地应用 | 批次身份、提交人、清洗版本、提交与重试、逐条处理结果关联 | 不以本地文件保存成功冒充服务器入库成功。 |
| 既有数据服务 | 原始记录与身份、唯一性、提交回执、版本、时间和事实统计 | 不把未知商品关联或低信息评论直接丢弃。 |
| 商品基础档案 | 店铺、链接、SPU、渠道规格、内部 SKU 及映射 | 不在反馈模块重复维护这些对象。 |
| 商品反馈管理 | 安排与任务展示、异常处理入口、人员统计、评论分类、分析和追溯 | 不操作真实平台评论，不建立角色演示或虚假权限。 |

上述职责是对接目标，不能视为现有工具能力已核实。真实跨人员考核依赖统一数据服务。本仓库的浏览器本地 Mock 只能演示这些流程和契约，不能证明多人共享或真实采集接通。

### 3.2 使用者与责任

- 采集执行人员：按安排进入正确店铺，执行全星级采集，查看回执并补采缺口。
- 采集安排负责人：维护店铺与人员的长期安排、查看遗漏、跟进覆盖与处理缺口。
- 商品或运营分析人员：查看明细、标注主题、核查异常、对比商品反馈。
- 研发支持人员：核对时间、身份、字段、覆盖证据及处理失败原因。

这里的岗位表达任务责任，不转化为原型的权限门槛。记录操作人、复核人，不新增“主管模式”等身份开关。

### 3.3 数据所有权

评论原始内容、原始评分、平台身份和来源时间属于采集事实；分析人员只能增加解释、译文、主题和关联纠正记录，不能编辑原文把差评改成好评。评论分类属于分析事实；任务安排属于管理事实；平台销量和评分属于带来源、范围、截至时间的外部指标。

### 5.2 对象关系及统计粒度

| 对象 | 一条记录代表什么 | 关联 |
| --- | --- | --- |
| 采集安排 | 某店铺在有效日期内的一套采集责任与规则 | 既有店铺、人员 |
| 店铺任务 | 某店铺、任务类型、业务日期或历史区间的一次约定目标 | 安排版本、执行批次、覆盖证据 |
| 采集执行 | 一次真实打开平台并执行采集的过程 | 一个店铺、一个执行人、范围、输出批次 |
| 提交批次 | 一组有固定身份的上报记录及其处理回执 | 执行、提交人、任务、重试 |
| 上报记录 | 本次提交中的一条来源记录 | 原始内容、处理去向、唯一评论或异常 |
| 唯一评论 | 经身份判断的一条平台评价 | 链接、可确认订单和规格、多次观察与版本 |
| 评论分类 | 针对某个评论内容版本的人工判断 | 分类规则版本、标注人、复核人 |
| 指标快照 | 某个外部指标在某范围、某时点的值 | 链接或其他明确粒度、来源、单位 |

店铺内链接可包含多个渠道规格；多个渠道规格可以映射同一个内部 SKU；一个内部 SKU 可以出现在多个店铺和多个链接。一条评论在同一统计维度只计一次，不能通过联表把评论复制到链接下所有 SKU。

### 5.3 时间维度

| 时间字段 | 含义及使用位置 |
| --- | --- |
| 业务日期 | 任务归属日期，按采集安排的考核时区生成 |
| 目标开始／结束 | 任务应覆盖的评论窗口，使用开始包含、结束不包含的区间 |
| 平台评论时间 | 评论在平台发生的时间；用于评论趋势，保留原始值、时区和精度 |
| 平台修改时间 | 平台确实提供时记录，不能以抓取时间代替 |
| 采集开始／结束 | 一次真实执行时间，不等于评论时间 |
| 服务接收时间 | 数据服务确认接收该执行数据及证据的时间 |
| 首次入库时间 | 按既定去重规则首次创建评论并成功持久保存的时间，用于新增入库量；人员采集产出按来源执行／任务归属 |
| 最近观察／更新时间 | 后续采到同一评论、或确认内容变化的时间，二者分别记录 |
| 完成交付时间 | 满足规定覆盖且所需原始数据和证据已被服务接收的最早时间 |
| 任务完成时间 | 覆盖与必要数据处理均满足条件的最早时间 |
| 指标截至时间／报表时点 | 外部指标有效时点，以及本次报表所依据的数据版本时点 |

不把服务器时间覆盖为平台评论时间，不把本地文件修改时间当成采集时间。时间缺失或来源存疑单独标记，不能默认补为当天零点。按日期筛选时，UI 显示实际时区和区间，完整一天换算为次日零点的开区间。

### 5.4 核心字段字典

下表为业务字段要求，不要求建立一张宽表。内部标识只用于关联，页面优先展示业务名称。

#### A. 采集安排

| 字段组 | 字段与约束 |
| --- | --- |
| 身份 | 安排编号、内部店铺 ID、渠道、市场、外部店铺 ID／code；店铺名称引用主档并保留历史显示名 |
| 责任 | 负责人 ID、负责人姓名、可记录协作人员；不得用提交人自动替代负责人 |
| 日历 | Asia/Jakarta、启用日期、每天执行（含周末与节假日）、每日 18:00 交付截止 |
| 范围 | 日常／历史补采、全星级固定值、链接覆盖策略、历史起点、增量目标端点、回看窗口 |
| 管理 | 草稿／已启用、规则版本、创建／修改人和时间、未来长期安排变更原因及生效日；无免采、临时改派、暂停／恢复入口 |

渠道、店铺、负责人、时区、范围、截止规则和生效日为启用必填。未填写完成可保存草稿，不能提前生成可考核任务。

#### B. 店铺任务及执行证据

| 字段组 | 字段与约束 |
| --- | --- |
| 身份与归属 | 任务编号、店铺 ID、类型、业务日期／历史区间、安排版本、责任归属快照 |
| 固定目标 | 目标开始结束、星级范围、目标链接集合或全店评价入口的范围依据、目标确定时间 |
| 执行 | 执行编号、实际采集人、开始结束、工具版本、实际店铺、实际筛选、排序方式 |
| 覆盖 | 已覆盖区间、目标／已覆盖链接数、成功／失败页或分片、终止原因、结束位置／水位依据 |
| 数据处理 | 关联批次、结果计数、未解决异常、服务接收时间、交付时间、完成时间 |
| 派生状态 | 执行状态、处理状态、任务状态、是否逾期、按时交付与按时完成结果 |
| 调整 | 覆盖核查、处理修复、重新判定的前后值、原因、操作人、时间及版本；任务责任归属固定 |

链接总数未知时显示“范围待核验”，不把已采链接数伪装成完成率。能够通过平台全店评价入口证明覆盖时，可以使用该入口的完整范围证据，不强迫逐链接打开。

#### C. 提交批次

| 字段组 | 字段与约束 |
| --- | --- |
| 身份 | 批次编号、执行编号、主要任务编号、来源店铺、载荷摘要、清洗规则版本 |
| 人员 | 采集人、提交人、接收端；程序账户与业务执行人分开 |
| 时间 | 采集时间、首次接收时间、处理开始／完成、最近重试 |
| 数量 | 上报 U、入库时新增 N、更新 M、重复 D、确定排除 X、失败 F、待处理 P |
| 结果 | 待处理／处理中／处理完成／有失败异常、逐条去向、错误原因、关联评论 ID、回执编号及处理版本 |
| 重试 | 同批次重试次数、每次尝试结果；重试不生成新批次产出 |

一个执行可分多个批次。一个批次最多只有一个主要任务归属；它的覆盖证据可以帮助核验实际覆盖范围内的每日及历史任务，逐任务核验、保留各自截止，评论新增产出只归属首次成功写入一次。

#### D. 评论及来源

| 字段组 | 字段与约束 |
| --- | --- |
| 内部身份 | 评论 ID、首次入库批次、最近观察批次、身份方式及版本、历史指纹 |
| 平台身份 | 渠道、市场、店铺、平台商品 ID；平台评论 ID 有则保存，不能虚构 |
| 订单与规格 | 平台订单号、订单明细 ID（若有）、平台规格 ID、卖家 SKU 原文、原始颜色／尺码 |
| 内部关联 | 链接 ID、SPU ID、内部 SKU ID、关联状态、依据、映射版本、确认人和时间 |
| 评论人 | 原始显示名必填且须来自来源评论；平台用户标识（若有）、来源头像引用；平台脱敏名称仍按原样保存，不能填造“匿名用户”补空 |
| 内容 | 原文、原始语言、原始星级、图片／视频引用（来源提供才记录）、回复及回复时间 |
| 时间与质量 | 平台评论时间及精度、时间可信状态、采集与入库时间、缺失字段、来源异常 |
| 版本 | 首次内容、当前内容、变更依据、修改记录；原始观察不被人工覆盖 |

平台商品 ID、订单号、评论 ID、规格 ID 一律按字符串处理，避免长数字丢精度、前导零丢失。不能通过截取 SKU 文本就认定内部规格；必须有映射依据。

评论者完整是本期有效数据与 Mock 的前提。所有演示评论均有非空来源显示名，不设计无评论者记录、占位名、身份补录或身份核验流程。平台原生评论 ID 与评论者是不同字段：有评论者不代表一定能取得平台原生评论 ID，去重仍按第 13 节确定规则处理。真实对接发现来源不满足前提时，先核对工具输出，不扩建本期身份待办业务。

#### E. 分类与指标

| 对象 | 字段与约束 |
| --- | --- |
| 评论分类 | 评论 ID、内容版本、信息量级别、主题标签、标签正负倾向、证据原句或图片引用、备注、分类状态、标注／复核人及时间、规则版本 |
| 指标快照 | 来源系统、对象粒度与 ID、指标名称、数值／未知、单位、累计或区间、起止／截至时间、评价计数口径、获取时间 |
| 统计结果 | 基础筛选范围、日期类型、时区、统计时点、规则版本、各分母及分子、未知与未分类数量 |

## 6. 交互架构与端到端流程

### 6.1 建立安排

1. 在“采集工作台 → 采集安排”从现有渠道店铺档案选择店铺。
2. 填写真实负责人及生效日；首批九店显示每天执行、Asia/Jakarta 18:00、昨日核心／最近 7 个完整日回看；全星级为固定只读要求。
3. 展示预览：将生成哪些日期的任务、每项任务覆盖什么评论范围、截止何时。
4. 保存安排版本。未来任务按新版本生成；已生成任务的历史责任和范围不静默变更。
5. 一期没有任务临时改派。长期负责人配置的后续变更只能从未来未生成任务的生效日开始，已生成任务的责任、日期、截止和执行事实保持原记录；不提供暂停或免采绕过每天执行要求。

任务生成不依赖某人打开页面或上传数据，否则无人上报的店铺会从考核中消失。真实服务使用既有任务生成能力或等效的按日任务事实；本方案不规定新增调度框架。

### 6.2 每日采集

1. 执行人查看今日任务，确认店铺和规定范围。
2. 在现有浏览器拓展进入对应平台店铺，使用全部评分且不限定“有内容／有图”的采集条件。
3. 拓展记录本次执行身份、起止时间、范围和结束依据；异常中断保留已覆盖部分和缺口。
4. 本地应用提交批次，服务给出接收与处理回执；PCS 展示已上报、处理中、异常或完成。
5. 系统按第 12 节规则判定交付与完成。不能通过“手动完成”按钮绕过证据。
6. 需要补采时查看缺口，再在现有工具执行新采集；需要补交时重传原批次，保留原执行日期。

PCS 一期不放无真实能力的“开始爬取”按钮。仅在工具已有可验证的直达协议时提供“打开采集工具”；否则提供店铺、目标范围和操作说明。

### 6.3 零新增、重试与补采

- 当次有效检查范围结束且没有新评论：保存零条结果及覆盖证据，可以完成。
- 当次采集全部命中已存在评论：可以完成，新增为零、重复为实际条数。
- 昨天文件今天重复上传：只补交昨天执行，不产生今天的新鲜采集事实。
- 客户端未收到成功回复：重试同一批次，返回已提交结果或续处理失败项，不能重复增加新增量。
- 部分链接失败：任务为部分完成，详情显示具体缺口；补采成功后合并覆盖证据，保留失败历史。
- 逾期补采：可以完成原任务，但仍保留逾期；不能将业务日期改为补采当天使其变成按时。

### 6.4 评论核查和分类

1. 从批次、商品汇总或分析图表进入同一评论明细页面，携带来源筛选。
2. 打开评论详情，核对原文、原图、评分、订单、规格、时间和来源。
3. 来源关联错误时提交“修正关联”，预览受影响 SPU／SKU 汇总；写明依据与原因，保存前后值。优先使用可靠订单明细及购买规格的历史对应关系；采用映射历史时，必须有支持该购买或来源事件时点的证据。仅知道评论发表时间，不能当然认定购买时采用了相同映射。缺少历史依据时保留待确认，不以当前主档映射冒充历史事实。
4. 标注信息量、主题和主题倾向。优先具体内容，不要求每条仅评分评论人为添加原因。
5. 标注完成后可直接确认；需要另一人复核的设为“待复核”，不引入角色权限。
6. 正文或评分出现新版本时，原标签保留历史，并提示“内容已更新，分类待复核”。当前确认分类不得自动套用到新正文。

商品关联修正只改变有证据支持的商品归属，不合并或拆分评论。主档新增或改变映射不自动改写历史评论；明确纠正关联时，展示原归属、目标归属、来源时点、映射版本、影响期间和当前统计变化。既有导出保持原时点，新报表标注关联修订版本。

### 6.5 统计下钻

点击统计卡、图形或主题行，打开带相同对象、期间和口径的明细。来自“差评率”的下钻保留原分母范围，并注明当前只展示差评分子；不能把分母随明细筛选改成差评本身。

返回恢复筛选、维度、排序、页码和滚动位置。点击关联商品仅打开对应既有档案，不能因反馈查看触发写入或修改。

### 6.6 通用动作约束

| 动作 | 前置条件 | 成功反馈 | 失败或取消 |
| --- | --- | --- | --- |
| 保存安排 | 必填完整、日期有效、同店规则不冲突 | 生效日及影响任务预览一致 | 保留输入并定位错误，不生成半套任务 |
| 查看批次／评论 | 对象可读取 | 打开详情与来源路径 | 展示读取失败和重新读取，保留筛选 |
| 修正关联 | 依据充分、目标有效 | 展示前后关联与统计影响 | 版本冲突提示重新读取，不覆盖他人结果 |
| 保存分类 | 主题合法、基于当前内容版本 | 更新状态与统计 | 保留草稿，内容版本变动时提示复核 |
| 导出 | 当前口径明确 | 导出全部筛选结果并标注范围 | 明确失败，不以当前页代替全部结果 |

### 6.7 核查与调整的具体入口

覆盖、处理和商品关联核查保留发起人、处理责任人、证据、结论、时间和版本。待核查不是自动扣罚；核查人不是采集人。这些操作仅用于修正覆盖或保存事实，不提供免采、临时改派、评论身份核验或人工身份合并／拆分入口。

| 操作 | 入口 | 表单与证据 | 可选结论及结果 |
| --- | --- | --- | --- |
| 覆盖核验 | 任务详情“核查与调整”；工作台“覆盖待核验”筛选 | 缺失范围、原始执行、工具补充的实际筛选与结束证据、核查人和备注 | 证据通过并重新计算、退回补证、证据不足继续待核验；无证据不能勾选通过 |
| 任务重新判定 | 已完成任务详情“核查与调整” | 新发现的覆盖或保存缺口、相关批次、原状态、新派生状态预览、原因 | 记录纠正后自动派生状态；不提供任意选择已完成 |
| 关联纠正 | 评论详情“关联信息 → 修正关联” | 原始购买规格、订单依据、采用映射及生效区间、原／新内部关联、影响报表 | 确认修正或取消；主档当前映射变化本身不是历史改绑依据 |

核查过程可保存工作草稿，最终确认时再次校验原始内容和处理版本；版本已变则提示重新读取并保留备注。覆盖证据不足时继续显示具体缺口，不凭人工勾选改为范围完成。

覆盖核验补充证据后，按原始持久接收的证据是否在截止前已足够决定交付时间：原有完整证据只是晚复核，可追溯确认原时点；必要证据后来才补齐，则取补齐并持久接收的时点，不能人工回填为按时。全过程显示“原始接收、证据补齐、核验结论”三个时间。

## 7. UI 设计规范与页面骨架

### 7.1 整体布局

沿用现有 PCS 顶部系统导航、左侧菜单、页签和视觉组件。展开“商品反馈管理”显示五个子页面；当前子页面高亮，但父菜单仍可手动收起、再次展开。

桌面基准 1366×768，最低 1280×720。页面结构统一为：

~~~text
页面标题                         主操作 / 刷新
业务说明（范围、时区、数据时点）
查询卡：常用条件 + 更多条件           查询  重置  导出
统计卡：关键数量 / 状态 / 口径提示
独立结果卡：标题与总数              列设置 / 适用批量动作
表头
数据行（宽表在卡片内部横向滚动）
每页条数 / 总条数 / 页码
~~~

查询卡和统计卡不占据整屏；常用筛选默认一至两行，低频条件在“更多条件”内展开。管理列表默认每页 20 条，可选 20／50／100；原型 Mock 与常规验收每次最多两页，不据此缩减真实业务结果。

### 7.2 视觉与组件

| 元素 | 设计 |
| --- | --- |
| 颜色 | 沿用系统主题主色；蓝色表示信息和主动作，绿色表示已满足条件，黄色表示待处理／部分完成，红色表示失败／逾期；始终附文字 |
| 字体层级 | 标题、卡片标题、正文、辅助信息沿用现有组件规范；正文建议 14px，辅助文字不小于 12px，不用浅灰承载关键数量 |
| 间距与密度 | 采用现有间距刻度；查询控件建议 32～36px 高，评论行可多行，其余任务行保持紧凑 |
| 数据显示 | 数量、单位、百分比清晰区分；零值显示 0，未知显示“未取得／未确定”，不混用横杠 |
| 评分 | 星级图形同时显示数字；未知评分显示“评分未取得”，不能画成零星 |
| 商品识别 | 同块展示对应商品缩略图、SPU、规格和链接 ID；图片保持比例，失败有明确提示 |
| 评论内容 | 列表展示约三行并可展开；详情保留全文；原文与译文分区，译文注明来源 |
| 宽表 | 关键对象列可冻结左侧，操作列固定右侧；不让整个页面横向溢出 |
| 长 ID | 完整值可查看和复制；紧凑显示可缩略，但不能只靠悬停才能取得完整信息 |
| 图表 | 基础条形图、折线图、星级分布；提供同数据表格，不为每条记录放一个大饼图 |

### 7.3 抽屉、弹窗和键盘

任务／批次详情抽屉建议宽约 720～840px；评论详情约 860～960px，窄于该宽度的窗口使用可读的全宽详情。右上关闭，Esc 可关闭，关闭后焦点返回触发按钮；有未保存分类时提示保存或放弃。

筛选支持 Enter 查询；Tab 焦点顺序与视觉顺序一致；图片预览可通过按钮打开、Esc 关闭。危险或影响统计的动作在最终确认页一次性展示对象、原因和影响，不叠加同义确认。

列设置可保存列显隐、顺序、冻结和每页数量；分页和排序按已有项目约定，不擅自长期固化。店铺、任务状态、核心身份等防错字段不可隐藏。

### 7.4 空态和异常态

| 场景 | 页面表达与操作 |
| --- | --- |
| 没有采集安排 | “尚未安排应采店铺”，提供新增安排；不能显示完成率 100% |
| 有任务但无人执行 | 所有应采店铺仍显示，状态未开始 |
| 无新增评论 | 明确“本次新增 0 条”，另显示覆盖是否完成 |
| 查询无结果 | “当前条件下没有结果”，可重置，保留条件 |
| 数据加载失败 | 显示读取失败、重新读取，不编造错误原因 |

### 8.1 店铺任务 Tab

目的：每日快速看到应采、遗漏、未完成原因及责任。

默认：当前业务日期、全部已启用安排的店铺、全部状态；未开始和部分完成靠前，已完成靠后。历史补采使用明确任务类型筛选，不与每日应采任务混算。页面主操作为“新建历史补采”，安排维护通过页内 Tab 进入。

| 区域 | 字段／内容 |
| --- | --- |
| 常用筛选 | 任务日期、渠道、店铺、负责人、任务状态 |
| 更多筛选 | 任务类型、是否逾期、覆盖状态、处理状态、异常类型 |
| 统计卡 | 应采任务、已按时交付、已完成、未完成、逾期；点击可下钻 |

### 8.4 新建历史补采

入口：“店铺任务”Tab 右上“新建历史补采”。表单必填：店铺、负责人、历史开始／结束、目标链接或全店入口范围、计划截止、原因；全星级固定，时区引用安排并显式展示。

支持按明确连续日期区间拆成若干任务，预览每段起止、覆盖对象和截止，不按任意评论条数拆分完整性目标。已有相同历史区间时提示复用原任务；与每日或其他历史任务重叠时展示重叠范围并要求明确用途，不能把重叠范围重复记成采集贡献。

首次启用预览并列“首个每日核心窗口、最近 7 个完整日回看、另行指定历史补采范围”。保存后历史任务出现在工作台“历史补采”筛选下，统计历史覆盖进度，不进入每日到期分母。

历史目标已确认：覆盖平台仍可访问、可核实的历史评论，包括可访问的历史／下架商品链接。执行顺序为核对现有存量及覆盖证据 → 优先近 90 天的缺口 → 向更早历史分段补齐。近 90 天按首次历史计划基准日 D0 的 [D0−90 日 00:00，D0 日 00:00) 固定，不每天滑动重建历史计划；与日常窗口重叠时可复用合格证据，新增产出仍只记一次。

平台最早可访问时间、各段缺口、负责人和计划截止需按实际情况填写；这些是计划执行参数，不再是是否开展历史补采的待确认决策。未知起点不能自动填造，可先保存草稿；不可访问区间明确标缺口，不承诺恢复。既有评论数量不能替代历史覆盖证据，也不据此回填过去人员成绩。

| 使用与价值 | 场景、搭配、性价比、复购意愿 | 适合通勤／与价格不符 |
| 原因不明 | 未说明原因、信息不足、待核查 | 不自行猜测质量或责任 |

消费者在评论中提到退货可以保留原文，按实际表达标注商品主题；不建立退货单或统计退货数量。八个一级主题已确认为一期字典，二级项按上表表达并提供证据，不因“原因不明”猜测归因。旧同名分类必须保留原 ID 并逐项映射确认，不能仅按名称合并。

### 10.2 分类状态与生效规则

| 状态／动作 | 要求 | 统计影响 |
| --- | --- | --- |
| 未分类 → 草稿 | 可以保存未完成信息，基于当前内容版本 | 草稿不进入确认主题和分类完成数 |
| 草稿 → 待复核 | 记录信息量、候选主题、证据和提交人 | 不作为已确认新分类 |
| 草稿／待复核 → 已确认 | 信息量不能为待判断；主题合法，有具体主题时给出原句／图片依据；确认内容版本一致 | 当前确认版本生效 |
| 仅评分 → 已确认 | 原始确无正文，确认信息量为仅评分，主题可以为空 | 计分类完成和评分，不虚构原因 |
| 证据不足但已完成复核 | 信息量用“信息不足（已复核）”及说明，分类状态为已确认，不用待判断冒充终态 | 计入分类完成数，不添加无依据主题，原因保持未知 |
| 已确认 → 修订草稿 | 说明新增／撤销标签和原因 | 同一内容版本原确认结果继续有效，草稿不改变统计 |
| 修订确认 | 比较旧新标签及影响，确认后保存新分类版本 | 新版本替代旧版本，保留历史 |
| 正文／评分内容更新 | 原确认标为不适用于当前内容，提示重新复核 | 当前分类完成数与确认主题中剔除旧内容分类；评分按当前有效评分规则更新 |
| 批量追加标签 | 预览明确记录集合与版本，先生成待复核建议 | 不自动新增确认主题；原有有效确认结果不被覆盖 |

同一内容版本可以同时显示“已确认，另有待复核修改”；这表示旧确认版本仍有效、草稿尚未生效。已确认但明显错误的分类可“撤回确认”，填写原因后变为待复核，当前确认统计同步扣除，保留旧版本。

一期采用受控主题字典，不允许分析人员在评论中随意新增同义标签。“反馈分析 → 查看分类规则”只读展示主题层级、解释、正负示例、规则版本、来源映射和引用数量。初始八主题及人工确认规则已经 D09 确认；后续变更按业务确认建立新版本，旧记录保留规则身份，不自动按同名合并。优先处理低评分和有具体内容的评论，同时保留有用好评；不要求全部评论立即完成人工分类，分类进度不阻断采集完成。

## 11. 页面四、五：商品评价汇总与反馈分析

### 11.1 商品评价汇总

默认维度为“店铺商品链接”，可切换 SPU、内部 SKU、店铺、渠道。默认分析近 30 天可信平台评论时间；用户可切换首次入库观察趋势，但界面明确“入库趋势”。时间未知记录不能确定属于这 30 天，单独显示“所选对象全部时间的评论时间待核验存量”，忽略当前日期范围但沿用对象筛选，并有独立下钻；不得与本期数量相加或共用分母。

| 区域 | 字段／内容 |
| --- | --- |
| 常用筛选 | 分析期间、渠道、店铺、SPU、SKU、平台商品 ID |
| 更多筛选 | 关联状态、最低样本量、数据覆盖状态；标签筛选属于明细观察，不默默改变商品差评率基础分母 |
| 统计卡 | 本期去重评论数、有效评分数、均分、差评数／率、有具体反馈数；全时间待核验存量置于独立提示区 |
| 默认列 | 当前维度对象、覆盖范围、已采评论数、有效评分数、均分、一至五星分布、差评数／率、具体反馈数、待分类数、最后成功覆盖、操作 |
| 条件列 | 平台销量、平台评论总数、平台评分、指标截至时间及来源；未接入显示未取得 |
| 行操作 | 查看评论、查看星级趋势、查看主题、打开商品档案 |

SPU／SKU 维度同时显示纳入店铺数和链接数。SKU 未确定的评论单列，不在已确定 SKU 间分摊。跨渠道比较展示渠道构成，不能把来源构成变化直接解释为商品改善。

点击某商品详情：顶部身份与样本范围，中部星级趋势和主要反馈，下部同范围评论。平台全量快照与已采样本放在不同区块，分别标注时间，不混成一个“总评数”。

当前筛选期间、当前比较对象的有效评分数少于 20 条时显示“小样本”；0 条显示“无有效评分”。不隐藏对象、不修改差评率、不自动判定好坏；达到 20 条也不代表结果已具统计可靠性。

提供“评分概览、问题反馈、正向反馈、数据待完善”四个页内视图，不新增侧边三级菜单。

| 视图 | 内容 | 下钻 |
| --- | --- | --- |

## 12. 采集完成判定与人员考核

### 12.1 任务范围与新鲜执行

任务目标在生成时固定并保存规则版本。每日任务应明确：哪个店铺、全部评分、目标时间窗口、应覆盖的链接范围或全店入口范围、截止时间。

每日任务 D 按 Asia/Jakarta 计算：核心窗口为 [D−1 日 00:00，D 日 00:00)，完整采集目标为 [D−7 日 00:00，D 日 00:00)，即昨日加此前六个完整自然日。核心和回看不是两项独立考核任务；一家店一天只有一项日常任务，完成须覆盖合计七日。D 日 18:00 为持久交付截止，对应北京时间 19:00；本日尚在产生的评论不属于当前固定窗口，若额外采到可正常保存，不能替代七日覆盖。

例如任务日为 2026-10-23：核心是雅加达时间 10 月 22 日 00:00 至 23 日 00:00；整体窗口是 10 月 16 日 00:00 至 23 日 00:00，交付截止为 23 日 18:00。采满昨日而前六日缺口未补齐时，任务仍为部分完成。近期重复上报增多属于七日回看的正常结果，不能按重复率直接处罚人员。

安排启用时明确首个任务日期。历史补采另建固定区间任务，先核对存量、优先近 90 天缺口，再向更早可访问历史推进；不能将全部历史欠账自动塞入今天任务。

连续漏采产生的旧任务缺口继续属于原任务，不因“上次成功时间”改变今天固定目标。一段新的有效采集若覆盖当前窗口和旧任务窗口，可以分别作为这些任务的证据；每个任务分别核验，旧任务仍按原截止判断逾期，同一评论新增产出只计一次。

每日完成仅表示约定窗口完成，不等于全部历史评论完整。首次历史补采单独记录起点、分段与缺口。平台晚展示的评论和修改需通过回看补采发现；有限回看不能保证发现所有长期历史修改，超出范围的限制必须可见。

当日任务需要针对该任务目标的真实新执行。旧文件重传不能凭当天上传时间构造新执行；执行 ID、载荷与时间证据须能够识别重放。仅有人工填报时间不能作为已核验新鲜执行的充分依据。评论时间存疑时，只有独立核实的平台原生筛选范围与结束证据可以证明目标窗口；没有该依据则覆盖待核验，不能使用疑似导入时间判断采全。

### 12.2 三层状态

| 层级 | 状态 | 含义 |
| --- | --- | --- |
| 执行 | 未开始、进行中、范围完成、部分完成、失败、覆盖待核验 | 表示规定范围是否实际检查结束 |
| 处理 | 未接收、已接收待处理、处理中、处理完成、存在失败异常 | 表示原始数据和处理结果是否可靠保存 |
| 任务 | 未开始、进行中、部分完成、已完成、失败；另附逾期标记 | 按下表派生，不由人工任意设置 |

| 情况 | 任务判定 |
| --- | --- |
| 无任何执行 | 未开始 |
| 有执行但尚未结束 | 进行中 |
| 范围不足、证据不足、真实评论未保存或 F／P 仍对应未解决数据缺口 | 部分完成，明确缺口类型；已经可靠补救的历史失败单列 |
| 执行失败且没有可用覆盖结果 | 失败 |
| 证据合格、规定目标覆盖完整（日常任务为合计七日，历史补采按任务固定区间）、必要处理完成且无未解决丢失 | 已完成 |

### 12.3 已完成必须同时满足

1. 店铺、渠道、任务目标和执行身份一致，证据属于有效执行。
2. 覆盖目标窗口及链接／入口范围，全部星级且不排除无正文或无图片评论。
3. 有正常结束依据；只记录页数、上报量或最大评论时间均不足以单独证明完整覆盖。
4. 本次范围内已抓取的真实评论原始记录和必要引用已持久保存，逐条结果有去向。
5. 无尚未解决的真实评论解析丢失、保存失败或处理中数据缺口；已经通过第 13.3 节修复引用得到可靠补救的旧失败不再阻断，但保留历史回执。所有评论满足有来源评论者的前提，按确定去重规则得到明确结果；不存在身份待核验完成特例。
6. 回执数量核对一致，覆盖与回执均可查询。

内部 SKU 未确定、人工分类未完成、人工译文未完成不阻断采集完成。原始图片引用已可靠保存、来源图片暂时无法打开，应标记媒体不可用；若采集工具漏掉平台实际提供的媒体字段，则属于采集数据缺口。不能以“过滤无效”掩盖真实评论保存失败。

零条结果必须有有效空结果和结束证据；没有上报不等于零评论。工具无法提供完整范围证据时，状态为覆盖待核验，不能自动标已完成；记录工具能力缺口，不自动认定员工怠工。

### 12.4 交付与入库分别计时

“完成交付”指实际范围采集已结束，且原始载荷、覆盖证据、执行与批次身份已经服务可靠持久保存、可回读，并产生接收回执。仅内存接收、开始上传、HTTP 200 或客户端本地保存都不构成交付。时间取满足全部条件的最早持久接收确认时点，不能取员工可任意修改的本地时间。

“任务完成”还要求必要处理去向明确且无数据丢失。若员工按时交付但服务后来处理失败，可以同时显示“按时交付、任务待处理”。考核分别展示这些事实，不用程序故障直接生成扣罚。日常任务的 18:00 是交付截止；完成时间也与同一截止比较，以便区分按时交付、处理延迟、按时完成和逾期完成。人工分类、译文及内部 SKU 关联完善不要求在 18:00 前完成。历史补采按 §8.4 单独约定的计划截止判断，单列进度，不套用日常任务的七日目标或每日截止。

| 指标 | 公式与规则 |
| --- | --- |
| 到期应采任务 A | 统计期间已到截止时间、按有效安排应执行的唯一店铺日任务数 |
| 考核分母 | 直接使用 A，不设免采扣减或额外分母集合 |
| 按时交付率 | A 中交付时间不晚于原截止时间的任务数 ÷ A |
| 完成率 | A 中截至报表时点已完成任务数 ÷ A |
| 按时完成率 | A 中完成时间不晚于原截止时间的任务数 ÷ A |
| 逾期完成 | A 中完成时间晚于原截止时间的任务数 |
| 未完成 | A 中截至报表时点仍未完成的任务数 |
| 待到期任务 | 已生成但未到截止的任务数，另列，不混入到期分母 |
| 人员新增产出 | 按首次成功新增记录对应的来源执行人和原执行／任务日期计，重复上报不增加产出；提交人和修复处理人不自动取得采集贡献 |

分母为零显示“不适用”，不显示 0% 或 100%。所有完成分子取自 A，满足“A = 已完成 + 未完成”和“已完成 = 按时完成 + 逾期完成”。今天尚未到 18:00 的任务列待到期，不纳入到期分母；当日状态仍可实时查看。历史补采单列进度，不进入每日完成率。九店启用后连续七日均已到期，对应 63 个应采任务，不能用“采过九家店”替代；每项任务回看七天也不把 63 乘以七。

### 12.5 固定责任、执行贡献与事实纠正

一个店铺日任务有且只有一个主责，在任务生成时保存责任快照。人员考核按该主责统计，实际执行人、提交人和协作贡献分别记录；多人共同完成仍只完成一项任务。一期没有任务临时改派，不重写已生成任务的责任或截止。未来长期安排变更只作用于未来尚未生成的任务。

一期不设免采申请、复核、状态或分母扣减。平台不可访问、服务故障、人员未执行等按实际原因记录，任务根据覆盖和保存情况显示失败／部分完成／未开始，不自动删任务或自动处罚。无新评论时，只要规定范围检查及有效空结果证据完整仍可完成；日常范围为七日，历史任务为其固定区间。

任务后来发现证据错误或评论保存缺失，可重新判定并保留旧状态和原因；既有导出保留原时点，重新出报表显示修订版本。不得删除失败历史来制造始终完成的记录。

## 13. 去重、评论更新和幂等

### 13.1 身份优先顺序

1. 能取得且核实范围的平台原生评论 ID：按其确定的渠道／市场／店铺／链接作用域建立稳定身份。
2. 没有原生 ID：使用带渠道、市场、稳定店铺、商品链接作用域及版本的组合指纹，保存现有 MD5 和原始字段；同作用域同指纹视为同一评论，不同指纹按不同记录处理。不设置疑似重复队列、人工身份复核或事后合并拆分流程。
3. 订单号、订单明细、平台规格、稳定用户 ID、原始时间用于来源展示和商品关联，不单独假设“一个订单只能一条评论”，也不新增身份推断流程。

当前规则为“链接 ID + 评论人名称 + 正文 + 评分 + 评分时间”。目标组合键为渠道／市场／稳定店铺作用域下上述五字段的 MD5，固定编码、字段分隔、空值表达、时间格式和精度，保留原文、旧指纹及算法版本。翻译文、分类标签及人工商品关联不参与计算；不因新增规范立即重算或删除历史真实记录。原生 ID 是否可用及现有 MD5 实现仍由研发核对，不能将目标设计描述为已上线。

所有评论有评论者不等于有稳定的原生评论 ID；姓名可变且脱敏名称可能相同。没有原生 ID 时，买家改名、改文或改分可能生成不同指纹，按本期规则会计为不同记录；相同五字段也存在误判重复的局限。这里明确算法边界，不追加身份核验、相似度猜测或评论者缺失业务。字段完整性由来源契约保证，不能虚构姓名使数据满足前提。

### 13.2 判断与处理表

| 场景 | 处理 |
| --- | --- |
| 稳定评论身份相同、内容相同 | 同一评论的重复观察；新增不增加，记录最近观察 |
| 稳定评论身份相同、内容确实更新 | 保存新版本，归为更新，不增加唯一评论数 |
| 同一批次原样重试 | 返回原结果或续处理失败项；不新增逻辑批次和产出 |
| 同批次 ID 但载荷或来源身份改变 | 拒绝作为重试，显示冲突并保留旧回执；新增采集、追加记录或修复后的新载荷必须用新批次 ID，并关联原执行和修复原因 |
| 不同批次同时提交同一身份 | 持久层保证仅一个首次新增，其余记录重复或合法更新 |
| 无原生 ID、同作用域且组合指纹相同 | 按确定规则记重复，保留本次来源和对应评论；不产生待核验状态 |
| 无原生 ID、组合指纹变化 | 按新指纹处理，不推断为旧评论编辑；原记录保留，不建立人工合并流程 |
| 不同链接各有相同文字 | 不因文本相同跨链接去重，按各自明确身份作用域处理 |
| 同一评论后续补齐 SKU 关联 | 更新关联版本，不产生新评论 |

本期处理结果直接由确定规则产生。评论者非空是来源契约和 Mock 的必备条件，不能用默认姓名、隔离记录或人工补录来替代；也不能把身份争议换名为 F／P，继续保留已取消的身份工作流。

### 13.3 批次和数量

每个批次的上报记录只归入一种当前结果：

U = N + M + D + X + F + P

- N：按当时处理版本首次创建唯一评论的上报记录，界面称“入库时新增记录”。
- M：更新已存在评论的上报记录；可以包含明确的来源内容更新。
- D：相同身份且没有需要更新的重复记录。
- X：有明确理由的非评论或确定不适用来源，保留原始记录和原因。合法评论只是超出当前任务日期时，应按真实身份正常保存，但不借它证明任务窗口；不能仅因不属于本次考核区间而丢弃。
- F：该处理版本中的失败来源记录；是否已被成功修复引用补救单独记录，页面同时显示未解决数与已补救数。
- P：已上报但尚未完成处理、尚无明确结果的来源记录，不表示待人工判断评论身份。

同一条评论在一个批次出现两次时，可以一条 N、一条 D；因此 U 不是唯一评论数。同一评论多次真实更新可能产生多条 M，更新次数与更新评论数应分别命名。

重试计数使用逻辑批次当前处理版本；尝试日志保留但不累加到 U。F／P 后续处理产生新版本，逐条去向转移仍满足守恒，旧回执不可覆盖。独立站写入数作为外部同步事实保留时也不加入本模块 N。

修复改变载荷而采用新批次时，新增“修复引用”：原执行／批次／来源记录、原错误、新批次及对应保存结果、验证依据、确认人和时间。只有能证明该缺失评论已可靠保存、来源一致且目标范围得到满足，才关闭原缺口；仅出现另一个“成功批次”不能自动关闭全部失败。原回执的 F 和尝试历史保留，当前任务显示“历史失败已补救”，按尚未解决的数据缺口判定完成，不要求每个历史尝试都从未失败。

原 P 仍有后台处理时，要有可核对的来源结果或可靠修复引用才能认定该条缺口已闭环；后续原批次再处理必须遵守相同身份幂等。覆盖缺口可由新的完整覆盖证据关闭，已知真实评论保存缺口仍需明确对应保存结果，不能仅用重新翻页成功替代。

一期不做事后身份合并、拆分和身份调整差额。新增贡献归属首次成功创建评论的来源执行；并发时以最终持久提交顺序确定，仅一个来源计 N。正常重试完成、处理延迟或失败修复时，新增入库量按首次成功保存时间统计，人员贡献仍归该条来源执行人和原任务，不归提交人或研发修复人。另一次独立采集先成功新增的，贡献归该独立执行；不能因前一失败尝试发生得更早就重复计功或倒改归属。评论合法更新不改变首次新增归属。

### 13.4 保存与版本要求

数据库普通索引不能代替唯一性约束。实现时需核对现有持久层唯一约束与提交幂等；确认保存完成才发布成功回执。评论、必要来源关联和该结果应能一致回读，不能出现页面显示新增成功但评论不存在。

原生评论 ID 模式下，有稳定平台版本或修改时间时按来源版本判断；仅采集时间较新不保证正文较新，缓存或迟到数据不得覆盖已有新版本。版本不可比较时保留来源观察且不覆盖当前正文，不另建身份待办。组合指纹模式依第 13.2 节处理，不推断跨指纹更新。

不在本次方案阶段修改数据库、清理历史真实评论或重算全部旧 MD5。历史切换另需明确保留范围、核查样本、回退和消费者，不能按演示数据清理真实资料。

## 14. 统计口径

### 14.1 基础集合与日期

每个报表先确定渠道、店铺、对象、期间、日期类型和统计时点，再按确定去重规则形成成功入库的评论集合；规则可以是平台原生身份或带版本的组合指纹，详情保留使用方式。来源错误或尚未成功处理的上报不伪装为已入库评论，所有正常评论均有评论者。

评论发生趋势使用可信平台评论时间；“新增入库量”使用首次成功创建评论的入库时间；人员考核使用任务日期；执行量与“采集新增产出”使用来源执行日期或原任务归属，按报表时点的实际处理结果统计。所有页面用完整名称，不用一个模糊“新增量”同时表示这两类时间口径。

例如昨日采集的同一来源批次今日才处理成功且首次新增：今日新增入库量增加，采集产出仍归昨日原执行人和原任务；既有导出保持原时点，新报表显示新的处理结果。实际执行人、上传人和修复人不能混为一人。评论发生时间未确认时仍可查看，计入独立的时间未知存量，不直接放进某天的评论发生趋势。

默认分析使用统计时点已确认的当前评论版本，评论修改可能使旧发生日期的均分重算。页面和导出必须声明这一点；固定历史导出带时点和版本，不自动改写。按当时版本回放历史不是一期默认能力。

### 14.2 评分指标

设 C 为同一基础范围内已确认唯一评论，V 为其中评分在 1～5 的评论，L 为其中按已确认差评规则判为差评的评论。

| 指标 | 公式／规则 |
| --- | --- |
| 已采评论数 | C 的条数 |
| 有效评分数 | V 的条数，含无文字评价 |
| 评分未知数 | C − V，保留原始值，不按零星计 |
| 平均评分 | V 的评分总和 ÷ V 的条数 |
| 某星级数量／占比 | 该星级去重评论数；占比为该数 ÷ V |
| 差评数／率 | L 的条数；差评率为 L ÷ V |
| 有正文数 | 有真实正文的去重评论数，不把页面占位符自动当作原始正文 |
| 有图数 | 来源提供图片引用的去重评论数，媒体当前可用性另列 |
| 具体反馈数 | 当前内容版本已确认分类为具体反馈的去重评论数 |

已确认本系统业务口径：1～2 星差评、3 星中评、4～5 星好评；这不是对平台自身等级规则的断言。所有有效评分均在 V 中，含仅评分评论。四五星含问题内容时仍进入问题主题，不修改其原始星级。

页面显示四舍五入后的均分与百分比，计算保留原始分子分母，不用显示值继续计算。样本为零时比例不适用。SPU／SKU 汇总直接汇总唯一评论的评分，不平均链接均分。

### 14.3 主题分析

| 分析 | 分子 | 分母 |
| --- | --- | --- |
| 全星级主题提及率 | 当前范围内命中主题的确认去重评论数 | 当前范围 C；同时展示分类完成率，结果是已识别提及而非全部真实发生率 |
| 差评主题提及率 | L 中命中主题的确认去重评论数 | L；无文字差评和未分类差评仍在分母 |
| 已分类评论内主题占比 | 已分类集合中命中主题的去重评论数 | 同一已分类集合；必须使用该完整名称 |
| 分类完成率 | 当前内容版本已确认分类的去重评论数 | C |

多标签同一评论可命中多个主题，各主题占比之和可能超过 100%；“问题评论总数”必须对这些评论再次去重。四五星也可进入问题主题，一二星也可能带正向反馈。

使用标签或星级观察筛选时，明细数量随之变化，但商品差评率仍使用独立标注的基础范围 V；若无法清晰展示双重范围，则该处不展示差评率，禁止出现误导性的差评占比 100%。

### 14.4 外部指标和多维汇总

- 平台评分、累计评论数与平台销量均来自带来源的指标快照，显示截至时间、覆盖区间与单位。
- 平台销量可能是订单数、销量件数或其他定义，未确认单位不混合相加。
- 累计快照使用目标时点适用的一份，不相加每天的累计值；差值只有在同一口径连续可比时才能作为新增指标。
- 采集评论总数与平台总数只有在范围、时点、去重及计数定义一致时才能计算比例；否则仅并列展示，不能标“完整率”。
- 平台均分缺少可比较的评分总和和评分数时，不汇总为跨链接精确均分。
- SKU 汇总仅纳入有可靠内部 SKU 关联的评论，未确定项另列；SPU 总数可以大于已确定 SKU 合计。
- 链接级销量、评分不得复制到每个 SKU。没有 SKU 级来源时 SKU 外部指标显示未取得。
- 同一 SKU 多店多链接的真实独立评论可合计，但同一评论身份在该 SKU 汇总中只计一次。
- 维度对比同步显示样本、渠道构成、覆盖及分类完成率。采集缺口不能被描述为差评下降。

若需接入历史真实数据，单独确认来源、范围、身份映射与处理方式；保留来源记录，不在方案阶段清理、覆盖或迁移。原型只使用两页内、合法且来源明确的演示场景，不复制整库评论作 Mock。
