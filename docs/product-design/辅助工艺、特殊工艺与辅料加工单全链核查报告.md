## 1. 修复前结论与问题基线（历史）

修复前总体状态为：**代码与本地页面核查完成，但存在对象身份和链路缺陷，且现实 PDA 逐项验收尚未完成。**

- 17 种通用工艺都能形成加工单列表、详情和打印适配结果；当前共 129 张加工单。
- 当前 Mock 中每个来源任务最多只有 1 张加工单，因此日常演示掩盖了“一任务多加工单”缺陷；构造该场景后，PDA 明确把用户选中的第二张加工单重新解析成第一张加工单。

### 1.1 更新后的业务主线判定

本次讨论进一步确认：对于本报告范围内的辅助工艺、特殊工艺、捆条、盘扣、橡筋定长切割和花边辅料加工单，**任务只在接单阶段是核心对象；生成具体加工单后，加工单是执行、交出、仓库、质检、结算、打印和追溯的全生命周期主线**。

```text
任务：报价、竞价、中标、接单、工厂分配、价格和交期
└── 加工单：接单后的唯一业务主线
    ├── 确认接收记录
    ├── 加工填报批次
    ├── 交出批次
    ├── 仓库实收、差异与库存记录
    ├── 质检批次
    ├── 结算明细
    └── 打印与操作日志
```

交出单、收货记录、库存记录、质检记录和结算明细可以拥有独立记录 ID，以支持分批、幂等和审计；但它们都是具体加工单的子事实，不能只关联任务，也不能从任务反查第一张加工单。

分批数量链必须以同一 `workOrderId` 累计：

- 可交出数量 = 累计加工完成产出 - 累计已交出。
- 待实收数量 = 累计已交出 - 累计已实收，差异单独记录。
- 待质检数量 = 按质检规则可送检数量 - 累计已质检。
- 可结算数量 = 按业务规则认定的合格/实收/完成数量 - 累计已结算。
- 任务只汇总子加工单进度；任一加工单完成不得直接完成整个任务。
- 对存在来源任务的加工单链，只有任务下至少存在一张加工单且每一张加工单都已完成时，任务才由系统自动完成；PDA 和 Web 都不提供“完成任务”操作。
- 取消、作废或未生成加工单不等于“加工单已完成”；如需把这些状态计入任务关闭，必须另行确认规则，当前不得擅自等同。

### 1.2 Web 与 PDA 的动作口径

Web 端已经业务讨论确认，加工单只保留四个主动作：

1. 确认接收。
2. 加工填报。
3. 发起交出。
4. 完成加工单。

PDA 不另建一套业务动作或状态账，而是用更少的阅读、选择和输入完成同四个动作：

- “接单”只展示任务、报价、竞价、中标和确认接单。
- “执行”以加工单为卡片和扫码结果，承载“加工填报、完成加工单”。
- “交接”以加工单为入口，承载“确认接收、发起交出”。
- 已知的加工单号、生产单号、菲票、SKU、工厂、操作人、时间、计划量、累计量和可操作剩余量尽量由扫码和系统自动带出。
- 实际收到、本次完工、本次交出、差异原因等现场事实仍必须输入或明确确认；“少填”不等于默认全部剩余量或无确认提交。

本范围明确不出现以下操作、字段、凭证要求、节点记录、配置入口或完成门禁：

- 开工。
- 开工凭证。
- 关键节点上报。
- 补报关键节点。
- 查看开工和节点。
- 手工完成任务。

确认接收后，加工单按既有加工状态继续执行，但不额外产生“开工”业务事件；第一次加工填报也不自动生成开工记录。每张加工单仍由员工执行“完成加工单”，来源任务则在全部加工单完成后由系统聚合完成。

上述排除只约束本报告中的辅助工艺、特殊工艺、捆条加工单和适用的辅料加工单，不删除三方小缝纫工厂现有的开工和关键节点能力。印花、染色专用加工单链另行核查，不使用本报告结论直接改造。

## 5. 关键问题与直接证据

### P0-01：PDA 选中加工单后丢失 `workOrderId`

**代码已确认**：

1. 扫码解析能先找出具体 `SpecialCraftTaskOrder`，并支持同一生产单返回多张候选。
2. 候选接口只公开 `taskId`，页面按钮只有 `data-task-id`。
3. 进入详情时调用 `getSpecialCraftPdaCandidateByTaskId(taskId)`，内部用 `.find()` 查第一张 `sourceTaskId === taskId` 的加工单。
4. 找到加工单后，最终动作载荷的 `sourceId` 才重新取 `workOrder.taskOrderId`。因此写回服务本身以加工单执行，但进入服务前可能已经选错加工单。

实现位置：

### P0-02：交接、仓库、质检和结算没有统一以加工单为主线

`ensureSpecialCraftUnifiedWarehouseArtifacts()` 写入入仓、待加工、待交出和出仓事实时只设置 `taskId/taskNo`；记录 ID 字符串中虽嵌入加工单 ID，但没有可用的结构化 `workOrderId`。仓库页面再把 `item.taskId` 传给 `buildSpecialCraftTaskDetailPath()`。

- `src/pages/process-factory/special-craft/warehouse.ts:363-370,850-869,940-955`

页面复现：辅助工艺待加工仓中点击烫钻记录 `TASK-AUX-202603-084-0004-09` 的“查看加工单”，进入任务 ID 路径后显示“未找到对应加工单详情”。

证据：`generic-warehouse-taskid-detail-failure.png`。

更新后的全链分类核查表明，这不只是仓库详情跳转问题：

- 通用 PDA 交出单头主要保存 `taskId/sourceTaskId`，并按任务查找或创建交出单；一任务多加工单时，无法表达本次交出属于哪张加工单。实现位置：`src/data/fcs/pda-handover-events.ts:349-405,4120-4274`。

- 通用质检建单与质检详情仍以任务为主要来源，页面存在“关联生产单 / 工厂 / 任务”和直接填写任务 ID 的路径，不能稳定定位到具体加工单的某批产出。实现位置：`src/pages/pda-quality.ts:350-464`、`src/pages/qc-records/context.ts:450-465`。
- 普通收入流水仍标记为“任务收入流水”并跳回接单任务；这与“具体加工单的分批完工/实收/合格数量形成结算明细”的新口径不一致。实现位置：`src/data/fcs/settlement-linked-mock-factory.ts:1200-1250`。

正确关系不是取消交出记录、库存记录、质检记录和结算明细的独立 ID，而是要求每条子事实必须保存 `workOrderId`，必要时再保存本次产出批次、交出批次或收货批次 ID。`taskId` 只作来源合同和汇总追溯，不参与选择具体执行对象。

### P1-04：Web 与 PDA 的数量确认语义不一致

## 6. Web 与 PDA 动作差异判定

业务动作以 Web 已收口的四动作为唯一事实：确认接收、加工填报、发起交出、完成加工单。PDA 可以简化展示和输入，但不得新增第五种业务状态，也不得用任务操作代替加工单动作。本范围不继承通用任务执行页的开工、开工凭证、关键节点上报、补报或节点查看能力。

| 项目 | Web 当前行为 | PDA 当前行为 | 判定 |
|---|---|---|---|
| 执行对象 | 详情和动作面板直接持有 `taskOrderId` | 候选选择后只保留 `taskId`，详情再取第一张加工单 | **对象串写风险，P0** |
| 确认接收 | 逐 SKU / 逐菲票确认数量 | 在交接 Tab；普通工艺默认提交全部剩余 | **功能语义不一致，P1** |
| 加工填报 | 逐 SKU / 逐菲票确认完工 | 在执行 Tab；普通工艺默认提交全部剩余 | **功能语义不一致，P1** |
| 发起交出 | 逐 SKU / 逐菲票确认交出 | 在交接 Tab；普通工艺默认提交全部可交出 | **功能语义不一致，P1** |
| 完成加工单 | 汇总核对；累计加工填报必须大于 0，不依赖是否已交出或交出多少 | 在执行 Tab；同一服务门禁，完成后仍可从交接继续交出剩余产出 | 端侧位置差异可接受；加工与交出为独立数量维度 |
| 完成任务 | 不应提供手工操作 | 不应提供手工操作 | **目标规则：任务下全部加工单完成后自动完成；当前需补聚合契约** |
| 工厂隔离 | `FAC-APF`、`FAC-SPF`、`FAC-FLOWER` 按加工单隔离 | 扫错工厂明确阻断“该单不属于当前登录工厂” | **当前通过** |
| 超量 | 服务阻断接收、完工、交出超量 | 共用服务门禁 | **当前通过** |
| 重复提交 | 无通用特殊工艺 `confirmationKey` | 无通用特殊工艺 `confirmationKey` | **缺独立幂等契约，P1** |
| 必需菲票 | 可出现“无菲票”并继续操作 | 同一加工单仍可能进入 PDA | **追溯门禁缺失，P1** |
| 错误/模糊扫码 | 精确匹配；错误工厂阻断；一个生产单多单时让用户选择 | 识别阶段正确 | 识别通过；选择后的身份丢失为 P0 |

### 6.1 PDA 少填、多扫码的目标操作

| 动作 | 优先扫码 | 系统自动带出 | 现场必须输入或确认 |
|---|---|---|---|
| 确认接收 | 加工单码；裁片工艺可继续扫菲票；成衣/辅料可扫 SKU/物料码 | 加工单、工厂、对象、应收量、单位、已收和剩余 | 本次实收数量；有差异时的差异量和原因 |
| 加工填报 | 加工单码或具体菲票/SKU/规格码 | 可填报剩余量、累计完工、对象图片和单位 | 本次实际完工数量；必要的差异/备注 |
| 发起交出 | 加工单码；可连续扫本次交出的菲票、批次或 SKU | 可交出数量、去向仓、累计已交和未交量 | 本次实际交出数量；与系统数不同时的原因 |
| 完成加工单 | 当前加工单上下文即可，无需再填数量；从外部进入时扫加工单码 | 计划、完工、已交、未交、差异和门禁结果 | 一次明确完成确认；门禁不通过时只显示如何处理 |

补充规则：

- 扫加工单码可唯一进入；扫生产单或任务码时，如果对应多张加工单，只展示紧凑候选，不自动选第一张。
- 扫菲票、SKU 或规格码时，系统应同时确定具体加工单和明细；存在歧义时阻断。
- 剩余量可以作为默认值减少输入，但数量必须在提交前保持可见、可修改且由操作人确认。
- 可由系统判断的工厂、仓库去向、任务来源、操作人、时间、单位和累计量不让一线重复填写。
- 必填未填、超量、扫错对象、重复提交、错误工厂和状态不允许必须阻断；无法判断时给出“叫主管处理”。

## 7. 捆条与盘扣必须继续分开

本轮再次确认：

- **捆条加工单（BIND-01）**：裁床内部把面料按物料、纸样和规格切成捆条，产出单位是米，每个规格生成捆条菲票。
- **盘扣加工单（AUX-10）**：辅助工艺厂接收捆条菲票，投入按菲票张数追溯，捆条长度只作追溯，盘扣产出和交出按个，去向为中央辅料仓。

不能把捆条加工单并入盘扣任务，也不能让 PDA 只打开裁床任务后推断某一张捆条加工单。正确关系应为：任务负责分配，捆条加工单负责执行；一任务允许有多张捆条加工单，盘扣再引用具体捆条菲票。

按本次新确认的四动作口径，捆条的“记录裁剪”应收口为加工填报，“结束加工”应收口为完成加工单，并补齐确认接收和分批发起交出。菲票查看/打印是加工单辅助能力，不增加第五个主流程动作。

## 12. 最终判定

业务对象最终判定为：**接单阶段以任务为核心；接单后，加工单是确认接收、加工填报、分批交出、仓库实收与库存、质检、结算和打印的唯一业务主线。** 任务号可在加工单基本信息中弱化展示，但不能用于反查并选择具体加工单；任务不允许手工完工，只能在其全部加工单完成后由系统自动完成。

本报告范围最终动作边界为：加工单只有“确认接收、加工填报、发起交出、完成加工单”四个员工主动作；没有开工、开工凭证、关键节点上报、补报关键节点、查看开工和节点。三方小缝纫工厂、印花加工单和染色加工单不使用本报告直接改造。
