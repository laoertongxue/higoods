## 0. 方案结论

### 0.1 本次调整的根本原则

本方案以当前原型为唯一实施载体。当前原型基本对应线上业务，尤其后道工厂管理已经形成较完整、较接近现场的页面和操作闭环，因此后续采用以下方式：

1. 保留当前应用菜单、页面入口、页面布局、详情结构、PDA 入口、打印入口和主要操作动作。
2. 保留当前已经成立的专项业务单据，不新建一套“万能加工单”替换染色单、印花单、裁片单、毛织单、辅助工艺单、后道加工单等现有单据。
3. 在现有技术包工序数据、技术包快照、生产任务、专项加工单和后道全流程数据上补充缺失的身份与关联。
4. 对业务结论已确认错误的局部逻辑做定点替换，例如全局默认顺序、裁片印花、空后道项目仍进复检、后道完工再次质检等。
5. 对新旧并行逻辑先停止旧入口继续产生新事实，再迁移消费者，最后删除旧代码；不以“一次性重写”换取表面上的整洁。
6. 每个阶段完成后，当前原型仍应可以独立演示和回退；不能等待全部模块重做完成后才恢复可用。

### 0.2 当前原型保留什么

| 现有能力 | 处理结论 | 原因 |
|---|---|---|
| 技术包中的工序卡片、上下移动、设置并行、编辑、来源关系、路线确认 | 保留并扩展 | 已经具备受控编排的业务雏形，LogicFlow 应成为同一份数据的可视化视图，不应另建编辑器 |
| 技术包版本和生产单绑定的技术包快照 | 保留并扩展 | 已经是版本隔离的正确承载体，只缺少对象分支、节点 occurrence 和显式边 |
| 准备阶段染色、印花、水溶等专项加工单 | 保留现有页面和单据类型 | 单据职责、现场操作和数量单位不同，不适合被统一单据替代 |
| 裁片、毛织、车缝、辅助/特种工艺、花边等专项域 | 保留现有业务域 | 只补路线来源、前后任务项和实际交接关联 |
| 后道工厂管理的菜单、列表、详情、仓库、QC、出货、日志、授权页面 | 全部作为后续迭代基础 | 当前链路已经覆盖主要角色和动作，问题集中在有限数据来源和少数分支规则，不在页面架构本身 |
| 后道自助回货登记后再确认实收 | 按当前模式保留 | 这是当前实际模式；扫码登记即实收只作为未来模式，不在本轮实现 |
| 后道责任由本次三方任务范围决定，QC 冻结最终项目 | 保留 | 当前新全流程已有正确基础 |
| 历史记录读取 | 在迁移期保留只读兼容 | 避免现有演示记录和页面突然失效；兼容期结束后删除旧写入与旧实体 |

### 0.3 只做哪五类结构性调整

1. **工艺路线对象化**：从“一款一个工序名”调整为“款式 × BOM 物料分支/纸样部位/成衣分支 × 工艺节点 occurrence”。
2. **路线拓扑显式化**：在现有技术包工序条目上保存真实前后关系，并用 LogicFlow 可视化；不再用全局默认顺序和相邻步骤全连接推导业务关系。
3. **准备、生产承接明细化**：在现有加工单详情中增加“需求来源、前置任务项、后置任务项、任务明细”的只读追溯，并用实际交出/接收事件控制可接收数量。
4. **后道局部纠偏和正式数据接入**：保留整个后道模块，只修正空项目直达成衣仓、处理完成不再质检、统一“烫包”、排除 KOL 等已确认差异，并把有限 Mock 数据源换成正式生产任务分配的适配入口。
5. **旧逻辑渐进收口**：为每套并行模型明确“当前权威源、只读适配、停止新写、迁移验证、删除”的顺序。

### 0.4 明确不做什么

- 不新建一套替代现有后道工厂管理的页面或模块。
- 不改变后道现有菜单层级和用户找单路径。
- 不把全部专项加工单改造成一张通用加工单。
- 不把后道硬套成“加工前—需求来源—加工后”的静态工序链。
- 不让技术包锁定生产单实际物料 SKU、批次、数量或工厂。
- 不把 LogicFlow 做成任意拖拽、任意连线、任意节点的通用流程设计器。
- 不迁移为 React，不改动当前 Vanilla TypeScript 页面体系。
- 不让系统因数量达到或下游收货而自动完成加工单或生产单。
- 不增加中间工序质量放行；整个生产只在成衣回到后道时做质量判断。
- 不把未来“扫码回货登记即确认实收”伪装成当前能力。

## 2. 增量后的整体业务结构

### 2.1 三层信息各自负责什么

```mermaid
flowchart LR
  A[技术包现有工艺条目] -->|补对象分支和显式前置关系| B[生产单现有技术包快照]
  B --> C[现有准备/生产需求与专项加工单生成器]
  C --> D[现有染色/印花/裁片/毛织/辅助工艺等单据]
  D -->|实际多次交出/接收| E[最小任务项关联索引]
  E --> F[现有下游专项单据]
  F --> G[成衣回货批次]
  G --> H[现有后道回货确认与唯一到货 QC]
  H -->|项目为空| I[直接生成成衣仓数量交接]
  H -->|项目非空| J[现有后道加工单与交出链]
```

这不是新增六套系统，而是给当前原型补齐三层职责：

| 层次 | 继续使用的当前载体 | 只回答什么 | 明确不回答什么 |
|---|---|---|---|
| 技术包路线 | `TechnicalProcessEntry` 及现有技术包标签 | 本款每条物料/部位分支需要经过什么工艺、先后和汇合关系 | 实际 SKU、批次、数量、工厂、这次是否换料 |
| 生产执行 | 现有生产单快照、需求、任务和专项加工单 | 这张生产单实际上对什么物料/裁片/成衣做多少、由谁做 | 不能反向修改未来技术包版本 |
| 实物交接 | 现有加工单明细、交出/接收记录，加一层最小关系索引 | 哪个上游明细的哪批数量交给了哪个下游明细 | 不定义款式固定路线，不代替单据完成 |
| 后道动态处理 | 现有后道全流程模块 | 本次回货质量、返厂、本批最终后道项目和成衣仓交接 | 不受技术包静态后道节点控制 |

### 2.2 为什么不建立“通用加工单大模型”

染色、印花、裁片、毛织、车缝外发、裁片辅助工艺和后道处理在对象、单位、来源、现场动作和完成凭证上都不同。当前专项单据已经表达这些差异。真正缺失的是它们之间的稳定身份和承接关系，而不是另一张更抽象的单据。

因此本方案只增加一个**轻量关联索引**，引用现有单据和明细，不复制数量账和状态：

| 字段 | 业务含义 |
|---|---|
| 关联 ID | 一次明确的上游任务项到下游任务项关系 |
| 生产单 ID | 限定在同一张生产单执行事实内 |
| 上游路线 occurrence ID | 对应技术包快照中的上游节点 |
| 下游路线 occurrence ID | 对应技术包快照中的下游节点 |
| 对象分支键 | 指明同一 BOM、纸样部位、毛织部位或成衣分支 |
| 上游单据类型/单号/明细 ID | 指向现有上游加工单明细 |
| 下游单据类型/单号/明细 ID | 指向现有下游加工单明细 |

实际交出数量、接收数量、时间、操作人继续写在各专项域已有的交接记录中；关联索引只负责“这条记录属于哪两个任务项”，避免形成第二套库存账。

### 2.3 后道为什么不加入通用前置/后置字段

准备、生产阶段的前后关系是“同一加工对象按工艺路线继续加工”。后道不是技术包预先确定的下一道工艺，而是成衣回货以后由唯一 QC 根据本次外发任务范围和现场质量动态决定。

因此：

- 准备、生产详情可以增加“需求来源、前置任务项、后置任务项、任务明细”。
- 后道继续展示“本次三方任务范围、回货批次、确认实收、QC 结论、最终项目、处理数量、后续仓库去向”。
- 后道页面不增加含义模糊的“加工前、需求来源、加工后”四块通用模板。

## 3. 技术包“工艺路线”的增量调整

### 3.1 页面承载方式

当前 `工序工艺` 标签不删除，只把用户可见名称改成 `工艺路线`。标签内部保留现有卡片和编辑弹窗，并增加两个视图：

1. **路线图**：LogicFlow 渲染的受控路线，用于查看对象分支、连接、串并行和汇合。
2. **工艺明细**：现有步骤卡片、来源关系和批量辅助的优化版，用于看完整字段和编辑细节。

两个视图读取和修改同一份 `state.techniques`；不是一边保存一份列表、另一边再保存一份图。切换视图不能改变路线，刷新后两边必须一致。

### 3.2 节点唯一性

当前一种工序码只生成一个自动节点，必须调整为：

`技术包版本 + 来源分支 + 工艺代码 + 作用对象 + occurrence ID`

示例：

- 主面料 A 的染色是一个节点。
- 主面料 A 的印花是另一个节点。
- 里料 B 只有染色，是第三个节点。
- 花边 C 的染色是第四个节点。
- 纱线 D 的染色是第五个节点。
- 前片的烫画和整件成衣的烫画必须是两个不同 occurrence。

工序代码用于说明节点类型，不能继续充当节点身份。

### 3.3 在现有条目上增加的最小字段

| 建议字段 | 是否新建模型 | 作用 | 是否锁死执行物料 |
|---|---|---|---|
| `routeObjectKey` | 否，扩展现有条目 | 稳定标识 BOM 行、纸样部位、毛织部位或成衣逻辑分支 | 否 |
| `inputObjectType` | 否 | 仅说明投入类型，如布料、纱线、裁片、毛织片、成衣 | 否 |
| `outputObjectType` | 否 | 仅说明产出类型 | 否 |
| `consumedBomItemIds` | 否 | 区分主加工对象和被消耗辅料，例如装扣子时主对象是成衣、扣子是消耗品 | 否 |
| `predecessorEntryIds` | 否 | 保存该 occurrence 的直接前置节点 | 否 |

`routeStepNo`、`routeLaneNo`、`routeParallelGroupId` 暂时保留，作为现有列表显示和旧消费者兼容投影；确认路线时根据显式边重新计算，不能再反过来作为唯一业务真相。

后置节点不重复存一份；由所有节点的 `predecessorEntryIds` 反向计算，避免两边不一致。

### 3.4 各来源怎样进入当前路线

| 来源 | 自动形成什么 | 用户能做什么 | 用户不能做什么 |
|---|---|---|---|
| BOM 原物料的水溶/染色/印花要求 | 每条 BOM 行、每个选中工艺各形成一个准备节点 | 排列本物料分支内先后、连接合法下游 | 不能把来源改成别的 BOM，也不能把多个同名工艺强制合并 |
| 布料 BOM | 形成该布料分支的默认裁剪节点；纯整件毛织主干除外 | 连接准备工艺产出到裁剪 | 不能把裁剪改成“裁片”工艺名 |
| 物料与纸样关联的辅助/特种工艺 | 形成绑定具体纸样部位的生产节点 | 调整该部位工艺顺序、与其他分支汇合 | 不能生成“裁片印花”；图案类使用烫画/直喷 |
| 成衣 BOM 的烫画/直喷选择 | 每个选择形成成衣对象的生产节点 | 排列成衣工艺 | 成衣 BOM 不展示其他普通准备/裁片工艺 |
| 整件毛织纸样类别 | 形成纱线到成衣的毛织节点 | 查看后续进入后道 | 不自动加入普通裁剪/车缝主干 |
| 部位毛织纸样类别 | 形成纱线到毛织横机片的节点 | 连接到裁床待交出和车缝汇合点 | 不把毛织片降格成普通裁片来源 |
| 人工新增生产工艺 | 使用当前新增弹窗，在字典允许范围内新增 | 选择合法对象和来源 | 不允许无来源、无对象的任意节点 |
| 产品资料中的扣眼、纽扣、包装要求 | 只在相应产品资料区域展示 | 查看产品要求 | 不进入技术包固定后道路线，不替代本批 QC |

### 3.5 类型级加工对象与转换

技术包只保存类型，不保存这张生产单实际换用的物料 SKU。首批至少按下表校验：

| 工艺/节点 | 技术包投入类型 | 技术包产出类型 | 关键业务边界 |
|---|---|---|---|
| 水溶 | 对应 BOM 原物料 | 同类 BOM 原物料 | 是否独立成单由现有水溶/染色规则处理，路线 occurrence 仍保留 |
| 染色 | 面料、纱线、花边等对应 BOM 原物料 | 染色后的同类原物料 | 不再硬写成只有面料 |
| 印花 | 可印花的 BOM 原物料 | 印花后的同类原物料 | 不允许已裁裁片；裁片图案用烫画/直喷 |
| 裁剪 | 布料 | 裁片 | 布料默认有；纯整件毛织主干没有 |
| 整件毛织 | 纱线 | 成衣 | 直接进入普通后道回货链，KOL 除外 |
| 部位毛织 | 纱线 | 毛织横机片 | 回裁床待交出仓，与其他裁片共同交车缝 |
| 绣花、打条、压褶、打揽、贝壳绣、曲牙绣、一字贝绣花、打褶、烫钻 | 指定裁片/部位 | 加工后的同一裁片/部位 | 压褶和打褶不同；仅保留曲牙绣 |
| 烫画、直喷 | 明确选择的裁片或成衣 | 加工后的同一裁片或成衣 | 两种对象都合法，必须分别绑定来源 occurrence |
| 花朵 | 指定裁片部位 | 由该裁片部位形成的花朵部件 | 当前业务不是外购独立花饰 |
| 盘扣 | 对应制作物料/部件 | 盘扣辅件 | 与把盘扣装到成衣不同 |
| 布包扣 | 对应制作物料 | 包布钮辅件 | 不得归为装扣子 |
| 开扣眼 | 成衣 | 已开扣眼成衣 | 只在后道 QC 动态项目中，不进技术包路线 |
| 装扣子 | 成衣；另消耗扣子 | 已装扣成衣 | 主对象不是扣子辅料，只在后道 QC 动态项目中 |
| 烫包 | 成衣 | 可交成衣仓的成衣 | 是否由三方完成或我方处理由任务范围和 QC 决定 |

### 3.6 路线边的业务含义

一条 LogicFlow 连线只表达：“在同一款的这条对象分支上，下游工艺的类型级投入来自上游工艺的类型级产出。”它不表达实际交了多少、哪个批次、谁确认接收。

允许连线必须同时满足：

1. 上游产出类型与下游投入类型相容；
2. 分支身份相同，或属于已定义的合法转换/汇合；
3. 不形成循环；
4. 不跨到后道动态项目；
5. 不把不同 BOM 物料仅因工序名相同而合并；
6. 裁片分支必须带纸样部位；成衣烫画/直喷必须带成衣 BOM；
7. 分支汇合必须指向真实消费节点，例如多个裁片/毛织片到车缝，而不是为画面整齐创建虚拟工序。

### 3.7 LogicFlow 的最小使用范围

采用 LogicFlow 是为了复用成熟的节点、边、画布、缩放、选择、事件和序列化能力，不自行实现通用图编辑底座。实施时先安装并锁定 `@logicflow/core`；只有本地 PoC 证明布局稳定时才增加 `@logicflow/layout`。官方说明可参考：

- [LogicFlow 官方仓库](https://github.com/didi/LogicFlow/blob/master/README.md)
- [LogicFlow 官方快速开始](https://github.com/didi/LogicFlow/blob/master/sites/docs/docs/tutorial/get-started.zh.md)
- [LogicFlow 核心选项源码](https://github.com/didi/LogicFlow/blob/master/packages/core/src/options.ts)

当前页面只暴露下列业务操作：

- 选择节点并查看来源；
- 打开现有编辑弹窗；
- 在合法锚点之间连接；
- 删除人工节点或允许删除的边；
- 调整先后和并行；
- 自动整理布局；
- 适配画布/恢复视图；
- 撤销、重做；
- 确认工艺路线。

LogicFlow `@logicflow/core@2.2.2` 及以上版本随 npm 包提供本地 AI 编程文档。进入 WP-03 后，实施人员/AI Agent 应先读取安装包内的本地官方文档，再按本项目当前版本实现；不能凭旧版本示例臆造 API。这个能力用于降低实现和维护成本，不会作为业务人员可见功能出现在页面中。

以下通用能力全部隐藏或禁用：

- 任意节点面板和任意拖入；
- BPMN、审批、网关、脚本、条件表达式；
- 任意修改节点颜色、形状、大小、旋转；
- 任意文本编辑；
- 任意跨对象连线；
- 导入/导出通用流程文件；
- 小地图、调试属性、技术 ID 等非业务信息；
- 删除 BOM 自动节点的能力。

### 3.8 与当前字符串模板页面的结合

不迁移 React。新增一个局部 LogicFlow 适配模块，由现有 `renderProcessTab()` 输出固定挂载容器：

1. 页面渲染完成后在容器内创建 LogicFlow 实例；
2. 整页或技术包局部重绘前销毁旧实例；
3. 图数据每次由 `state.techniques` 派生；
4. 图上动作调用与现有卡片按钮相同的路线命令；
5. 路线变化只写回 `state.techniques`，不另建图 store；
6. 只读技术包版本启用静默模式，不可连接、删除或移动业务节点；
7. 节点 ID 直接使用现有条目 ID，边 ID 使用稳定的“上游 ID → 下游 ID”；
8. 边不显示长文本，具体来源和对象放在节点卡片/右侧详情，降低错位风险。

自动布局采用阶段从左到右、同一对象分支从上到下的确定性规则。每次增删节点或边后重新布局；禁止保存用户随意拖出来的任意坐标作为业务事实。布局库只负责位置，不负责业务校验。

### 3.9 路线确认门禁

确认按钮沿用当前入口，但校验改为：

- 所有自动节点均有真实来源和对象分支；
- 每个需要上游的节点都有合法直接前置；
- 图不存在循环；
- 不存在裁片印花；
- 烫画/直喷明确区分裁片或成衣；
- 同款不同物料分支未被同名工序吞并；
- 纯整件毛织主干没有普通裁剪；
- 部位毛织能走向裁床待交出/车缝汇合；
- 路线不包含开扣眼、装扣子、烫包等本批后道动态项目；
- 新条目、边和兼容步骤投影可以完整写入技术包版本快照。

确认只代表技术包路线已确认，不代表生产任务已生成、物料已经接收或现场已经开工。

## 4. 准备、生产加工单的“需求来源—前置—明细—后置”增量调整

### 4.1 四块信息怎样定义

| 区块 | 准确业务含义 | 当前页面中的呈现方式 |
|---|---|---|
| 需求来源 | 为什么产生本加工需求，例如生产单、备货、补料、采购投影，以及对应技术包 occurrence | 在现有详情基础信息中增加只读来源卡片，不要求现场编辑 |
| 前置任务项 | 哪张上游单据的哪条明细会产生本单所需对象 | 管理端显示单号、明细、对象、已交/可收数量和状态；可点击当前已有详情 |
| 任务明细 | 本加工单实际要处理的对象、规格/SKU/颜色/部位和计划数量 | 保留各专项单据现有明细，不强制统一列 |
| 后置任务项 | 本单产出预计供给哪张下游单据明细 | 管理端显示已分配、已交出、下游已接收数量；未生成下游时显示“待生成”，不虚构单号 |

这四块必须和工艺路线一起生成和维护，但不是同一份数据：路线决定应有的上下游关系，生产单拆解形成任务项，实际交接记录数量。

### 4.2 现场接收与自动开工

普通准备、生产加工单采用用户已确认的简化规则：

1. 上游发生一次交出后，对应下游任务项出现可接收数量。
2. 当前加工方点击“确认接收”。
3. 同一次动作记录实收数量，并自动把本加工单从待接收推进到加工中。
4. 不增加“质量放行”“是否允许部分放行”“齐套检查”等现场门禁。
5. 同一加工单可多次接收、多次填报产出、多次交出。
6. 本次接收不能超过该上游累计交出减去其他下游已接收的剩余数量。
7. 数量达到计划值不自动完成单据；加工单和生产单只能由人工完成。

裁片交给三方车缝工厂是特例：裁床完成交出即由系统替三方记录接收并自动开工，不要求三方再点一次“确认接收”。这只是减少现场动作，不代表系统可以自动完成车缝任务。

### 4.3 多次交出和接收的最小账

每一次交出/接收继续使用各专项域已有记录；缺少时只补最小事件字段：

- 上游单据和明细；
- 下游单据和明细；
- 对象分支键；
- 交出数量；
- 接收数量；
- 操作人和时间；
- 是否为裁片交三方的自动接收；
- 撤销/更正所对应的原事件。

可接收数量只做数量守恒：

`上游累计交出 − 下游累计有效接收`

不在这里引入合格数量、质量放行或中间质检。


### 4.3.1 中转区域的原交出接收

对接收方已经明确为“中转区域”的原交出记录，仓储端沿既有“入库管理”入口提供待接收和已接收视图。接收人员核对来源加工单、生产单、对应物料、原单位和本次交出数量，填写实收数量；确认后保留本人姓名、时间和差异原因，并更新同一条原交出记录。禁止自动生成实收、替来源工厂代收、复制另一套数量账。

页面明确展示“当前原型身份”：中转区域收货员或只读查看。收货员姓名必填并写入原记录；只读身份不能提交。该显式原型身份不等同真实仓库账号或生产鉴权，不借F090和中央辅料仓身份，不创建密码。

仅展示原接收方为WH-TRANSFER的交出记录；不把这一步强加给本来直接交给下游加工方的路线。禁止重复确认、无姓名、负数、非有限数和超过原待接收数量；有差异必须记录原因，不增加质量复检和齐套动作。收货不自动完结加工单或生产单。

### 4.4 物料替换不会被路线锁死

技术包路线引用的是逻辑分支，例如“主面料 BOM 行”“花边 BOM 行”“前片纸样部位”“成衣 BOM 行”。生产单快照保存这些逻辑分支，执行加工单再保存本次实际物料。

替换面料、纱线或其他辅料时：

1. 不修改技术包版本；
2. 不改变生产单与原技术包快照的关系；
3. 在生产执行的物料引用中记录替换前后物料；
4. 原路线 occurrence 继续有效，因为逻辑用途和对象分支未变；
5. 后续加工单读取替换后的实际物料；
6. 已发生的交接保留当时真实物料，不能被新替换覆盖。

只有替换导致工艺要求或对象转换本身变化时，才属于生产单工艺变更，而不是普通物料替换。

### 4.5 管理端与执行端的差异

管理端详情可以看到完整四块关系和跨单据导航。执行端只保留：

- 当前加工单；
- 当前实物及真实图片；
- 本次可接收/已接收数量；
- 当前要做的动作；
- 已完成/待交出数量；
- 一个主要操作按钮。

执行端不展示 LogicFlow、技术包版本、路线 occurrence、关系索引或通用状态机术语。

### 6.1 辅助/特种工艺的合单边界

现有 `SpecialCraftTaskOrder` 可以继续作为 18 类工艺的共同承载体，但合单键必须至少考虑：

- 生产单；
- 工艺代码；
- 作用对象类型；
- route occurrence；
- 对象分支/部位；
- 责任工厂或执行方；
- 实际物料身份；
- 适用 SKU 范围。

“多个明细可以出现在同一张加工单”不等于“可以丢失 occurrence 后再按工艺名自动合并”。合单后每条明细仍要能回到原路线节点、上游任务项和后置任务项。

## 7. 后道工厂管理的增量调整方案

### 7.1 先冻结现有页面和入口

本次不删除、不重排以下现有入口：

1. 后道生产任务；
2. 后道辅料调拨单；
3. 质检单；
4. 后道加工单；
5. 复检单；
6. 后道待加工仓；
7. 后道待交出仓；
8. 后道出货单；
9. 差异与操作日志；
10. 我的动态授权码；
11. 成衣 SPU 替换。

另外保留现有后道统计路由和专用打印路由。它们不一定都出现在上述菜单子项中，但属于当前后道原型的现有承载体。

列表筛选、详情页、真实图片、角色动作、PDA 入口、打印和仓库页面继续沿用。实现工作的目标是让这些页面读取唯一、正确的正式事实，而不是另做一套新页面。

#### 7.1.1 当前 Web、PDA 和打印承载体的保留清单

| 现有承载体 | 当前动作 | 本轮处理方式 |

| 后道生产任务 | 按生产单汇总任务、历次回货、质检和各状态数量 | 页面和聚合方式保留；正式来源适配后替换有限 Mock |

当前明确没有后道工厂 PDA 的“成衣仓收货”入口，这个角色边界继续保留。成衣仓接收属于外部仓库责任，不能因为空项目直达而重新塞到后道工厂 PDA。

#### 7.1.2 迁移期间不得退化的现有现场契约

1. Web 管理、Web 质检、PDA 一线执行保持当前职责分工。
2. 现场继续扫描或输入完整业务单号，不改成模糊搜索后让人员猜选。
3. 三方可对同一生产单分多次登记回货，每次形成独立回货批次。
4. 每个回货批次只生成一张到货 QC；送检动作不再次建单或改变 QC 单号。
5. 所有回货、质检、加工、复核和出货数量按 SKU 记录，不允许不同 SKU 互相抵消。
6. 当前模式下，回货登记与后道确认实收分开；登记不等于已经接收入库。
7. 回货确认保留第一次点数；超过当前 5% 差异规则时进行第二次点数并按现有授权机制处理。分母继续使用三方登记数量，除非以后另有明确业务变更。
8. 后道主管订正已确认回货时生成新确认版本，原版本保留，不静默覆盖。
9. QC、后道加工和处理后复核继续保留领取人/开始人责任；误领可退领，主管可释放。
10. 仅车缝锁定我方三项，含烫包任务默认空选并允许 QC 调整。
11. 每次 QC 只进入一个后续分支：无项目直达成衣仓，或有项目进入一张后道加工单；绝不并行生成两套。
12. Web/PDA 当前共用的后道加工草稿、接管原因和操作留痕继续保留。
13. 有处理项目的复核继续保留错码阻断、重贴和复扫正确的防错能力。
14. 一个合法交出来源幂等生成一张后道出货单，不因刷新、重复点击或跨端操作生成两张。
15. QC、后道加工、处理后复核以及相关业务单据都由人显式提交完成；系统只按结果生成下游事实。
16. 款式/物料真实图片、点击大图、图片加载失败提示继续保留。
17. 每次操作继续记录人员、时间、前后状态、数量差异和授权事实。
18. 后道辅料调拨与成衣回货数量规则继续隔离；不能用调拨到货反推本批需要做什么项目。
19. 后道待加工仓与待交出仓继续是两个不同库存/批次追溯位置。
20. 当前打印纸张、字段、业务单号、二维码/条码扫描目标和按件标签数量不得退化。

### 7.2 当前主干和页面链保留，只调整 QC 后分流

当前运行模式继续是：

`三方车缝工厂自助回货登记 → 后道确认实收 → 后道待加工仓 → 唯一到货 QC`

QC 后只修正分流：

- 最终项目为空：`直接生成成衣仓数量交接`。
- 最终项目非空：`生成现有后道加工单 → 完成处理 → 现有处理后交出链 → 后道出货单 → 成衣仓接收`。

未来扫码模式“扫码登记时即确认实收”暂不新增按钮、路由和状态，只在数据接口上避免把“登记”和“确认”永远写死为同一个动作。

### 7.3 正式数据接入方式

`post-finishing-full-flow.ts` 当前内置有限验收生产单和固定扫码格式。增量方式不是重写后道实体，而是增加一层来源适配：

1. 从正式生产单、有效任务分配和车缝/毛织成衣交出事实中取得可回货任务；
2. 映射成当前 `PostFinishingAcceptanceProductionOrder` 页面所需 DTO；
3. 保留当前回货、QC、处理、仓库、出货实体和页面读取接口；
4. Mock 只保留为演示 seed，不再是业务允许范围的判定依据；
5. 回货次数不固定为 1～5；一次回货只要求本批有至少一个 SKU 数量大于零，不要求所有 SKU 都必须正数；
6. 同一生产单多次回货继续按回货批次分别 QC 和处理；人工完成生产单的规则不变。

### 7.4 本次三方任务范围与 QC 默认规则

| 本次分配给三方的任务范围 | QC 默认后道项目 | 是否可修改 | 业务解释 |
|---|---|---|---|
| 仅车缝 | 开扣眼、装扣子、烫包 | 不可修改 | 三方未承担这些工作，我方后道必须执行 |
| 车缝+烫包 | 默认不选 | 可以手工调整 | 三方原则上完成烫包，现场 QC 决定是否仍需我方处理 |
| 裁剪+车缝+烫包 | 默认不选 | 可以手工调整 | 同上，且三方同时承担裁剪 |

项目集合保存在后道加工单单头，明细继续是 `SKU × 数量`，不改成 `SKU × 项目 × 数量`。

### 7.5 唯一质量和返厂节点

到货 QC 保留以下职责：

- 对本批各 SKU 做质量判断；
- 记录返厂/退回三方数量、原因和接收工厂；
- 根据任务范围得到默认项目和可编辑性；
- 确认本批最终后道项目；
- 冻结本批 QC 结果，供处理、仓库、出货和日志读取。

准备阶段、生产中间工序、后道加工完成和处理后交接都不再新增“合格/瑕疵/返厂”判断。返厂分支只从到货 QC 产生和确认。

### 7.6 QC 项目为空时的最小修改

当前 `completePostFinishingQcTask()` 在项目为空时调用 `createRecheckOrder()`。只替换这个分支，不推翻 QC 主函数：

1. 保存 QC 结果和返厂结果；
2. 对无需返厂且无需我方处理的 SKU 数量，直接创建一张成衣仓数量交接/后道出货事实；
3. 复用现有后道出货单和成衣仓收货实体，或提取当前 `upsertOutboundFromRecheck()` 中与复检无关的共用构造函数；
4. 出货来源明确标记为“到货 QC 直接交成衣仓”，不能伪造复检单号；
5. 不创建后道加工单；
6. 不创建复检单；
7. 不进入后道待交出仓的再次扫码/点数动作；
8. 不要求额外确认“无需处理”；QC 提交即完成该分支的系统生成。

“直接生成交接”不等于伪造成衣仓已经收货。成衣仓继续按现有仓库收货职责确认实收；这属于接收方责任，不是后道工厂内部的复检动作。被明确取消的是后道工厂内部额外的复检、扫码和点数。

### 7.7 QC 项目非空时的最小修改

保留当前一张 QC 最多生成一张后道加工单的结构：

- 单头：回货批次、责任快照、项目集合、执行工厂、状态；
- 明细：SKU、计划处理数量、累计处理数量、未处理数量；
- 项目内部顺序：仍属于后道/QC 内部安排，不进入技术包工艺路线；第一版不因顺序另拆多张加工单。

后道加工完成只提交：

- 各 SKU 本次处理数量；
- 各 SKU 未处理数量；
- 未处理说明；
- 操作人；
- 操作时间。

不再提交合格数量、瑕疵数量和返厂数量。若处理过程中发现无法继续的质量问题，应回到原到货 QC 的授权更正/返厂处置机制，不在加工完成页创造第二个质量事实。

### 7.8 复检页面怎样保留而不推翻

为保护当前原型和线上相似操作，第一阶段保留“复检单”菜单、路由、列表、PDA 和条码动作，但收窄其职责：

- 只服务“确实经过我方后道处理”的分支；
- 负责处理后数量交接、条码正确性和进入待交出仓；
- 不再判断合格/瑕疵，不再产生返厂；
- 项目为空的批次完全不进入；
- 页面布局和扫码动作保留，字段文案逐项调整。

是否把用户可见名称从“复检单”改成“处理后交出复核”可作为独立的小范围产品确认，不阻塞本轮数据规则修正；在确认前先保留当前菜单名称，避免大范围改变现场找单习惯。

### 7.9 “烫包”统一

增量迁移分三步：

1. 所有新写数据、页面文案、筛选项、打印和测试统一使用 `烫包`；
2. 读取历史 `熨烫和包装` 时归一化为 `烫包` 展示；
3. 历史 seed/存储完成迁移后删除旧值兼容分支。

不能把两个名称同时展示为两道工序，也不能继续让新数据写旧值。

### 7.10 KOL、整件毛织和成衣图案加工的入口

- KOL 样衣、KOL 小单整单任务在可回货来源解析处直接排除，不能等 QC 时再隐藏。
- 普通整件毛织成衣可作为后道回货来源，任务范围使用毛织任务的后续责任事实，不虚构车缝单。
- 普通成衣烫画/直喷的成衣产出可继续进入后道，但路线节点本身不预设后道项目。
- 普通车缝、车缝+烫包、裁剪+车缝+烫包按当前责任规则进入。

### 7.12 出货、待交出和成衣仓接收的状态收口

当前新全流程在处理后复核完成时创建待交出仓记录和出货单，成衣仓接收时再把待交出仓改为已交出；但部分详情、打印和通用 PDA 对“出货单已生成”“后道已交出”“成衣仓已确认”的表述并不一致。

本轮不新建仓储模块，只统一三个事件：

1. **出货单生成**：表示已经形成要交给成衣仓的数量和单据，状态为待成衣仓接收；此时不能显示“成衣仓已收”。
2. **后道实物交出/成衣仓接收**：沿用当前成衣仓接收动作作为责任转移事实；确认后待交出仓数量扣减并记录已交出。
3. **通用 PDA 已交出**：只读新全流程中已实际交出的记录，不能继续读取旧出货 store，也不能把“单已生成”误显示成“已交出”。

页面和打印上的错误路径“后道待加工仓 → 后道待交出仓”应改为本单真实去向“后道待交出仓 → 成衣仓”；QC 空项目直达分支则显示“到货 QC → 成衣仓待接收”，不经过后道内部复核/点数。

### 7.13 已定位的后道局部代码问题

这些问题都应在现有模块内定点修复，不构成重做后道的理由：

| 问题 | 当前代码表现 | 增量修正 | 验证 |

| 辅料调拨责任标签可能为空 | `material-transfers.ts` 的旧兼容读取使用不存在的 `.label`，而当前快照字段是 `responsibilityLabel` | 新数据直接读 `responsibilityLabel`；确有旧快照时只在迁移器兼容 `.label` | 新旧样例责任标签均显示且无 `undefined` |

## 8. 新旧逻辑兼容与工程清理方案

### 8.1 清理不是第一步删除文件

理想终态确实只保留已确认的最新业务逻辑和相关代码，但当前代码存在跨 Web、PDA、仓库、打印、统计和详情回退的消费者。直接删除旧域会使当前原型出现空页、旧记录打不开或不同页面数量不一致。

所以每一套旧逻辑按五个门槛处理：

1. 指定最新权威事实源；
2. 停止旧模型产生新记录；
3. 用只读适配器让旧页面先读权威事实；
4. 迁移路由、PDA、打印、统计、测试和历史 ID；
5. 全仓确认无调用、无新写、无历史阻塞后删除旧代码、文案、Mock 和存储键。

### 8.2 已识别的并行事实及收口方向

| 并行事实 | 当前情况 | 权威终态 | 增量迁移顺序 |
|---|---|---|---|
| 正式裁片单 vs 旧运行时裁片单 | 两套实体和进度并存 | PROD-001 正式生成裁片单 | 停旧创建→旧详情读正式适配→迁进度/路由/测试→删 PROD-002 |
| 正式染色/印花 vs 工厂端印花演示域 vs 旧染印域 | 多套单据可表达相同需求 | PREP-001～008 正式专项单 | 停旧新写→映射历史 ID→迁页面/PDA/打印→删 PREP-010/011 写域 |
| 专用捆条单 vs 旧特殊工艺捆条投影 | 可重复出现 | PROD-003 专用捆条单 | 通用列表只投影专用单→删旧写入 |
| 专用盘扣流 vs 通用辅助工艺盘扣单 | 可能双写 | 专用盘扣流为执行源，通用域为索引/列表入口 | 建一对一适配→停止通用重复建单→迁详情/统计 |
| 现代曲牙绣 vs 旧曲牙→车缝 | 名称和责任冲突 | PROD-017 曲牙绣 | 禁止旧选择/生成→历史只读映射→删除旧词条/seed/测试 |
| 新后道全流程 vs 旧后道域 | 页面已有新链，PDA/详情仍有旧消费者 | POST-002 及其同一 full-flow 状态 | 正式来源适配→停旧创建→迁消费者→删旧写域 |
| 新后道全流程 vs 静态后道路由/通用回货质检 | 可能平行计算项目和状态 | 本次任务范围 + 唯一到货 QC | 静态路线降为只读说明→停止生成项目→迁统计/结算→删除业务判定 |
| 新后道出货 vs 旧 localStorage 出货实体 | 可能各自产生出货/收货 | POST-014/015 新全流程实体 | 旧页读新适配→迁历史 ID→删平行写入和存储键 |
| 独立烫包运行时任务 vs 合并任务/后道 QC 加工单 | 同名但身份不同 | 任务范围负责分配，POST-002 负责 QC 后我方处理 | 先标明身份→消除重复生成→再判断是否删除 POST-001 seed |

#### 8.2.1 旧后道域不能直接删除的已确认消费者

当前 `post-finishing-domain.ts` 及静态后道路由仍被以下消费者直接或间接读取；WP-10 必须逐个迁移和验收，不能把删除一个文件当作清理完成：

- 通用 PDA 与移动任务：`factory-mobile-todos.ts`、`factory-mobile-warehouse.ts`、`mobile-execution-task-index.ts`、`pda-handover-events.ts`、`pda-start-link.ts`、`process-mobile-task-binding.ts`；
- Web 状态和执行写回：`process-action-writeback-service.ts`、`process-execution-writeback.ts`、`process-web-status-actions.ts`；
- 仓储和交接：`process-warehouse-domain.ts`、`process-warehouse-linkage-service.ts`、`pda-handover.ts`；
- 生产单/结果追溯：`production-object-overview.ts`、`platform-process-result-view.ts`；
- 统计、结算和质量：`process-statistics-domain.ts`、`pre-settlement-ledger-repository.ts`、`quality-deduction-analysis.ts`、`store-domain-statement-source-adapter.ts`；
- 打印：`task-print-cards.ts`、`post-finishing-qc-print-template.ts`、`post-finishing-route-card-template.ts`、`post-finishing-outbound-template.ts`；
- 静态路线消费者：`return-inbound-workflow.ts`、`return-inbound-quality-chain-facts.ts`、`return-inbound-qc-view.ts`、进度交接和质量类型相关模块；
- 页面级兼容：后道加工单详情的旧域 fallback、后道统计的新旧混合投影、通用 PDA“已交出”的旧出货数据源。

其中打印模板需要先拆成“纯版式渲染器”和“旧域取数构建器”。新全流程可以继续复用成熟版式，但不得为保留版式而永久保留旧业务写域。

### 8.3 旧逻辑删除清单必须覆盖什么

每项旧逻辑只有同时完成以下检查才算删除完成：

- 字典词条；
- 类型和枚举；
- seed/Mock；
- 生成器和写入命令；
- localStorage 键和迁移读取；
- 菜单和路由；
- 列表、详情、弹窗、PDA、打印；
- 统计和结算投影；
- 中文文案和空状态；
- 单元/契约/E2E 测试；
- 当前现状/方案/验收文档；
- 历史记录 ID 的最后读取路径。

仅隐藏菜单、仅停止按钮、仅改中文名都不算完成。

### 8.4 历史兼容的截止方式

由于这是原型仓库，兼容不应无限期存在。每套迁移在代码中写明：

- 旧 schema 版本；
- 迁移到的新 schema 版本；
- 读取迁移函数；
- 一次迁移成功标记；
- 删除旧读取器的条件和对应需求编号。

不再增加“如果新模型没有数据就永久回退旧模型”的无期限 fallback。迁移完成后，新页面找不到权威事实应明确显示数据缺失，而不是偷偷读另一套旧事实。

## 9. 分阶段实施工作包

### WP-00：冻结当前原型基线和回归样例

**业务目标**：保证后续每次改动都能证明“在当前原型上迭代”，而不是换了一套页面。

**涉及位置**：当前技术包命名页面、所有后道 Web/PDA/打印命名路由、现状文档中的加工单登记册。

## 11. 实施顺序与发布切片

### 第一阶段：只纠正词典和路线数据，不碰后道页面结构

包含 WP-00～04。完成后，技术包能正确表达同款多物料、多部位和不同顺序，并用 LogicFlow 可视化，但专项加工单的现场承接仍按原逻辑运行。

发布门禁：旧技术包可读、新技术包可编辑、快照不丢字段、现有生产单页面无回归。

### 第二阶段：补准备和生产阶段关系，不改专项单据外形

包含 WP-05～07。按水溶/染色/印花→裁片/毛织→辅助工艺/车缝→辅件分支的依赖顺序接入。每接入一个专项域就完成该域页面和数量回归，不等全部域一起上线。

发布门禁：已接入域的上下游和数量守恒；未接入域仍使用原逻辑但不得被误标为已完成。

### 第三阶段：在现有后道模块内修正规则和正式来源

包含 WP-08～09。先把正式任务映射成当前 DTO，再改 QC 两个分支；页面、路由和角色动作保持。

发布门禁：三种任务范围、两条 QC 后分支、QC 返厂、PDA、打印、两仓和成衣仓接收全部通过。

### 第四阶段：逐域停止旧写和删除旧代码

包含 WP-10。一次只清一套旧事实，先迁消费者再删除。每次删除均独立提交，方便回退和定位遗漏。

发布门禁：无旧新写、历史样例可读、无 fallback 命中、全仓无消费者、命名页面无回归。

### 第五阶段：完整交付闭环

包含 WP-11。完成需求正向/反向追踪、治理记录、专项检查、命名页面验收、任务收据和发布证据。

## 12. 必须通过的业务验收场景

### 12.1 工艺路线场景

1. 同款主面料 A：染色→印花→裁剪；里料 B：只染色→裁剪；两条路线互不强制同序。
2. 同款主面料 A：印花→染色；另一款相同工艺可以是染色→印花，系统不自动改回默认顺序。
3. 纱线染色和花边染色保留各自物料类别，不显示为面料。
4. 同一工序码在多条 BOM 分支出现多个节点，确认路线后不合并。
5. 前片烫画、后片直喷和成衣烫画同时存在，三者节点、对象和加工单不互相吞并。
6. 尝试把 `PRINT` 连接到已裁裁片时阻断，并提示改用烫画/直喷。
7. 纯整件毛织路线为纱线→成衣，无普通裁剪；同款存在其他梭织分支时，仅对应分支保留裁剪。
8. 部位毛织为纱线→毛织横机片→裁床待交出，与其他裁片在车缝消费点汇合。
9. 删除某条 BOM 的染色要求，只影响该 BOM 的染色 occurrence；存在人工内容时沿用当前确认移除机制。
10. LogicFlow 路线图和现有工艺明细来回切换，节点、连线、顺序和编辑结果完全一致。

### 12.2 准备、生产执行场景

1. 生产来源、备货来源、补料来源的染色/印花单各自保留正确需求来源。
2. 水溶单多次交出，染色/印花下游分次确认接收并自动开工；水溶单仍需人工完成。
3. 同一上游产出分配给两个后置任务项时，可接收数量不重复占用。
4. 裁片分两批交给三方车缝，系统分别记录自动接收/开工，三方无需额外领料动作。
5. 部位毛织片与普通裁片分别交出、分别记录，车缝任务不设齐套门禁。
6. 替换生产单实际面料后，技术包版本不变，下游单据读取替换后的实际物料，历史交接仍显示原物料。
7. 压褶和打褶同款并存，生成两种不同加工单明细。
8. 曲牙绣正常生成，所有新建页面无旧曲牙选项。
9. 指定前片制作花朵，花朵单能回溯前片裁片任务并交给正确消费节点。
10. 盘扣、捆条、花边各只出现一个可操作执行单，不在通用域重复生成。

### 12.3 后道场景

1. 仅车缝：自助登记→后道确认实收→QC；三项默认勾选且不可改；生成一张后道加工单。
2. 车缝+烫包：QC 默认不选项目且可改；保持为空时不生成加工单/复检，直接生成成衣仓交接。
3. 裁剪+车缝+烫包：与上一场景相同，但页面正确显示本次三方任务范围。
4. 含烫包任务在 QC 手工选择开扣眼和装扣子：生成一张单头含两项目、明细为 SKU×数量的加工单。
5. 到货 QC 判定部分数量返厂：返厂对象、数量、原因和接收工厂只在 QC 产生；后道完工不能再次返厂。
6. 有项目加工完成：只填处理/未处理数量；进入处理后数量/条码复核，再到待交出仓和出货单，无第二质量结论。
7. 无项目直达：后道复检列表、PDA 和待交出内部操作中不出现该批；成衣仓能从明确的 QC 直达出货来源接收。
8. 同一生产单多次、部分 SKU 回货：每批独立登记、确认、QC，未回货 SKU 可以为零/不在本批。
9. KOL 样衣/KOL 小单：后道生产任务、回货来源和所有 POST 单据均不出现。
10. 普通整件毛织：能进入后道回货和 QC，但不伪造车缝任务单号。
11. 历史数据含“熨烫和包装”：页面显示烫包；所有新记录只写烫包。
12. 后道现有 11 个菜单入口、列表、详情、PDA、打印和真实图片能力保持可用。

### 12.4 清理场景

1. 新生产单只生成正式裁片单，不生成旧裁片单；历史旧裁片单仍能通过迁移映射查看。
2. 新印花需求只生成正式印花单，不再同时生成工厂端演示单或旧染印单。
3. 同一回货批次只存在一张可操作 QC、一张有条件的后道加工单和一张出货单。
4. 旧后道页面消费者全部读取新权威事实后，删除旧 seed/store 不出现空页或数量变化。
5. 全仓没有两项已确认淘汰的停用历史准备词条、旧曲牙→车缝、裁片印花的可操作代码、文案、Mock 或测试。

## 12.5 新增完整生产需求单验收硬门禁（2026-09-07）

本轮复现补充：任务拆解只建立待执行任务，不代表领料或开工。不能用“染印加工后的库存已就绪”作为首次生成染印任务的前置，否则形成循环等待。物料检查继续显示真实缺口，配料、领料与实际开工沿原流程阻断；缺失技术包或不合法工艺仍不得生成。初始原料仅为显式 Mock 输入，不代表采购入库已发生。损耗沿技术包比例值计算（0.03 表示 3%），原单位不得无换算改写。

用户明确要求至少创建5个生产需求单，全流程、多场景覆盖后才能验收成功。实施按《七张生产需求单全流程验收.md》执行7张独立新需求及必要增补场景。每张从初始需求经原转单、冻结路线、任务派生、适用加工与上下游交接，走到自身正确的仓库接收和人工完成终点。不得用旧单改名、预置终态、孤立专项通过或5张同质单替代。上述新增门禁优先于此前阶段性验收结论。

## 14. 风险、门禁和回退

| 风险 | 发生原因 | 防护方式 | 回退点 |
|---|---|---|---|
| LogicFlow 与现有卡片状态不一致 | 两套事件分别写状态 | 共用路线命令，图数据单向由 `state.techniques` 派生 | 保留工艺明细视图，可关闭路线图挂载 |
| 自动布局错位 | 节点长文本、边标签、自由坐标 | 固定卡片尺寸、无边长标签、确定性阶段/分支布局、变更后重排 | 退回现有列表视图，不影响保存数据 |
| 同名工艺重复/丢失 | 仍按 processCode 聚合 | occurrence ID + routeObjectKey，生成和合单分别校验 | 保留原条目快照并阻断发布 |
| 物料替换失效 | 路线引用实际 SKU | 路线只引用逻辑分支，执行单保存实际物料和替换记录 | 回退执行引用，不修改技术包快照 |
| 后道改动破坏现场路径 | 重排页面或状态 | 冻结 11 个入口和主要动作，只换数据源/分支 | 每个后道工作包独立提交，可回退逻辑但保留数据迁移 |
| 空项目直达伪造成衣仓已收货 | 把“生成交接”和“仓库接收”混为一体 | 只自动生成出货/交接来源，保留现有成衣仓接收责任 | 关闭直达生成，恢复待人工处理并排查，不伪造收货 |
| 旧逻辑过早删除 | 未迁 Web/PDA/打印消费者 | 停写→适配→迁消费者→删除的固定门槛 | 保留只读迁移器直到证据闭环 |
| 历史兼容永久化 | 无截止版本 | schema 版本、一次迁移标记、删除需求编号 | 不允许无期限新旧 fallback |
| 数量重复记账 | 关系层复制交接数量 | 关系层只引用现有明细和事件，不新建库存账 | 禁用关系写入，不影响专项单据原账 |

## 15. 最终验收口径

本方案实施完成不能只以“页面能打开”或“构建通过”为准，必须同时满足：

1. 当前技术包和后道原型的页面结构、入口和主要操作仍在，业务人员无需重新学习一套系统。
2. 技术包工艺路线能按同款不同 BOM/部位独立表达不同工艺和顺序。
3. LogicFlow 只展示维护路线需要的操作，节点多时仍清晰稳定。
4. 生产单快照、任务和所有正式加工单能保留 route occurrence 和对象分支。
5. PREP-001～012、PROD-001～028、POST-001～017 每项均有明确的保留、调整、兼容或删除证据。
6. 准备、生产加工单能查看来源、前置、明细和后置，并由实际多次交出/接收承接。
7. 确认接收即自动开工；裁片交三方自动接收/开工；所有真单据仍人工完成。
8. 物料替换不要求修改技术包版本或重建所有单据。
9. 后道继续使用当前模块；本次任务范围、回货、实收、唯一 QC、加工、仓库、出货和日志责任清楚。
10. 空后道项目不加工、不复检、不扫码点数，直接生成成衣仓数量交接；有项目继续使用现有后道加工与交出链。
11. 返厂只在到货 QC 产生；处理完成和处理后复核不再判断质量。
12. 新写和用户可见业务名称统一为烫包。
13. KOL 整单不进入普通后道；整件毛织等普通成衣来源可合法进入。
14. 已确认淘汰的旧写入口、旧模型、旧文案、Mock、测试和存储在消费者迁完后完整删除，不留双写或永久 fallback。
15. 正向追踪能从本方案每条原子需求走到实现和证据；反向追踪能从每处代码改动回到需求编号。

一句话概括最终调整方式：

> 保留当前原型已经形成的页面、专项单据和后道操作闭环，在它们之间补齐“对象分支、路线 occurrence、显式前后关系和实际交接”，定点修正已确认错误，再逐套停止并删除旧事实源；整个过程是可分阶段验收的迭代优化，不是另起炉灶。

### 2026-09-08 全流程验收补项：新生产单裁片放行承接

### 4.3.2 已有车缝交出与后道实收的来源关联补项

当独立车缝的原交出记录和原公共送货单分别存在时，由该后道工厂已登录管理员在原交出记录中明确选择对应送货单并确认关联。系统必须校验同一执行任务、生产单、来源工厂，以及逐颜色尺码的登记数量完全一致；同一送货单不得重复关联。无明确对应、拆批或合批无法逐条对应时保留待关联，不按序号或合计数自动猜配。

关联只保存双方原单据身份及关联人、时间；实收数量、确认人和确认时间继续读取原后道最终确认事实，不产生另一笔接收，不修改原工厂交出数量或原后道单。原后道确认订正后联查跟随当前事实，失效或缺失时不得沿用旧实收。未关联记录仍按原流程保留，不通过隐藏历史记录消除差异。已关联记录不得在泛用收货表单重复录实收。

本补项对应EXEC-008/010与POST-002，正常验收为CASE01原HDR两笔与DEL两笔明确关联后两端同为S6/L4；边界验收覆盖错误任务/工厂/SKU/数量、重复占用、越权、取消、存储失败和刷新后来源不变。原型管理员身份并非生产鉴权或现场接受回执。
