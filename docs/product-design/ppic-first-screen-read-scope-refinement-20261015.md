# PPIC 首屏读取依赖补修方案

本方案属于已确认 PPIC 每日回货方案及其 R51／R52／R58／R59 的发布补修，阶段为实施前范围登记及本地验证后追加结果。已部署 `030fdecb` 的 43 项资源哈希和 113 项 Web 业务断言通过，但新上下文冷加载 1075.6～1535.6ms，真实成员首例 1599.2ms，仍不满足 1 秒。先前各版本及失败记录保留原身份；本方案不预填最终结果。

目标：PPIC 读取已经冻结的生产单和技术包时，保留同一事实、复制语义和恢复顺序，同时不因同模块内的建单函数载入 PCS 当前技术包及审批、样衣等无关写入模块。正式新建生产单仍执行原实时技术包校验及冻结。无新业务规则、存储键、状态源、后台、鉴权或框架。

本任务为 T4。直接接口为内部函数归属调整；原三种应回依据、实际身份、每日截止、两节点、后道最终实收及原子保存不变。生产单数组与持久覆盖仍留在原模块，未复制数据事实源或新增迁移。

顺序：原体提取并记录哈希 → 类型／构建及实际静态闭包 → 原有创建与冻结回归、PPIC 22 浏览器及 73 类性能 → 冻结并完整审查／收据 → main 快进推送 → Caddy 成功、正式资源和闭环再验。具体消费者在实现中绑定，实际产出和证据在本版本审查记录及外部部署记录登记。

非范围：不改生产数量／来源选择，不重做 PCS／FCS 架构，不新增业务状态与后备存储，不改变正式合同原版和实物图片；真实 PDA、打印机和工厂接口仍无现场接受证据。

实施中的依赖复核发现，生产单分离后仍由“累计回货 → 既有换款原 SKU 映射 → 当前 SKU 档案”带入 PCS 审核依赖。S07／S08 是这一直接链的补充，不是新业务：换款用户覆盖仍从原键按原格式读取，原保存动作和负责端保留，普通 PPIC 读取不新增写入；默认记录使用原完整样本的发布静态值，新换款仍读取实时 PCS SKU 并执行原校验。本次不宣称换款模块旧保存结构已经整体迁移或修复。

本地阶段追加（2026-10-15）：S01～S04、S07／S08 的原体、保存覆盖、建单／冻结、969 单元及 22 浏览器回归通过；S05 的本地 73 类 365 样本全部 ≤1000ms，最大 915.5ms；S06 最终只读审查无新增 P1／P2。S05／S06 仍须同一新发布 SHA 的正式性能及部署闭合。实际文件、源集合哈希、脚本与本地确认人绑定 [本版本审查记录](../prototype-review-records/ppic-first-screen-read-scope-20261015.md)。确认人是 Codex 技术验证，不代表业务方接受。
