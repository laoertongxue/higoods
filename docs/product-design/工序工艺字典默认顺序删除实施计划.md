# 工序工艺字典默认顺序删除实施计划

## 1. 目标与完成标准

以 `main` 为目标分支删除工序工艺字典的跨款式默认顺序，并证明技术包仍按每款显式路线工作，必要物料依赖不受影响。实现先在隔离任务工作树完成，再通过干净 `main` 工作树集成和发布。

完成标准：`ORDER-001` 至 `ORDER-008` 均有实现位置和直接证据；当前页面不再出现默认顺序入口；专项检查、命名路由验收、原型治理、CodeGraph 和任务收据完成；本地、远端跟踪引用、`git ls-remote` 和 GitHub API 的 `main` SHA 一致。

## 2. 工作包

### WP-1：删除字典默认顺序事实

- 业务目标：字典只描述能力，不定义款式路线。
- 文件／符号：`src/data/fcs/process-craft-dict.ts` 的工序定义与列表函数；`src/pages/production-craft-dict.ts` 的页面状态、渲染和事件。
- 修改：删除逐工序排序值、默认顺序查询函数、入口、弹窗和事件；列表改为阶段分组后的名称排序。
- 验证证据：`check:production-craft-dict-page`、`check:process-craft-final-taxonomy`、`/fcs/production/craft-dict` 页面验收。
- 完成条件：页面与运行源码均不存在默认顺序能力，详情仍可打开。

### WP-2：解除技术包隐式依赖

- 业务目标：每款技术包只使用自身路线，不被字典重新排序。
- 文件／符号：`src/data/tech-pack-process-route.ts` 的基础比较器；技术包上下文、版本仓库、任务生成和生产快照中的路线来源归一化。
- 修改：移除字典排序导入及工序级兜底比较；无明确步骤时只按阶段并稳定保留原始录入顺序；删除空技术包硬编码路线；把来源改为“工序字典引用”。
- 验证证据：`check:tech-pack-process-route`，包含反向于旧默认顺序的输入用例、显式步骤及水溶／染色依赖回归。
- 完成条件：技术包路线模块不再读取字典默认顺序，空技术包不虚构生产路线。

### WP-3：交付闭环

- 业务目标：证明删除范围完整且没有破坏相邻功能。
- 文件／符号：专项检查、`src/pages/task-breakdown.ts`、需求追踪矩阵、原型审查记录。
- 修改：把原肯定性默认顺序检查改为禁止回归；让任务清单可见地展示准备工序边界，并保留 `main` 已有的 KOL-GOTO 和合并任务说明；记录页面影响和保留边界。
- 验证证据：专项命令、浏览器快照、构建、原型治理、CodeGraph 状态和任务收据。
- 完成条件：最后一次实质修改后的证据全部重新生成；无未说明失败；只暂存声明范围内文件并经干净 `main` 工作树发布。

## 3. 依赖顺序

`WP-1` 与 `WP-2` 共享“字典不提供路线”的事实，代码修改完成后统一执行 `WP-3`。浏览器验收必须使用当前分支和当前工作树启动的服务。

## 4. 风险与控制

| 风险 | 控制 |
| --- | --- |
| 删除展示但技术包仍按旧顺序重排 | 专项检查直接禁止路线模块引用字典排序，并用旧顺序相反的输入验证稳定性 |
| 删除默认值后空技术包出现虚假完整路线 | 空技术包只允许根据 BOM 真实要求生成准备工序 |
| 必要工艺约束被当成默认顺序一起删除 | 保留并回归同 BOM 水溶先染色、染色先印花约束 |
| 字典详情或筛选随弹窗删除受损 | 页面专项检查和真实路由交互验收详情打开／关闭 |
| 标准列表页不渲染 `description`，准备工序边界只存在于源码 | 在任务列表操作区直接展示准备工序、KOL-GOTO 和合并任务三条边界，并用真实页面验收 |

## 5. 非本次任务

- 不替各款重新设计或确认具体生产路线。
- 不修改任务合并、生产任务生成和工厂履约状态机。
- 不恢复或合并已放弃的旧 KOL-GOTO 分支历史；仅保留 `main` 当前已经生效的业务行为。
- 不修改历史设计与历史审查记录；它们只说明当时版本，不作为当前实现依据。
