## 1. 目标与完成标准

### 1.1 目标

- 只保留“设计改款任务”一个对象和一套路由。
- 设计改款必须有 A、B 款和跟单上传的真实设计稿。
- 买手一次确认目标颜色、物料和整款费用。
- 跟单下达专业任务和销售展示样衣颜色／尺码／数量。
- 工程主单可以复用设计改款成果，但正式技术包只由工程主单生成。
- 生产准备时效只读工程主单及主单专业任务。
- 删除工程变更完整能力和旧改版第二事实源。

### 1.2 完成标准

1. 81 条原子需求全部标记“已验证”。
2. 新专项契约、相邻领域契约、构建和治理检查通过。
3. 统一列表、新建、详情、专业任务、工程主单、技术包、时效和 FCS 快照在同一分支运行验收。
4. 旧双路由、工程变更路由和专用文件不可用。
5. 当前五份权威文档均为新口径。
6. 两轮核验均在最后一次实质修改之后执行。
7. 任务收据绑定最终 HEAD 和本任务边界。

## 2. 范围与非范围

### 2.1 实施范围

- 生产工程菜单、路由、统一设计改款列表／新建／详情。
- 设计改款领域、真实文件、颜色、BOM 与价格、专业任务。
- 工程主单复用、任务方案、产前版样衣和关闭边界。
- 技术包生成来源、审核、正式快照和 FCS 读取。
- 项目关系、归档、关闭和来源标准化。
- 生产准备时效投影和只读页面。
- Mock、测试、脚本、现行文档和原型审查记录。
- 工程变更和旧改版事实源删除。

### 2.2 非范围

- 老任务迁移或兼容读取。
- 同一 SPU 关闭后再修订正式技术包。
- 真实后端和鉴权。
- 新审批流、取消流或可调依赖。
- 商品测款流程本身和样衣管理模块重做。

## 4. WP1：统一设计改款领域

**业务目标**

不再保存“设计／改款”分类，所有新任务使用同一对象、同一编号和同一状态机。

**负责需求**

SCOPE-002、SCOPE-003、DR-001～DR-005、STATE-001～STATE-005。

**文件／符号**

- src/data/pcs-engineering-master-types.ts
- src/data/pcs-engineering-master-sampling.ts
- createEngineeringIndependentSampling()
- completeEngineeringIndependentBuyerPreparation()
- confirmEngineeringIndependentSamplingPlan()
- confirmEngineeringIndependentSamplingResult()

**修改**

1. 类型收口为 DESIGN_REVISION。
2. 编号收口为 ES-DR-*。
3. 创建输入改为 sourceStyleId、targetStyleId、creationReason、designFiles 和 merchandiser。
4. A/B 款存在且不同；要求非空；禁止隐式建单。
5. 统一四步业务状态和当前团队推导。
6. 步骤完成后重新读取最新事实，页面自动进入下一步。

**验证证据**

- 设计改款专项契约。
- A 缺失、B 缺失、A=B、缺说明、缺设计稿阻断。
- 四步推进和重复点击幂等。

**完成条件**

新记录、列表和详情都不再保存或显示设计／改款分类。

## 5. WP2：统一页面与真实设计稿

**业务目标**

只保留一个菜单、一个列表、一个新建弹窗和一套详情；设计稿是真实图片文件。

**负责需求**

FILE-001～FILE-005、IMAGE-001、PAGE-001～PAGE-003。

**文件／符号**

- src/data/app-shell-config.ts
- src/router/routes-pcs.ts
- src/router/route-renderers.ts
- src/main-handlers/pcs-handlers.ts
- src/pages/pcs-independent-sampling.ts
- src/data/pcs-engineering-file-upload.ts

**修改**

1. 规范路由改为 /pcs/engineering/design-revision 及详情路由。
2. 删除两个旧路由且不重定向。
3. 创建弹窗同时选择 A、B、填写要求、选择真实设计稿。
4. 跟单可在工作安排确认前替换设计稿并保留操作记录。
5. 列表只提供当前需处理的团队筛选。
6. 列设置放在列表表头最右侧。
7. A/B 款和设计稿支持真实缩略图、大图、遮罩、关闭和 Esc。
8. 文件失败时保留用户已填内容并给出重试动作。

**验证证据**

- 页面结构和路由专项。
- Playwright 命名页面验收。
- 真实 File 读取成功／失败案例。
- 1366×768 与 1280×720 验收。

**完成条件**

用户只能看到“设计改款任务”，且缺少真实设计稿不能创建。

## 6. WP3：颜色、BOM 与专业任务

**业务目标**

A 只提供参考，B 形成自己的目标颜色、BOM 与价格、工作安排和专业成果。

**负责需求**

COLOR-001～COLOR-003、BOM-001～BOM-005、TASK-001～TASK-005。

**文件／符号**

- src/data/pcs-engineering-bom-types.ts
- src/data/pcs-engineering-bom-repository.ts
- src/data/pcs-engineering-bom-version.ts
- src/data/pcs-engineering-task-field-policy.ts
- src/pages/pcs-engineering-tasks.ts
- src/pages/pcs-engineering-tasks/shared.ts
- 各专业任务详情模块

**修改**

1. B 款颜色可独立增减。
2. 每个 B 色选择 A 参考色或无参考色。
3. 有参考色按完成确认时间／更新时间倒序选择最近有效方案。
4. 无参考色创建空白草稿。
5. 买手可新增、删除、替换物料。
6. 自定义费用统一作用于整款，物料和费用一次确认。
7. 跟单下达销售展示样衣颜色、尺码、要求数量。
8. 固定依赖自动补齐，不提供依赖编辑。
9. 专业任务使用统一事实和同一详情路由。
10. 图片、PRJ、AI、PDF 等成果读取真实本地文件。

**验证证据**

- 多版本来源 BOM 选择专项。
- 颜色少／等／多、无参考色、多对一案例。
- 物料新增／删除／替换和费用统一确认案例。
- 多颜色、多尺码、多数量样衣要求。
- 专业任务真实文件和双入口同 ID。

**完成条件**

买手完成的是一份整款资料，跟单确认后生成可执行的真实专业任务。

## 7. WP4：工程主单衔接

**业务目标**

工程主单读取已确认设计改款成果，并由跟单逐项决定复用、重做或不采用。

**负责需求**

MASTER-001～MASTER-008、PAGE-005。

**文件／符号**

- src/data/pcs-engineering-master-repository.ts
- src/data/pcs-engineering-master-view-model.ts
- src/pages/pcs-engineering-master-list.ts
- src/pages/pcs-engineering-master-detail.ts
- src/data/pcs-engineering-master-sampling.ts

**修改**

1. 同一 SPU 只允许一张未关闭主单。
2. 新建主单后先确认任务方案。
3. 只展示已完成且整单确认的设计改款成果。
4. 同类型多个成果按完成时间倒序推荐最近版本，同时允许改选历史有效版本。
5. 保存复用／重做／不采用决定。
6. 销售展示样衣与产前版样衣分开。
7. 关闭前返工留在原主单；关闭后只读。

**验证证据**

- 工程主单领域、任务方案、前期成果复用专项。
- 默认最近版本与改选历史版本。
- 复用／重做／不采用三类案例。
- 主单详情跳转专业任务和设计改款成果。

**完成条件**

主单没有双打样来源和工程变更来源，只读取统一设计改款成果。

## 8. WP5：技术包唯一来源

**业务目标**

新业务技术包只有工程主单技术包确认任务一个创建入口。

**负责需求**

PACK-001～PACK-009。

**文件／符号**

- src/data/pcs-technical-data-version-types.ts
- src/data/pcs-technical-data-version-repository.ts
- src/data/pcs-technical-data-version-bootstrap.ts
- src/data/pcs-engineering-tech-pack-workspace.ts
- src/data/fcs/production-tech-pack-snapshot-*
- src/pages/pcs-technical-data.ts
- src/pages/fcs-production-tech-pack-snapshot.ts

**修改**

1. 来源类型只允许 ENGINEERING_MASTER。
2. 创建时校验来源工程主单、来源任务和目标款式一致。
3. 来源任务必须是该主单的技术包确认任务。
4. 设计改款和专业任务只能作为追溯或资料输入，不能生成新版本。
5. 保留技术包内容内部“人工维护／人工调整”的资料含义。
6. 发布时形成 BOM 与价格正式快照。
7. FCS 继续读取和冻结已发布版本。
8. 技术包审核脚本夹具全部使用工程主单来源语义。

**验证证据**

- 技术包来源阻断矩阵。
- 审核通过、退回、返工、锁定与发布专项。
- BOM 正式快照和 FCS 生产快照回归。
- MANUAL、旧改版和工程变更来源零残留。

**完成条件**

所有新技术包记录均能回到唯一工程主单和技术包确认任务。

**业务目标**

统一来源收口不破坏项目归档、正式技术包和生产时效。

**负责需求**

TIME-001～TIME-004、PAGE-004、PACK-006～PACK-009、ARCHIVE-002。

**修改**

1. 时效投影只遍历工程主单快照和主单任务。
2. 同一主单去重。
3. 设计改款推进不新增时效记录。
4. 页面保持只读并可返回主单或任务。
5. 项目归档统一收集设计稿、BOM、样衣和专业成果。
6. FCS 正常读取正式技术包。

**验证证据**

- 时效投影、颜色投影、筛选和只读脚本。
- 项目关系／归档／关闭专项。
- FCS 快照专项。

**完成条件**

## 11. WP8：文档、矩阵与双轮验收

**业务目标**

让设计、实施、代码和证据形成可交付闭环。

**负责需求**

DELETE-010 以及全部 81 条证据字段。

**交付物**

- 总体设计文档。
- 本实施计划。
- 81 条需求追踪与交付矩阵。
- 产品需求说明书。
- 全流程测试方案与实际案例。
- 原型审查记录。
- 最终任务收据和验收清单。

### 11.1 第一轮：正向核验

1. 从 81 条原子需求逐条检查实现位置。
2. 执行新专项契约和直接相邻领域契约。
3. 运行构建、列表治理和原型治理。
4. 在统一路由走完设计改款、工程主单、技术包和时效命名页面。
5. 修复发现的问题；任何实质修改后本轮重跑。

### 11.2 第二轮：反向核验

1. 从菜单、路由、页面、领域、Mock、测试和脚本反查需求。
2. 扫描旧路由、旧类型、旧字段、工程变更实现和旧文案。
3. 验证旧路由无兼容入口。
4. 重跑核心专项、构建、治理和命名页面。
5. 对最终 diff 做越界、遗漏和代码质量审查。

## 12. 风险与控制

| 风险 | 控制 |
|---|---|
| 删除测试掩盖回归 | 用新统一专项和相邻领域专项替代，并记录删除原因 |
| 正式技术包来源收口破坏 FCS | 单独执行发布快照与 FCS 冻结读取回归 |
| 页面状态与领域状态不同步 | 成功动作后重新读取事实并回归四步推进 |
| 多份 A 款 BOM 选错 | 明确按确认／更新时间倒序并做多版本契约 |
| 历史文档继续误导研发 | 五份现行权威文档全部重写；历史材料标记历史版本 |
| 工作树与运行服务不一致 | 在隔离工作树启动指定端口，并记录 HEAD、路由和地址 |
| 真实文件只做假路径 | 契约使用 File 对象，页面使用本地文件选择与读取结果 |
