# 后道逐项加工与多次复检出货实施及验收计划

阶段为实施与逐项验收。用户已授权执行原方案及计划；基线HEAD为 `4a0ce9ef5a30e8dec4537de1ff59159543902a25`，当前分支为 `codex/post-finishing-partial-flow`，使用同一工作树。依赖已用锁文件恢复。用户后续已明确授权：全部验收通过后，本地合并main并推送GitHub main；按当前RELEASE-01继续核对对应SHA的Caddy正式部署。当前整合基线为ecc8af013b5f9d67f5fef14fe5b692483aada61d。

## 2. 依赖顺序与工作包

顺序：P0范围冻结→P1数量模型与失败契约→P2记录保存与迁移工具→P3多次复检出货→P4 Web／PDA执行→P5直接读取方与打印／Mock→P6显式存量切换及综合验收→P7最终审查与交付。P3依赖P1、P2；界面不得在未满足数量和原子保存时先假成功。

### P0：冻结需求与存量边界

**业务目标：** 明确哪些是已确认规则，哪些是方案选择和待定异常，避免实现时暗增规则。

**对象／位置：** 三份本次文档；`post-finishing-full-flow.ts`、`post-finishing-records.ts`、`post-finishing-current-read-model.ts` 的当前契约；相关旧脚本和两套打印入口。

**工作：**

1. 逐条确认矩阵与方案双向覆盖；固定复检差异处理、代登记范围、正式订正是否纳入本期、旧在制人工承接口径及新单编号格式。
2. 登记每个业务对象的静态源、对象仓库、写入动作、读者、旧项及迁移验证。列出既有QC、回货、PPIC、日志和附件共用边界，不随方案重置。
3. 核查当前可用依赖、服务和路由；当前曾出现 `vite: command not found`，实施时先恢复本工作树可复现运行环境，再采集新页面证据，不复用另一工作树的服务。
4. 固定有效旧断言和被替代断言清单，不把旧“唯一复检／整单完成”测试当新规则。

**证据：** 冻结的业务决定、存储边界表、源文件/运行环境版本、原子矩阵。

**完成条件：** 正常主链与异常决策都有可判定预期；没有以“待开发时决定”掩盖数量或历史去向问题。

### P1：四项加工链与统一数量计算

**业务目标：** 每个SKU各项完成量独立累加，后项受前一适用项约束，正常余量持续保留。

**负责文件／符号：**

- `src/data/fcs/post-finishing-full-flow.ts`：`PostFinishingProcessItem`、`resolvePostFinishingResponsibility`、QC冻结项目、`PostFinishingPostTask`、旧draft/results、相关命令。
- 现有局部实现或必要的新轻量 `src/data/fcs/post-finishing-process-progress.ts`：四项执行顺序、分项累计和SKU可登记量；新文件名是实施建议。
- `post-process-route.ts`、`post-stage-taxonomy.ts`：明确内部执行和外部组合术语边界；只改直接需要部分。
- `post-finishing-current-read-model.ts`：分项结果与整体完成供给计算。

**修改：** 增量完成记录结构；统一计算 `Q、Ci、F`、前序可用量；QC实际选择可编辑；单项及任意筛选链；责任人与录入人分开。新单不再要求每SKU“已处理＋未处理=应处理”才可推进。原整单开始人不再成为各项所有完成记录的唯一责任人。

**先建立最小失败契约：** 四项500/300/200/100、仅装扣子和包装、仅熨烫、跨SKU超量、后项先于前项、多人多次累加。断言业务结果和数量守恒，不写仅镜像字段setter的测试。

**完成条件：** 两端可调用同一数量判断；未选项不进入前序；成衣完成量只按最后适用项计算；新旧模型来源身份清晰。

### P2：记录保存、去重、冲突与显式迁移能力

**业务目标：** 一次登记完整保存，失败不改数，多标签／重试不重复登记，历史不丢不伪造。

**负责文件／符号：** `post-finishing-records.ts` 的record主键注册、flatten/overlay、hydrate、`runPostFinishingCommand`、导入导出和旧源迁移；`post-finishing-full-flow.ts` schema、seed、normalize、编号归一；`post-finishing-operation-log.ts`；按需扩展现有 `storage-notice.ts` 及已有存储共用工具。

**修改：**

1. 新加工记录逐条持久化到同一后道命名空间，主单必要版本和日志同事务。累计是只读计算，不能在两个可写源分别维护。
2. UI提交意图标识跨同次重试稳定；不能拿每次随机数据库事务ID替代业务去重键。不同真实登记使用新意图。
3. 事务内检查revision、余量和去重；事务complete后更新内存、显示成功并给下游可读结果。并发竞争失败保留输入并要求重新读取，不无条件自动重试。
4. 新命令先校验、后变更；审查现有“带业务错误码仍保存”的语义，禁止把授权失败、数量超限等意外保存为成功占用。保留已有回货二次点数的必要阶段事实，不能全局改成丢失该事实。
5. 显式升级版本和记录迁移，新增集合纳入种子覆盖、导出、恢复、附件引用和一致性核验。普通读取不能触发写入或整包种子复制。
6. 提供隔离的迁移dry-run／结果核对能力，针对已确认的旧源逐批转换、稳定映射和可恢复进度；仅受影响记录停旧写。历史未知分项保留合并记录身份。

**证据：** 持久回读、关闭重开和下游直达；数据库事务中止／额度／revision冲突；导入导出字段完整；旧schema样例迁移前后逐SKU数量、关联和附件引用对照；失败原数据保留。

**完成条件：** 不半套成功、不假成功、不回退localStorage、不删库；PPIC共用记录不丢；迁移尚有人工待核对记录时明确局部未完成。

### P3：多次交复检、出货及父状态

**业务目标：** 每次提交只占用新的可用量，父单多次推进，各次互不覆盖。

**负责文件／符号：** `post-finishing-full-flow.ts` 的 `createRecheckOrder`、`completePostFinishingRecheckOrderFullFlow`、`upsertOutboundFromRecheck`、`getOrCreateWaitHandoverWarehouseRecord`、`receivePostFinishingOutboundOrder`、`relationForDelivery`、`getPostFinishingFullFlowTrace` 及编号归一；`post-finishing-document-numbering.ts`；`post-finishing-current-read-model.ts` 的工作单、动作和生产任务聚合。

**修改：**

- 新交复检命令接收父单、按SKU的本次量、提交意图和预期版本；创建时占用，不等复检完成。领取／释放保留占用；异常条码不能生成出货。
- 复检增加独立创建人、创建时间、序次；不再用QC创建时间替代。新ID和编号独立于回货次数，旧单号不改。
- 一复检一出货保留；出货ID从具体复检派生，待交出仓和日志依具体子单关联。QC直达仍由QC来源去重，不能与复检出货ID相撞。
- 按冻结的差异口径处理补占用和差异待处理量；数量、授权消耗、日志、出货、待交出记录和库存流水共同提交。授权不足不改实数或占用。
- 每张出货沿用一次正式仓收，重复收货同单幂等；父单可多张。仓收后仅更新该张及其来源仓记录，再聚合父单状态；不直接全回货完成。
- 追溯接受父单或具体子单；返回集合及当前上下文。新命令日志显式传真实子单，不能依赖“首个关联”。

**完成条件：** 100/100/800正常链可形成3复检、3出货、3实收；未完成部分仍可登记；第1张只读事实保持；全部页面聚合与持久回读一致。

## 6. 性能验收

遵循PERF-01，适用加载和操作完整响应通常为 `<=1000ms`。仅下述本期明确确认的大规模完整恢复采用单独时限。每个受影响入口先功能核验；按实现、规模、状态、完成条件相同才划为等价性能家族，各家族最少5个有效原始样本，包含首次和适用边界。冷启动、刷新、站内切换、成功、失败、不同规模不能随意合并。

计划采样家族：四项QC选择与提交、逐项登记保存、交复检创建、复检领取/释放/扫码/完成、出货与成衣仓实收、列表过滤/分页/详情、追溯多子单聚合、仓库多来源读取、图片预览、各类打印生成、受影响备份恢复/显式迁移。迁移或大打印如不能在规则内完成，先报告实际结果与阻塞，不能自动豁免。

每条记录包括真实事件起点、必要计算/持久保存/DOM/绘制/图片就绪终点、持久结果读回、样本值及最大值、脚本/环境/版本。保存计时包含事务complete及可读结果；只看按钮变色、HTTP200、函数返回不算完成。任何有效样本超过其适用门槛即对应需求未完成（通常1秒，仅下文确认的固定完整恢复为10秒），保留失败并追加修复后复测，不能用平均值掩盖。

本期在固定的本地生产预览采样；开发服务诊断另列。实际家族、原始值、失败与复测见性能report.json，不以构建或单元测试替代。

2026-10-19实施阶段，用户在本会话明确确认“仅该规模完整恢复采用 ≤10 秒，其余仍 ≤1 秒”。适用对象严格限定为冻结D10的完整备份恢复：27548条底层独立记录、36178108字节JSON（约36MB），对应本期公开命令生成的固定备份。该家族完整响应允许 `<=10000ms`，计时仍到同事务完成、目标关系及完整数量读回、页面与必要图片/字体可用及绘制结束；至少5个有效样本。原子性、失败无半套、冲突和附件完整性均不放宽。普通页面、日常动作、打印、导出、旧数据转换及其他恢复规模仍 `<=1000ms`。授权不代表产品支持上限、不自动覆盖更大备份，也不修改AGENTS.md的通用规则。原先按1秒门槛记录的失败保留原版本身份，新复测分别记录门槛与确认来源。

真实双标签升级验收发现，共享PCS资料准备可能先于后道仓库读取而被旧连接阻止，原先落入无恢复动作的通用失败页。本期局部调整 `main.ts` 的后道入口错误分支与 `storage-notice.ts`，只在共享读取的实际失败原因匹配时显示原因、关闭旧页及现有重新读取动作；PDA错误页暂停未准备的执行处理器。共享数据库引擎不改，关闭旧连接后真实重载验证版本升级、共用记录保留及无后道种子写入。

最终独立语义审查发现恢复候选未完整沿用正常命令的关联约束：出货与来源复检、库存及实收数量不一致仍可能被接收，订正可换原责任/SKU，post Q可脱离可信QC通过量，完成复检条码可不完整。本期在F现有记录校验回调补齐这些已确认规则，不新增业务流程。新逐项记录要求完整原子关联，历史全套记录保留原合法零SKU行；缺失历史WH/实收/反向链接保持未知，不凭当前人员补造，已有矛盾仍拒绝。原11种恢复成功的红色反例保留独立版本；绿色通过后才关闭该项。
