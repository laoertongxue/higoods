## 1. 目标与完成标准

本轮修复四个已由起点页面和代码共同确认的问题：待加工仓 Web 扫码收货入口表达缺失；后道单把现场动作强制导向 PDA；PDA 后道详情错误地再次勾选质检已确认项目并把结果字段平铺；差异日志详情没有按层级展示。

完成必须同时满足：

1. Web 和 PDA 读取并写入同一后道任务与回货确认事实。
2. Web 待加工仓可扫描或输入完整送货单号完成兜底收货。
3. Web 后道单可开始、填写 SKU 完成数量、逐原因增减瑕疵并完成。
4. PDA 逐 SKU 以完成数量输入为主动作；质检已确认的加工项目只读，瑕疵调整进入独立页面。
5. 任一 SKU 没有合法完成数量时，界面与领域函数都阻断完成。
6. 日志详情三个层级互斥展示，操作记录按阶段分组。
7. 最后一次修改后的专项检查、构建、命名 Web/PDA 页面和治理检查通过。
8. 不把本地浏览器测试声明为真实现场 PDA 或生产数据验收。

## 2. 事实依据与范围

### 2.1 起点代码事实

- `warehouse.ts`当前存在“回货确认”弹层，但入口没有表达“扫码收货”及 Web 兜底定位。
- `work-orders.ts`只提供打印、PDA 执行和查看全流程，没有 Web 执行动作。
- `pda-post-finishing-flow.ts`在每个 SKU 下平铺合格、瑕疵、返厂和六类附加输入。
- `audit-records.ts`在一个详情页同时展开链路、差异、时间线和瑕疵。
- `post-finishing-full-flow.ts`现有完成函数只验证数量和原因，没有加工项目完成门禁，也没有可跨端继续的加工草稿。

### 2.2 本次范围

- 后道待加工仓 Web 扫码收货入口与弹层。
- 后道单 Web 列表与详情的应急操作。
- 后道任务完成数量草稿、加工项目只读展示、SKU 调整和完成门禁。
- PDA 后道详情和独立 SKU 调整路由。
- 差异与操作日志详情层级。
- 相应路由、处理器、测试、总体设计、矩阵和审查记录。

### 2.3 非范围

- 不修改质检、复检、出货的已确认主业务规则。
- 不新建真实接口、数据库、生产鉴权或离线队列。
- 不把所有历史后道领域模型合并重构。
- 不宣称现场 iData、真实照片或生产业务数据已经执行。

## 3. 工作包

### WP-01 共享后道数量草稿

**业务目标**：PDA 和 Web 能在同一后道单上继续完成数量填报和 SKU 结果调整。

**文件/符号**：

- `src/data/fcs/post-finishing-full-flow.ts`
- `PostFinishingPostTask`
- 新增加工草稿结构、项目更新、SKU 调整、草稿完成函数

**修改**：

1. 每个 SKU 保存完成数量、各瑕疵原因当前数量、返厂、更新人和时间。
2. 完成数量保存覆盖同一草稿，不重复累计；加工项目只读取质检结果，不进入后道更新。
3. 瑕疵调整使用“增加/减少 + 原因数量明细”，逐原因校验整数、余额和上限。
4. 删除后道责任方与现场证据图片的输入和写入。
5. 返厂接收责任只能从可搜索候选列表选择。
6. 从“完成数量 - 瑕疵合计 - 返厂”生成合格数量并调用现有完成链路。
7. 完成前验证全部 SKU 均有合法完成数量，或瑕疵/返厂已覆盖该 SKU 全部应加工数量；整批瑕疵允许零合格完成。
8. 完成数量、逐原因瑕疵调整和 Web 应急接管写入业务日志。

**验证证据**：领域专项覆盖空草稿、部分数量、全部数量、未填完成数量先登记瑕疵、整批瑕疵零合格完成、两种原因增加、逐原因减少、减少超余额、超量、跨端继续和唯一复检单。

**完成条件**：不依赖 DOM 即可阻断未完成数量归类或错误原因明细；PDA/Web 只调用同一组领域函数。

4. 定位后仍进入既有逐 SKU 确认、授权、入库和流水逻辑。

**验证证据**：完整号进入、部分号阻断、回车/按钮两种入口、确认后库存与日志一致。

**完成条件**：页面不再让用户误以为 Web 收货能力已删除，也不产生第二套业务数据。

### WP-03 后道单 Web 应急处理

**业务目标**：PDA 故障时 Web 能完成同一张后道单。

**文件/符号**：

- `src/pages/process-factory/post-finishing/work-orders.ts`
- `src/pages/process-factory/post-finishing/work-order-detail.ts`
- `src/pages/process-factory/post-finishing/events.ts`

**修改**：

1. 列表保留“PDA 执行（优先）”，新增“Web 应急处理”。
2. 详情识别全流程后道任务并展示共享加工草稿。
3. Web 可开始、填写完成数量、进入 SKU 逐原因调整、完成后道。
4. 操作人不一致时提供带原因的应急接管，不静默覆盖。
5. 历史后道详情继续使用原有渲染，不破坏已有路由兼容。

**验证证据**：Web 独立完成一张单；PDA 先操作后 Web 继续；旧详情路由仍可打开。

**完成条件**：Web 不只是跳转 PDA，所有关键动作有可执行入口并写回共享事实。

### WP-04 PDA 后道完成数量重构

**业务目标**：把小屏主流程聚焦到逐 SKU 填写完成数量。

**文件/符号**：

- `src/pages/pda-post-finishing-flow.ts`
- `src/router/route-renderers.ts`
- `src/router/routes-pda.ts`
- `src/main-handlers/pda-handlers.ts`

**修改**：

1. SKU 卡片只读展示质检已确认的加工项目，并提供大尺寸完成数量输入。
2. 删除工序复选框及 SKU 卡片内瑕疵/返厂字段平铺。
3. 保留 SKU 瑕疵调整命名路由，并让每张加工中 SKU 卡片始终显示入口；未保存完成数量时也可直接登记瑕疵。
4. 调整页提供增加/减少切换和每种原因数量输入，删除责任方与现场证据图片。
5. 返厂接收责任使用移动端可搜索的大触控候选列表。
6. 底部完成按钮按已完成数量归类的 SKU 数启用；整批瑕疵/返厂覆盖应加工数量时无需先填完成数量。

**验证证据**：360×800 和 400×806 页面无横向溢出；主动作、返回、保存、门禁和完成闭环通过。

**完成条件**：首屏只要求完成数量；加工项目不可编辑；瑕疵明细只出现在聚焦页。

## 5. 风险与控制

| 风险 | 控制 |
|---|---|
| 新草稿与历史完成结果冲突 | 已完成任务继续读取最终结果；仅待后道/后道中任务使用草稿 |
| Web/PDA 操作人不一致 | 所有更新检查任务所有人；应急接管要求原因并写日志 |
| UI 禁用按钮被绕过 | 领域完成函数再次检查每个 SKU 的完成数量 |
| 瑕疵调整丢失 | 每次保存立即写共享原型状态，返回主任务重新读取 |
| 旧测试仍按工序勾选 | 更新受影响场景；保留核心数量守恒断言，不保留错误 UI 形态 |
| 日志标签隐藏必要事实 | 三个层级均可从固定详情头进入，URL 可刷新和分享 |
| 把本地验证误作现场通过 | 最终把浏览器原型、真实 PDA、生产数据证据分开汇报 |
