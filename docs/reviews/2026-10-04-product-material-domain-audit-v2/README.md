### 2.1 不能忽略的引用方式差异

1. 款式商品资料用配置 ID 引用部分属性，但显示名称读取当前配置。改名会影响历史显示；资料保护不等于已经冻结字典版本。
2. 规格档案颜色和尺码通过配置取得**名称字符串**，记录仍保存名称，没有等价的稳定字典引用。配置改名与规格身份之间没有完整契约。
3. 颜色/尺码配置没有可用项时，规格页面会回退固定颜色和尺码。这会让“停用全部”与“新建不能选”相矛盾。
4. 项目品类来自平面 `categories`；商品资料用 `productCategories` 树；五类物料又用各自硬编码分类。三套分类目前没有明确的目的和映射契约。
5. 物料 SKU 颜色、规格等仍是自由文本，并没有因为基础配置里存在颜色就自动受到统一约束。
6. 风格编号的 `code` 按数组序号生成，显示名称却包含原业务编号；缺号后会错位，例如代码 `44` 对应名称开头 `45-…`。商品资料又会取这个代码作为品类编号，不能把它当可靠的外部业务编码。
7. 当前商品资料配置映射不包含特殊工艺；有配置面板不意味着所有需要的页面都已接入。
8. 商品分类删除保护依赖记录中的 `productCount`；没有据此确认真实全链路引用完整性。本轮没有通过执行删除验证该风险。

直接依据：`pcs-config-dimensions.ts`、`pcs-config-workspace-repository.ts`、`pcs-project-config-workspace-adapter.ts`、`pcs-style-product-information.ts`、`pcs-product-information.ts`、`pcs-product-archives.ts`。

### 2.2 旧库没有一个可以直接整体搬运的“干净字典”

`td_dm1/td_dm2` 同时存在：颜色 106、Colour 660、Color 671；尺码 138、Size 364；Specification 729、Pack Size 115；Material 91。另一套 `td_attr/td_attr_value` 中，部分同名维度的数量并不相同。

这些可能涉及语言、渠道、历史版本或不同属性体系。**不能直接合并后去重，也不能仅凭名称认为其中一套可以删除。** 当前只能确认并存和差异，尚未确认每套的所有写入者、权威关系和线上使用范围。

建议分层维护：业务分类、属性定义、属性值、分类属性模板、外部映射；品牌和组织主数据按各自规则维护。后台可以放在同一设置入口，不能因此变成一个没有业务语义的万能字典。

## 3. 数据库与线上字段的重大语义冲突

| 字段/现象 | 已见证据 | 必须采取的分析口径 |
|---|---|---|
| `vendor` | 两套库商品表注释均为“商品负责人”；线上页面标签为“供应商”，另有“供应商名称” | 人员责任与供方必须分别追溯；不能整体转成 supplierId |
| `fabric_composition_short` | 旧商品表和默认物料表是 P/C/N/A/B 成分简称；默认商品表却是非毛织/毛织/毛织＋梭织 | 同名字段的枚举完全不同，转换必须带来源库、表和版本 |
| `product_type` | 旧商品表混装常规、面料、辅料、物料、组合；默认库商品与 fitting 分离；线上还有纱线、耗材、配件 | 区分类型、用途、加工阶段；不能按一套整数全库转换 |
| `stock_type` | 两套已查结构注释均为“1：SPU 维度，2：SKU 维度”；线上却呈现“原料/面辅料” | 必须核对是否实质切换计库存粒度，不能先改名为加工阶段枚举 |
| `price_type/side_type` | 旧 SKU 的价格类型区分数码印、低价数码印、MJS 染色、GTG 染色；单双面还区分单面、同花双面、不同花双面、渗透印 | 仅保留“染色/印花”会丢失已有信息；工艺规格与定价方式需分别建模 |
| SKU `status` | 旧库 0 正常、1 下架；默认库 0 无效、1 有效 | 数字同值可能表达相反可用性，不能统一直接映射 |
| 商品 `status` | 旧库表达采集阶段/链接无效/删除；默认库表达草稿/启用/失效 | 采集、档案生命周期、审核、上架必须拆分 |
| `compare_at_price` | 相关 SKU 表注释为“成本价” | 不能按通用电商字段习惯解释成划线价 |
| `td_products_collection.num` | 注释“商品位置” | 不能直接当作组合商品的组件数量 |
| `category` | 默认商品属性表注释“只有一个值”；原型有 `categoryTags` 多值 | 要明确营销标签与正式归类，不能擅自单选转多选 |
| 商品分类 | 平台扩展表存在四级类目及平台属性 | 平台类目不应被内部三层树截断 |
| 长度/空差/重量 | 线上物料表单“空差(cm)”“幅宽(cm)”“克重(KG)”；原型有长宽高及克重文本 | 空差不是包装长度；重量与 g/m² 不是同一量纲 |
| 金额精度 | 默认 fitting 成本 decimal(6,2)，旧商品成本 decimal(11,4)，线上运输样本 0.001 | 直接迁到两位小数会丢精度；单位币种亦必须同时保留 |
| 运输成本 | `td_spu_print_dye_price.transport_cost` 注释为“含运费成本价”；其他业务表同名列另有转运含义 | 不能把所有 transport_cost 一概当作可相加的纯运费 |

`td_products_supplier` 已有商品/原材料与供方的关系线索；`td_products_cost` 已区分生产、现货采购、样衣采购等成本类型；`td_products_extend/extra` 保存区域内容与平台属性。线上字段移出主档不等于丢弃，而是映射到有明确责任的关联对象。

FLLR081 编辑页可见采购价格、独立币种、ID 进口运输成本及其币种、综合成本等。两套已查测试库没有找到这些字段的完整对应结构。只在其他表查到同名或近似字段，语义不同。

此项需要当前线上后台对应版本的只读代码、表结构/视图及脱敏响应样本。**在补齐前，不能承诺线上价格信息已完成一一映射。**

### 3.2 补查的约束与数据分布

- 默认库相关 24 表返回 75 条索引列记录，旧库 12 表返回 35 条。已查元数据中，商品和 SKU 编码没有对应的数据库唯一索引；不能先假设“编码就是全局唯一主键”。
- 当前账号在这些表范围内未查到外键及触发器记录；这不证明应用没有校验，也不排除账号可见性限制。
- 默认库物料表 215 行：无空主码、无重复主码，150 行成分为空、1 行成本为 0。不能把这些测试数据的缺值率直接当作生产情况，也不能认为所有辅料必须填写成分。
- 默认库供方关系 1,961 行，全部 `supplier_id` 为 0 或空；旧库商品 170,580 行也全部没有有效 `supplier_id`。存在名称/文本信息不等于具备可靠供方外键，迁移需要实体匹配和待确认状态。
- 旧库商品总数 170,580，包含各生命周期；主码没有空值，但重复主码查询返回达到 20 组上限，示例 `YSSZAW122101` 为 6 行、`FADAH25033110` 为 3 行。SKU 重复查询也达到 20 组上限。**这是存在重复的证据，不是重复总量统计；重复中是否含历史删除记录须另看状态。**
- 对上述样本进一步核对：`YSSZAW122101` 的 6 行都是已采集、审核通过；`FADAH25033110` 的 3 行则包含 2 行删除和 1 行有效历史。SKU `BTSZIDOE050704` 在同一父商品下有 5 行相同编码且均为正常、未删除。可见既有历史重复，也有当前状态相同的重复，不能用一条统一去重规则处理。
- 旧库全表关联聚合发现 48,989 条 SKU 的 `p_id` 找不到商品主键，另有 82 条 SKU 的非空 `spu` 与其已关联父商品主码不一致。统计包含全部状态；它证明此测试数据集存在关系不完整，**不能推断线上也有同样数量或直接自动删除这些记录**。脱敏样本和聚合见 [身份核查结果](database-identity-results.json)。
- 旧库 SKU 按状态、删除标记及价格类型得到 8 组分布，价格类型存在 0、1、2、3、4。状态与价格类型不是同一枚举，不能从某个默认值代表全部记录。
- 旧库物料的计价单位实际出现 M、Yard、PCS、KG、Pair、DZ、Bunch、roll、cns 共 9 种，且面料类型也存在 PCS 计价。不可依据类型强制把所有面料改成米。单双面字段在本次非零价格类型的聚合样本中均为 0；其他枚举来自表注释，不能说这些样本已验证全部单双面场景。见 [单位和加工分布](database-unit-process-results.json)。

上述聚合和样本均为测试库证据，SQL 及原始聚合结果保存在附件中。

## 4. 五类物料档案并未形成分类属性契约

| 类别 | 当前 SKU 主/次输入 | 主要问题 | 候选修正方向 |
|---|---|---|---|
| 面料 | 颜色 / 克重 | 克重文本、单位和成分缺少结构；幅宽身份作用未统一 | 分类模板定义成分、组织、幅宽、克重、弹性等；逐项决定 SPU/SKU/批次层级 |
| 辅料 | 颜色 / 规格 | 花边、纽扣、拉链、织带共用宽泛输入 | 各子类定义尺寸、齿型、材质等身份维度，避免所有字段通用必填 |
| 纱线 | 颜色 / 纱支 | 分类固定为车缝线、包缝线、绣花线、织带线；不能代表全部毛织/原纱业务 | 区分用途和物理规格；纱支体系、股数、捻度、成分与筒装另行定义 |
| 耗材 | 颜色 / 规格 | 同样出现面料成分、门幅、克重字段 | 用适用性模板控制，不强迫无关录入 |
| 配件 | 适配设备 / 型号规格 | “适配设备”实际进入 `colorName` | 设备兼容关系应结构化，多设备适配不能伪装成颜色 |

主档记录 27 个字段，SKU 记录 29 个字段，另有草稿输入、用量引用、日志和单位换算对象，详见字段清单。五类建档表单仍高度共用，分类、单位选项也主要硬编码，不能认为已被“基础配置”管理。

物料单位换算虽有 `fromUnit/toUnit/factor` 类型和保存方法，但当前表单未完整表达换算维护及依据。米↔码可以是固定换算；公斤↔米取决于规格或批次实际情况，卷/包/箱还需要包装含量，不能统一写一个永久系数。

**保留已明确的 TMF 特例：**织带、绳子半成品的幅宽/直径属于其主档规格，颜色/花型属于 SKU；截断长度、尺码用途、端头属于加工规格、批次或包装，不因一个用途就无限新增永久 SKU。不能将这一规则无条件套给其他所有物料类别。

当前 SKU 存成本和运费数值，但缺少完整币种、适用组织、采购条件、有效期和价格版本。编辑 SKU 时编码会随属性重建：即便内部 ID 不变，也需明确旧编码、条码及历史单据的追溯规则。

## 5. 原料、加工物料与变体的身份尚未统一

当前至少有两套表达：

1. `MaterialSkuRecord` 保存原料 SKU、染后中间 SKU、印染加工链、色号和花型。
2. `MaterialVariantRecord` 另存基础编码、前驱变体、工艺步骤、层级，`materialSkuId` 可选。

页面新建基础变体可从物料 SPU 编码开始而不绑定 SKU；BOM 旧数据转换却基于具体 SKU 建基础变体。因此“一个变体代表什么”在两个入口不一致。染色分支的步骤/层级处理又不同于其他工艺追加，同类工艺重复被统一阻止；不能将这些现有代码条件直接当成已确认业务规则。

用户现已明确各加工阶段有对应物料档案编码，先染后印需承接染后完整编码。建议统一加工阶段/SKU身份及前驱关系，工艺定义描述如何加工，实际加工单记录哪次执行；具体库存事实由WMS独立持有。现有两套变体模型与新规则如何统一仍需评审。

特殊工艺标签、物料加工能力、工艺路线、实际加工记录必须分别命名。默认测试库的 FCS 工艺/工序还具有作用对象、生成任务、标准工时、计价币种/单位等信息，不能降为原型中的 5 个固定工艺引用。

## 6. 渠道店铺商品当前仍受项目流程和上传批次牵引

当前 `PcsProjectChannelProductRecord` 有 49 个字段，其中项目/节点必填、顶层单 SKU、上架批次和渠道商品状态共存。规格行有 16 个字段，保存外部 SKU、sellerSku、颜色、尺码、图片、价格和库存，但**没有每行明确的内部 SKU ID**。

由此产生的问题：

- 历史线上商品未必有 PCS 项目，不能为了导入强行补一个虚构项目。
- 一条 listing 的多规格不能靠顶层一个内部 SKU 代表；必须逐行映射。
- 当前标题、价格、币种、图片同时存在多套近似字段，需要明确正文、默认值、覆盖值、发布快照和平台实际值。
- 列表 `resolveSpuCode` 优先取平台商品 ID，随后取其他编码；该值还参与分组。内部 SPU 与外部 PID 混用后，回填外部 ID 可能改变列表归组身份。
- 汇总读取各历史记录规格行，而库存取当前记录，口径可能不一致。历史发布尝试不能累加成当前规格数量。
- `resolvePcsStoreCurrency` 返回结算币种；已有店铺样本为销售 MYR、结算 USD。两个币种不能混为一个“店铺币种”；未知店铺也不应无提示兜底到另一个店铺或 IDR。
- 上架成功、平台审核通过、实际在售、同步成功、测款通过是不同事实，不能共用一个状态字段。

候选对象为：店铺、渠道商品 Listing、渠道规格 Listing SKU、内部 SKU 映射、发布任务、同步结果/差异、测款引用。项目、技术包和测款可追溯，但不决定 listing 是否可以独立存在。

## 7. 价格、库存、供应商：按用户补充修订的目标归属

| 线上信息 | 候选归属 | 档案页面如何覆盖 |
|---|---|---|
| 商品负责人 Vendor | 责任人/组织引用 | 显示负责人，不转换成供方 |
| 供应商名称、地址、电话 | 采购/供方主数据 | 已确认第一种方案：物料档案不维护供方信息或供方视图；旧值保留迁移来源 |
| 供应商货号、采购链接、供货地区、MOQ、交期 | 采购侧来源/交易条款 | 实际采购时明确，不属于物料档案字段或建档前置条件 |
| 标准采购成本与币种 | 物料标准成本版本 | 不依赖档案绑定供方；实际报价另属采购 |
| 标准运输费及逐道加工费用 | 物料标准成本版本 | 综合标准成本=标准采购+运输+累计加工费，显示每层承接与新增；上游标准采购成本调整后下游新标准自动生效；品牌差异仍待核 |
| 实际采购、运输、加工费用 | 采购/物流/生产单据及实际成本核算 | 不当成档案标准成本，也不无提示覆盖标准成本 |
| 库存、货架库存、可售库存 | WMS唯一库存来源 | 商品/物料档案无库存字段或摘要；在WMS对应对象查看 |
| 吊牌价、直播价、批发价、清仓价 | 销售定价/促销 | 区分市场、店铺、客群、生效期及价格类型 |
| 平台回传数量 | 必要时作为同步记录/差异中的外部观察值 | 不作为档案库存；发布数量从WMS已确认口径取得 |

例如 MODXU26100225 表单总库存 400、每规格 100，而列表货架库存为 0。这是旧系统不同字段的现状证据；目标已明确为WMS唯一库存来源，旧档案值不能未经核对直接作为WMS余额。

例如 FLLR081 有成本 8、SKU 成本展示 8.001、采购 4、标准运输 0.001、综合 4.001。这些历史值如何对应新标准成本组成仍须核对，不能自动修正原值。新标准成本的组成已由用户明确为采购、运输和逐层加工费用。Asaya 价格为 0 同理：可能未维护、默认值或真实零价，本轮没有证据确定。

## 8. 存储、读取及历史冻结的实际状态

基础配置、物料档案、物料变体、汇率仍有直接 localStorage 业务持久化入口，未纳入当前 PCS 按记录 IndexedDB 桥接登记。**不是所有 PCS 模块都未迁移，也不是已有 IndexedDB 就代表这些对象已迁移。**

物料变体保存捕获 localStorage 异常后仍保留内存状态，存在“界面成功但未落盘”的风险。配置和物料档案仍有整包快照及先更新内存再写入路径。本轮做源码定位，没有执行破坏性容量测试。

另一个明确入口：`getTechnicalDataVersionContent` 读取草稿时调用旧 BOM → 基础变体转换，必要时创建持久变体并保存 BOM 补丁。普通读取因此可能产生写入，应作为后续显式迁移范围；不能为了本次只读核查去触发和修改现有草稿。

也应保留正确事实：已发布技术资料的 BOM 成本快照已有冻结和禁止覆盖规则；汇率变化针对草稿触发复核失效。**本轮不认定已发布 BOM 会被当前汇率直接重算覆盖。**需要解决的是页面“统一读取最新汇率”的过宽表述及不同存储之间的动作原子性。

后续界面要求已明确：PCS 全部页面取消浏览器资料迁移、备份和恢复维护工具，包括公共浮层及异常时出现的迁移面板；普通读取失败提示和重试保留。本地代码移除情况见 [业务基线第 9 节](confirmed-rules-and-refinements.md#9-pcs-全部页面取消浏览器资料维护工具)。这不代表底层旧资料、缺失附件或全部存储问题已修复，也不授权清空数据。

## 9. 本轮结论

两大模块可以有集中页面，但不能各自变成包揽所有业务的大对象。商品档案限定为款式衣服的SPU、SKU及渠道售卖关系；物料档案负责物料身份、加工阶段编码和标准成本；渠道店铺商品保留同PID多外部SKU与内部SKU的关系；实际采购、实际成本、WMS库存及加工执行各自保有写入责任。

基础配置应先厘清业务语义和作用范围，再建立可复用的属性维护。当前最优先的工作是关闭身份、属性、价格、状态和旧数据映射的未决项，随后才能冻结架构与字段、形成实施计划。未决清单见下一份文档，不以字段清单行数替代业务查明程度。
